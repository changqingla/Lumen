## 2. 3 分钟项目讲解版

如果面试官让你直接介绍项目，可以按下面这个结构讲。

### 2.1 标准版

`lumen` 是一个面向复杂任务自动化的 AI Agent runtime 平台。它不是普通聊天应用后端，而是把模型调用、上下文管理、工具调用、沙盒执行和扩展能力接入组织成一个统一的 Agent 运行时。

这个项目的核心点有三块。

第一块是 Agent loop。我们没有把 Agent 理解成单纯的“模型加工具”，而是基于 middleware 组织了一条运行时执行链，把线程状态、上传文件、沙盒生命周期、上下文压缩、Todo 规划、记忆注入和澄清机制都纳入统一流程，所以 Agent 在多轮任务里能持续规划、执行和迭代。

第二块是工具系统。我们做了统一工具装配，支持普通本地工具、内建工具和 MCP 工具动态合并。这样外部 MCP server 暴露的能力可以透明注入给 Agent，模型不需要区分工具来自本地还是远程服务。

第三块是执行环境。我们设计了线程级容器沙盒机制，让同一个 thread 在多轮任务中尽量复用同一个执行环境。为了解决容器冷启动和重复创建问题，我们引入了确定性 `sandbox_id`、warm pool、空闲回收、懒加载和并发锁，提升了多轮任务中的环境连续性、稳定性和资源利用率。

如果总结成一句话，这个项目的价值就是把大模型从“会回答问题”扩展成“能在真实环境里稳定完成复杂任务”的 Agent 系统。

### 2.2 更简洁版

`lumen` 是一个 AI Agent runtime 平台，重点解决多轮任务执行里的上下文维护、工具调用和执行环境治理问题。项目基于 middleware 组织 Agent loop，支持 MCP 和 skills 扩展，并通过线程级容器沙盒、warm pool 和并发控制提升 Agent 在真实任务场景中的执行稳定性和环境复用能力。

## 3. 1 分钟项目讲解版

如果面试官给你的时间比较短，可以用这版。

这个项目是一个面向复杂任务执行的 AI Agent runtime。我们不是只做模型对话，而是把模型调用、上下文管理、工具调用、MCP 扩展和容器沙盒统一成一套运行时。项目里一个比较关键的点是用 middleware 组织 Agent loop，把记忆、Todo、摘要压缩、澄清和沙盒生命周期都纳入统一流程；另一个关键点是线程级容器沙盒复用，通过确定性 `sandbox_id`、warm pool 和并发锁解决多轮任务里的冷启动和重复建容器问题。

## 4. 8 个最高频追问

下面这 8 个问题基本是最容易被追问的部分。建议优先熟悉。

### 1. 你说的 Agent loop 具体是什么？

口语化回答：

我理解这个项目里的 Agent loop 不是自己手写一个 while 循环，而是基于 LangChain 的 agent 框架，再通过 middleware 把运行时能力一层层挂进去。比如线程状态、上传文件、沙盒、摘要压缩、Todo、记忆、澄清这些都不是散落逻辑，而是统一进入主执行链。所以它更像一个 middleware-driven 的 Agent runtime。

### 2. 为什么要用中间件链，而不是把逻辑放进工具？

口语化回答：

因为很多能力不是某个工具自己的职责，而是模型调用前后的统一治理。比如澄清、上下文压缩、记忆注入、沙盒生命周期，这些如果全塞进工具里会特别乱。中间件链的好处是工具本身保持窄职责，而运行时层面的策略可以按顺序统一接入。

### 3. MCP 在这个项目里到底有什么价值？

口语化回答：

MCP 的价值是把远程能力变成本地 Agent 看起来像普通工具的东西。模型并不知道某个工具是远端 MCP server 提供的，还是本地 Python 实现的，它只看到一个统一的工具空间。这样外部服务能力就能比较自然地接入 Agent，而不用每个都单独做一套本地封装。

### 4. skills 和 MCP 有什么区别？

口语化回答：

MCP 更像外部工具能力的接入层，解决的是“Agent 能调用什么远程能力”；skills 更像领域知识和行为约束的扩展层，解决的是“Agent 在某个领域里该怎么做事”。在这个项目里，skills 主要通过 `SKILL.md` 和扩展配置参与提示词与运行时，不是直接等同于一个工具。

### 5. 为什么 skills 只注入索引，不全文注入？

口语化回答：

主要是为了控制上下文长度。因为 skills 多了以后，如果每次都把全文塞进 prompt，很快就会撑爆上下文窗口。所以我们做成先注入技能索引和路径，等模型真的需要时再用 `read_file` 去加载具体内容。这其实是一种按需加载的设计。

### 6. 为什么沙盒要做成线程级复用，而不是请求级？

口语化回答：

因为 Agent 任务天然是多轮的。如果每次请求都重新建环境，上一轮产生的中间文件、工作区状态和任务上下文就很难延续，而且容器冷启动成本也很高。做成线程级资源以后，同一个 thread 在多轮里可以尽量复用同一个执行环境，更适合复杂任务。

### 7. warm pool 是什么？为什么有必要？

口语化回答：

warm pool 可以理解成“已经释放但还没销毁的容器”。这样用户下一轮继续追问时，不用重新冷启动容器，直接把这个环境认领回来就行。它的本质就是把 release 和 destroy 拆开，用一点资源换多轮任务里的执行连续性和响应速度。

### 8. 多进程下怎么避免重复建容器？

口语化回答：

我们做了两层保护。第一层是进程内锁，避免同一个进程里多个线程同时抢同一个 thread 的沙盒。第二层是文件锁，解决多进程场景下的并发创建。再加上确定性 `sandbox_id` 和后端发现机制，后来的进程会优先复用已有实例，而不是直接再建一个。

## 5. 最容易讲出彩的 4 个点

如果面试时间有限，最值得重点展开的是这 4 个点。

### 1. middleware-driven Agent loop

这是你和普通“调个工具”的项目拉开差距的地方。重点讲：

- 为什么不用纯工具函数堆逻辑
- 中间件链如何承接上下文、记忆、压缩、澄清、沙盒生命周期
- 为什么这更适合复杂任务执行

### 2. MCP tool injection

这是你和普通“本地工具注册表”拉开差距的地方。重点讲：

- MCP 在这里是 client 集成层，不是 server
- 远程能力如何透明注入 Agent 工具空间
- 配置热更新和跨进程一致性是怎么处理的

### 3. skills progressive loading

这是你和普通“硬编码 prompt”拉开差距的地方。重点讲：

- skills 是领域能力扩展，不只是文档
- 为什么只注入索引而不全文注入
- 它如何兼顾上下文成本和领域任务能力

### 4. 容器沙盒复用

这是你和普通“会用 Docker”拉开差距的地方。重点讲：

- 为什么沙盒是线程级资源
- 为什么需要确定性 `sandbox_id`
- warm pool、空闲回收、并发锁分别解决什么问题
