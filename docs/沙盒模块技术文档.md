# lumen 沙盒模块技术说明

## 1. 文档目标

本文面向后端开发者与架构维护者，详细说明 lumen 中沙盒模块的实现思路。重点不在接口用法，而在于其内部算法逻辑、状态流转、路径模型、并发控制和生命周期管理。阅读本文后，读者应能够回答以下问题：

- Agent 为什么需要沙盒，以及本项目的沙盒到底隔离了什么
- 同一线程为什么能在多轮对话中“复用同一个执行环境”
- 本地模式与容器模式在路径处理上为什么采用不同策略
- 多进程或多实例场景下如何避免同一线程重复创建多个容器
- 上传文件、工作目录和生成产物如何在宿主机与沙盒之间保持一致
- 沙盒在空闲、释放、驱逐和应用关闭时分别如何处理

### 1.1 先给出六个直接答案

- Agent 为什么需要沙盒：因为它不仅要调用模型，还要执行命令、读写文件、处理上传和生成产物；沙盒模块负责把这些能力绑定到统一执行环境上，并按线程隔离数据空间。
- 为什么同一线程能复用同一个执行环境：因为系统把沙盒视为线程级资源，并通过确定性标识、缓存和 warm pool 等机制尽量复用已有实例，避免重复冷启动。
- 为什么本地模式和容器模式路径处理不同：因为两种后端看到的真实文件系统不同，但项目要求 Agent 始终看到一致的虚拟路径语义，所以需要不同映射策略来收敛到同一个 `/mnt/user-data` 模型。
- 多进程或多实例如何避免重复创建容器：核心做法是确定性 `sandbox_id`、进程内缓存、发现现有实例以及跨进程锁配合，避免同一线程被并发建出多个环境。
- 上传文件、工作目录和产物如何保持一致：项目把每个线程固定映射到 `workspace`、`uploads`、`outputs` 三类目录，并在上传与工具执行链路中同步宿主机和沙盒视图。
- 空闲、释放、驱逐和关闭时如何处理：`release()` 负责轮次级释放，空闲回收和 warm pool 管理负责资源复用，驱逐与应用关闭则负责最终清理和优雅退出。

## 2. 模块定位

lumen 的沙盒模块本质上是 Agent 执行环境的统一抽象层。Agent 在运行过程中需要具备几类能力：执行命令、读写文件、查看目录、接收上传文件、产出新文件，以及把这些行为稳定地绑定到某个会话线程上。沙盒模块的职责，就是在不暴露底层执行介质差异的前提下，为这些能力提供一个统一模型。

从架构上看，沙盒模块位于 Agent 工具层与实际执行介质之间。上层工具只关心“执行一个命令”或“读取一个文件”，不关心底层究竟是当前宿主机、Docker 容器，还是经由 provisioner 创建的远程 Pod。下层 Provider 负责把统一抽象映射到具体运行时。

因此，沙盒模块解决的不是单纯的“安全执行”问题，而是以下几个问题的组合：

- 执行环境抽象：让工具调用不依赖具体运行时
- 线程级隔离：不同会话拥有独立的数据目录和状态绑定
- 路径一致性：让 Agent 始终看到统一的虚拟路径模型
- 生命周期管理：避免每次调用都冷启动一个新环境
- 多进程一致性：让 Gateway 与 LangGraph 进程可以定位到同一线程对应的沙盒
- 文件一致性：保证上传文件、工作区和产物在宿主机与沙盒视图中一致

## 3. 总体设计原则

沙盒模块的实现遵循四条核心原则。

第一，抽象先行。系统先定义统一的 `Sandbox` 与 `SandboxProvider` 抽象，再由不同 Provider 分别实现本地执行与容器执行。这样工具层可以完全依赖抽象接口，而不是具体后端。

第二，线程绑定而非请求绑定。lumen 把沙盒看作“线程级资源”，而不是“单次请求级资源”。这意味着同一条对话线程跨多轮对话会尽量复用同一执行环境，以保留上下文文件、避免冷启动，并提升任务连续性。

第三，虚拟路径统一。无论底层是真实宿主机目录还是容器挂载目录，Agent 都始终使用统一的虚拟前缀 `/mnt/user-data` 访问文件。这使得提示词、工具描述、上传注入和产物返回具有稳定语义。

第四，创建昂贵，复用优先。容器沙盒的冷启动成本高，因此系统将“发现现有实例”“回收 warm pool”“延迟销毁”这些优化放在设计中心，而不是每次执行后立即销毁。

## 4. 核心抽象模型

沙盒模块围绕两个核心抽象展开。

`Sandbox` 表示一个已经可以执行操作的环境实例。它只暴露六类最小能力：执行命令、读取文件、列目录、写入文本文件、更新二进制文件、删除文件。这个抽象故意压缩得很小，目的是把 Agent 真正依赖的操作边界控制在最小集合中，避免把底层执行后端的复杂性泄漏到上层。

`SandboxProvider` 表示沙盒的供给者。它只负责三件事：获取实例、查询实例、释放实例。注意这里是“供给与生命周期管理”而不是“执行”。这种拆分带来的直接好处是，环境供给策略可以独立演进，例如从本地单例切换成容器池，或者从 Docker 切换成 provisioner 管理的远程 Pod，而工具层完全无感知。

围绕这两个抽象，系统又配套了一组运行时状态：

- `sandbox`：记录当前 Agent 轮次绑定的 `sandbox_id`
- `thread_data`：记录当前线程的工作区、上传目录、产物目录真实路径
- `thread_directories_created`：用于本地模式下避免重复创建目录
- Provider 内部缓存：记录活动沙盒、线程到沙盒的绑定关系、最近活跃时间、warm pool 等

这些状态共同构成一个从 Agent 到执行环境的映射网络。

### 4.1 代码入口与职责映射

如果从代码层面理解沙盒模块，最关键的入口集中在以下文件中。

- `backend/src/sandbox/sandbox.py`
  这一层只定义抽象接口 `Sandbox`。所有执行后端都必须实现六个核心方法：命令执行、文件读取、目录遍历、文本写入、二进制更新和文件删除。它不包含任何调度逻辑，作用是统一上层调用面。

- `backend/src/sandbox/sandbox_provider.py`
  这一层定义 `SandboxProvider` 抽象，并通过 `get_sandbox_provider()` 完成具体 Provider 的动态装配。这里的关键点不是业务逻辑，而是“根据配置解析实现类并缓存为单例”。也就是说，Agent 与工具层实际上永远不直接 new 某个具体 Provider，而是统一通过这个工厂入口拿实例。

- `backend/src/sandbox/middleware.py`
  这里实现了 `SandboxMiddleware`。它负责把 `sandbox_id` 注入到 Agent 状态，并在本轮执行结束后调用 Provider 的 `release()`。如果想看“沙盒何时进入 Agent 生命周期”，这里是第一入口。

- `backend/src/sandbox/tools.py`
  这里是沙盒模块真正的运行时核心。所有内置沙盒工具都定义在这个文件里，而懒初始化、虚拟路径替换、本地模式目录创建、运行时状态回写，也都集中在这里。如果要理解“Agent 发起工具调用后，代码到底如何拿到沙盒并操作文件”，这一层最关键。

- `backend/src/sandbox/local/local_sandbox.py`
  这里实现了 `LocalSandbox`，即本地执行后端。路径映射、命令前替换、输出反向替换，以及本地文件读写，都在这一层完成。

- `backend/src/sandbox/local/local_sandbox_provider.py`
  这里实现了 `LocalSandboxProvider`。它的职责很集中：维护单例 `LocalSandbox`，并在初始化时注入技能目录映射。

- `backend/src/community/aio_sandbox/aio_sandbox.py`
  这里实现了 `AioSandbox`。它不直接操控容器，而是把统一的 `Sandbox` 方法映射成 `agent_sandbox` HTTP API 调用，因此这一层可以看作“沙盒实例的远程客户端适配器”。

- `backend/src/community/aio_sandbox/aio_sandbox_provider.py`
  这里实现了容器模式的主要调度算法，包括确定性 `sandbox_id`、进程内缓存、warm pool、空闲回收、优雅关闭、线程锁和跨进程文件锁。本文中涉及的资源复用和生命周期策略，绝大多数都落在这个文件里。

- `backend/src/community/aio_sandbox/local_backend.py`
  这里实现了本地容器供给后端，负责 Docker 或 Apple Container 的启动、发现、停止和端口管理。也就是说，Provider 决定“何时需要一个容器”，这个文件决定“如何真的把容器启动起来”。

- `backend/src/community/aio_sandbox/remote_backend.py`
  这里实现了 provisioner 模式下的远程供给。它把创建、发现和销毁动作翻译为对 provisioner 的 HTTP 请求。

- `backend/src/config/paths.py`
  这里实现了线程目录模型和虚拟路径到真实路径的安全解析。只要涉及线程目录、上传路径、产物路径或路径穿越防护，这个文件都是事实上的路径裁决中心。

- `backend/src/agents/middlewares/thread_data_middleware.py`
  这里实现 `ThreadDataMiddleware`。沙盒能正确工作，前提是运行时已经知道当前线程对应的 `workspace_path`、`uploads_path` 和 `outputs_path`，这些状态就是在这里写入的。

- `backend/src/gateway/routers/uploads.py`
  这里不属于狭义沙盒实现，但它承担了上传文件与沙盒文件系统同步的一半责任。特别是在非本地沙盒模式下，这个路由会显式调用 `sandbox.update_file()` 和 `sandbox.delete_file()` 来保持容器视图一致。

如果把沙盒模块理解成一条可执行链路，那么职责大致是：

- 抽象层：`sandbox.py`、`sandbox_provider.py`
- 生命周期接入层：`thread_data_middleware.py`、`middleware.py`
- 运行时工具层：`tools.py`
- 本地执行后端：`local_sandbox.py`、`local_sandbox_provider.py`
- 容器执行后端：`aio_sandbox.py`、`aio_sandbox_provider.py`
- 基础设施供给层：`local_backend.py`、`remote_backend.py`
- 路径与文件一致性：`paths.py`、`uploads.py`

## 5. 线程级数据模型

lumen 的沙盒不是一个“无状态命令执行器”，而是一个与线程目录结构紧密耦合的数据空间。每个线程在宿主机侧都会映射出三类标准目录：

- `workspace`：Agent 主工作区，用于执行中间产物和临时编辑
- `uploads`：用户上传的输入文件
- `outputs`：最终可暴露给用户或外部通道的产物

这个三分模型非常关键，因为它把“输入”“计算过程”“输出”明确分层：

- 上传文件是用户显式提供的数据，生命周期通常受线程约束
- 工作区文件是 Agent 自行创建、修改、实验的中间状态
- 输出文件是要被展示、下载或经由 IM 通道发送出去的最终结果

这种目录设计不仅方便权限控制，也让后续的上传同步、产物暴露、路径校验和消息通道发送可以各自依附于不同目录，而不必在一个混合空间里做复杂判定。

## 6. 虚拟路径模型

沙盒模块最重要的语义统一机制，是把所有线程数据都投影到统一的虚拟根目录 `/mnt/user-data` 下。Agent 看到的路径始终是：

- `/mnt/user-data/workspace`
- `/mnt/user-data/uploads`
- `/mnt/user-data/outputs`

这样做有三个作用。

第一，提示词稳定。无论底层使用本地文件系统还是容器卷挂载，Agent 和工具描述都可以始终引用同一组路径，不需要根据部署模式切换认知模型。

第二，跨模式可迁移。上传中间件、文件工具、产物 API、通道附件发送都围绕虚拟路径工作，因此本地模式与容器模式可以共享绝大部分上层逻辑。

第三，安全边界清晰。所有允许暴露给 Agent 的线程数据都位于 `/mnt/user-data` 之下，后续的虚拟路径解析就可以基于固定前缀和路径归属关系来做越界检查。

路径解析的核心逻辑不是简单的字符串拼接，而是“两阶段校验”：

- 先验证传入路径是否确实以预期虚拟前缀开头，拒绝前缀伪装
- 再把相对路径拼到线程根目录后做规范化解析，并验证结果仍位于线程根目录之内，防止路径穿越

这意味着即便上层传入了看起来合法但含有路径逃逸意图的路径，最终也无法越出线程专属的数据空间。

## 7. Agent 运行时中的沙盒注入

沙盒模块并不是在服务启动时一次性初始化的，而是通过中间件在 Agent 运行时按需注入。

运行顺序上，`ThreadDataMiddleware` 先执行，负责根据 `thread_id` 计算线程目录的真实路径。它默认采用延迟创建策略，也就是先把路径信息写入状态，而不立即在磁盘上创建目录。这样可以避免纯文本问答这种不触发文件操作的请求产生无意义的目录。

随后 `SandboxMiddleware` 负责把沙盒资源接入当前 Agent 状态。它支持两种模式：

- 预初始化模式：在 Agent 调用前就获取沙盒
- 懒初始化模式：直到第一次工具调用时才真正获取沙盒

项目当前更偏向使用懒初始化，因为不是每次对话都需要执行命令或读写文件。这个决策直接减少了无效环境获取与无意义容器唤起。

值得注意的是，沙盒中间件在轮次结束时会调用 Provider 的 `release`。但 release 的含义并不等于“立刻销毁”。本地模式下 release 实际上是空操作；容器模式下 release 会把实例移入 warm pool，而不是立刻停止容器。也就是说，中间件释放的是“当前轮次对该实例的活跃占用”，不是“彻底终结该环境”。

### 7.1 代码中的接入顺序

这一过程在代码里是可直接追踪的。

第一步，`backend/src/agents/lead_agent/agent.py` 中的 `_build_middlewares()` 会把 `ThreadDataMiddleware` 放在 `SandboxMiddleware` 之前。这意味着沙盒中间件运行时，线程路径信息已经在状态里可用。

第二步，`ThreadDataMiddleware.before_agent()` 会从 `runtime.context` 读取 `thread_id`，然后把三类线程目录路径写入状态中的 `thread_data`。默认情况下它只计算路径，不立即建目录。

第三步，`SandboxMiddleware.before_agent()` 在非懒加载模式下会立刻调用 `provider.acquire(thread_id)` 并把 `sandbox_id` 写入状态；而在懒加载模式下，它什么也不做，把真正的获取动作延迟到工具首次调用。

第四步，`SandboxMiddleware.after_agent()` 在本轮执行结束后检查状态或上下文里是否存在 `sandbox_id`，若存在则调用 `get_sandbox_provider().release(sandbox_id)`。这就是 warm pool 能接管资源的原因，因为 release 在容器模式下并不真正 destroy。

## 8. 工具调用路径上的懒加载算法

真正触发沙盒初始化的关键函数不是中间件本身，而是沙盒工具内部的初始化逻辑。其算法可以概括为一个四阶段过程。

第一阶段，检查运行时状态中是否已经存在 `sandbox_id`。如果存在，并且 Provider 还能返回对应实例，则说明本轮中此前工具已经成功获取过沙盒，当前调用可以直接复用。

第二阶段，如果状态里已有 `sandbox_id` 但实例已经不存在，则视为之前环境已被释放或驱逐，进入重建路径。

第三阶段，从运行时上下文读取 `thread_id`，向 Provider 发起获取请求。Provider 返回一个新的或复用的 `sandbox_id` 后，工具将该标识写回运行时状态。

第四阶段，从 Provider 查询具体实例对象，并同步把 `sandbox_id` 写入运行时上下文，保证轮次结束时中间件能够正确释放它。

这个算法的意义在于，沙盒获取是“工具首次使用时发生的幂等初始化”。同一轮内第一次工具调用负责建联，之后所有工具共享状态，不重复走 Provider 逻辑。

### 8.1 这一算法在代码里如何落地

这套逻辑主要由 `backend/src/sandbox/tools.py` 中的几个函数协同完成。

- `ensure_sandbox_initialized()`
  这是工具层真正的懒初始化入口。它先查 `runtime.state["sandbox"]`，如果能从 Provider 找回实例就直接返回；否则读取 `runtime.context["thread_id"]`，调用 Provider 获取新实例，并把 `sandbox_id` 回写到状态与上下文中。

- `get_thread_data()`
  这个函数从工具运行时提取 `thread_data`，供路径映射与目录创建使用。

- `is_local_sandbox()`
  这个函数通过检查 `sandbox_id == "local"` 来决定当前是否处于本地模式。后续是否需要路径替换、是否需要显式创建线程目录，都是基于这个判断分流。

- `ensure_thread_directories_exist()`
  该函数只在本地模式下生效。它读取 `thread_data` 中的三个真实目录路径，执行实际目录创建，并通过 `runtime.state["thread_directories_created"]` 避免同轮重复执行。

- `replace_virtual_path()` 与 `replace_virtual_paths_in_command()`
  前者负责单个路径替换，后者负责命令字符串中的批量替换。也就是说，`read_file`、`write_file`、`ls` 这种参数明确传路径的工具主要依赖前者，而 `bash` 这种整段命令字符串则依赖后者。

五个工具函数 `bash_tool()`、`ls_tool()`、`read_file_tool()`、`write_file_tool()`、`str_replace_tool()` 的结构几乎一致：先初始化沙盒，再按需创建目录，然后在本地模式下进行路径替换，最后把具体动作委托给 `Sandbox` 实例。

这说明工具层实际上使用的是一个模板化调用协议，而不是每个工具各自管理一套沙盒逻辑。这样的实现减少了分支散落和行为漂移。

## 9. 本地模式的实现逻辑

本地模式的目标不是做强隔离，而是提供一种最轻量、零容器依赖、仍保留统一路径语义的执行方式。因此它采用了“单例沙盒 + 路径映射”的设计。

### 9.1 单例模型

`LocalSandboxProvider` 只维护一个全局单例 `LocalSandbox`，其 `sandbox_id` 固定为 `local`。这意味着所有线程共享同一个执行进程视角，但线程级数据目录依然隔离，因为线程实际访问的文件目录是由路径映射和线程目录计算控制的。

这个设计的核心考虑是：

- 本地执行不需要管理昂贵实例，因此不必为每个线程创建独立对象
- 真正需要隔离的是数据目录，而不是 `subprocess.run` 本身的对象身份
- 开发环境里更看重简洁与速度，而不是容器级强隔离

### 9.2 路径映射

本地模式下，Agent 仍然会发出 `/mnt/user-data/...` 或 `/mnt/skills/...` 这样的路径引用，但宿主机显然并不存在这些目录。因此系统会在工具层和本地沙盒内部进行路径映射。

这里实际上有两层映射机制。

第一层是线程数据映射。对 `workspace`、`uploads`、`outputs` 这三个线程目录，工具层会在调用 `bash`、`ls`、`read_file`、`write_file`、`str_replace` 之前，把虚拟路径替换成当前线程的真实宿主机路径。

第二层是固定挂载映射。对技能目录这类非线程级路径，本地沙盒对象内部维护一份“容器路径到本地路径”的映射表。例如 `/mnt/skills` 会映射到真实技能目录。命令执行前，本地沙盒会扫描命令中的绝对路径并做替换；命令输出返回前，又会把宿主机路径反向替换回容器语义路径。

双层映射的价值在于：

- 线程目录依赖运行时上下文，适合在工具层按线程替换
- 技能目录是全局静态映射，适合在沙盒对象内部长期维护

### 9.2.1 一个具体例子：同一路径在两种模式下如何流转

假设当前线程 ID 为 `thread_123`，Agent 需要读取文件 `/mnt/user-data/uploads/a.pdf`。

在容器模式下，这个路径通常不需要在工具层改写。Provider 在创建容器时，会把宿主机线程目录直接挂载到容器中的 `/mnt/user-data/...`：

- 宿主机：`{base_dir}/threads/thread_123/user-data/uploads/a.pdf`
- 容器内：`/mnt/user-data/uploads/a.pdf`

因此，当 Agent 在容器里执行 `cat /mnt/user-data/uploads/a.pdf`、`ls /mnt/user-data/uploads` 或 `read_file("/mnt/user-data/uploads/a.pdf")` 时，容器进程访问的就是挂载后的真实文件。这里的 `/mnt/user-data` 是一个真实存在于容器视角中的挂载点，而不是仅供显示的逻辑前缀。

在本地模式下，这个路径并不会真实挂载到某个 `/mnt` 目录。Agent 虽然仍然会发出 `/mnt/user-data/uploads/a.pdf`，但工具层会先根据当前线程的 `thread_data` 把它替换为宿主机真实路径，再交给 `LocalSandbox` 直接访问本机文件系统：

- Agent 视角：`/mnt/user-data/uploads/a.pdf`
- 工具层替换后：`{base_dir}/threads/thread_123/user-data/uploads/a.pdf`
- 本地实际访问：宿主机上的同一路径文件

如果这是 `bash` 命令，本地模式下工具层会先把命令字符串中的 `/mnt/user-data/uploads/a.pdf` 替换成真实路径，然后 `LocalSandbox.execute_command()` 再通过 `subprocess.run()` 在宿主机执行。如果这是 `read_file` 或 `write_file` 这类显式传路径的工具，工具层同样会先完成虚拟路径到真实路径的替换，然后本地沙盒直接对宿主机文件进行读写。

因此，这个例子的关键区别不是“最终读到的文件是否相同”，而是“路径语义是如何落地的”：

- 容器模式：通过卷挂载让 `/mnt/user-data/...` 在容器中真实存在
- 本地模式：通过路径替换让 Agent 继续使用 `/mnt/user-data/...` 语义，但实际操作宿主机目录

这也是为什么两种模式都能让 Agent 稳定地使用同一套 `/mnt/user-data/...` 提示词和工具说明，但底层实现方式完全不同。

### 9.3 目录懒创建

本地模式下线程目录并不会在每次进入 Agent 时立即创建，而是在首次使用任意沙盒工具时检查并创建。工具层通过一个布尔标记记录目录是否已创建，避免同一轮工具调用重复执行 `mkdir`。

这个算法本质上是在“最晚安全点”做资源初始化：只在真的需要文件系统时，才完成目录物化。

### 9.4 输出反向映射

本地模式的一项细节优化，是命令执行结果和目录列表会做反向路径映射。原因在于如果直接把宿主机绝对路径返回给 Agent，那么 Agent 看到的世界就与提示词和工具描述中强调的 `/mnt/...` 模型不一致，容易造成后续路径推理混乱。

因此，本地沙盒会在输出阶段把命中的宿主机路径尽量替换回容器语义路径。这并不改变真实执行，只是保持认知模型一致。

### 9.5 本地模式的具体实现位置

本地模式的代码实现主要可以按四段来看。

第一段是 `backend/src/sandbox/local/local_sandbox_provider.py` 中的 `LocalSandboxProvider.acquire()`。它不会根据线程创建不同实例，而是只在首次调用时构造一个 `LocalSandbox("local")`，之后永远返回固定 ID。

第二段是同文件中的 `_setup_path_mappings()`。这个函数会读取应用配置中的技能目录，并把技能容器路径映射到宿主机真实路径。也就是说，`/mnt/skills` 这类全局路径不是由工具层按线程计算的，而是 Provider 在初始化时一次性配置进 `LocalSandbox`。

第三段是 `backend/src/sandbox/local/local_sandbox.py` 中的 `_resolve_path()`、`_resolve_paths_in_command()`、`_reverse_resolve_path()` 和 `_reverse_resolve_paths_in_output()`。这四个函数构成了本地模式的双向路径映射核心。

第四段是 `LocalSandbox.execute_command()`、`read_file()`、`write_file()`、`update_file()`、`delete_file()` 和 `list_dir()`。这些方法并没有额外包装复杂逻辑，而是统一遵循“先解析路径，再访问真实宿主机资源，最后在必要时把结果反向映射回虚拟路径”的策略。

其中最值得注意的是 `execute_command()`。它先把命令中的容器路径替换成宿主机路径，再调用 `subprocess.run()` 执行，并在结果返回前把输出中的宿主机路径反向替换回容器语义路径。因此，命令真正运行在宿主机，但 Agent 感知到的仍然像是在一个稳定的虚拟文件系统里工作。

## 10. 容器模式的实现逻辑

容器模式由 `AioSandboxProvider` 驱动，其底层执行对象是 `AioSandbox`。这个 Provider 不是单纯的“创建一个容器然后返回”，而是一个带缓存、发现、预热池、空闲回收和优雅关闭机制的资源调度器。

### 10.1 Provider 与 Backend 分层

容器模式又分成两层。

上层 Provider 负责策略，包括：

- `sandbox_id` 的分配策略
- 线程到沙盒的绑定关系
- 进程内缓存
- warm pool 回收
- 副本数约束
- 空闲检查与关闭

下层 Backend 负责供给方式，包括：

- 本地容器后端：直接管理 Docker 或 Apple Container
- 远程后端：调用 provisioner，由后者创建 K8s Pod 和 Service

这样的分层让“如何调度实例”和“实例由谁创建”彼此解耦。项目因此可以在不改变 Provider 复用策略的前提下切换部署形态。

### 10.2 确定性沙盒标识

线程绑定场景下，Provider 不使用随机 ID，而是根据 `thread_id` 生成确定性 `sandbox_id`。这个设计是容器模式最关键的算法之一。

确定性标识带来的效果是，同一线程无论在哪个进程、哪个 worker、甚至在共享存储前提下的哪个 Pod 中发起请求，都能推导出相同的目标容器名。这样跨进程复用不需要共享一份全局内存状态，只需要能够根据同一输入得到同一标识。

换句话说，系统不是通过“共享一张记录表”来判断某线程已经有容器，而是通过“同样的 thread_id 一定映射到同样的 sandbox_id”这一数学性质，实现分布式视角下的重建与发现。

### 10.3 三层获取算法

容器 Provider 的获取流程可以理解为一个三层回收与创建算法。

第一层是进程内缓存。如果当前进程已经为某线程维护了活动沙盒对象，直接复用，这是最快路径。

第二层是 warm pool。如果活动对象已释放，但容器仍在运行，则可从 warm pool 中直接“认领”回来，省掉冷启动和健康等待。

第三层是跨进程发现与创建。如果前两层都未命中，则在加锁后先尝试通过后端发现是否已有同名容器或远程实例存在；只有发现失败时才真正创建新实例。

这种分层算法的收益在于：

- 常见场景下尽量不触发容器创建
- 允许不同进程接管彼此创建的实例
- 最大限度降低同线程重复建容器的概率

### 10.4 双层锁机制

为了避免并发条件下重复创建沙盒，Provider 同时使用进程内锁和文件锁。

进程内锁负责序列化同一进程中针对同一线程的获取请求，避免多线程竞争。

文件锁负责跨进程序列化。锁文件放在线程目录下，多个进程在对同一线程创建沙盒前必须先争抢同一把文件锁。后进入的进程在拿到锁之后，会重新检查一次进程内缓存和 warm pool，并尝试后端发现。这样即便两个进程几乎同时开始获取，也通常只有先拿到锁的那个会真正执行创建，后者大概率会在发现阶段接管现有实例。

这一点非常重要，因为如果没有文件锁，只靠“确定性容器名”并不能避免竞态，只能在冲突发生后依赖容器运行时返回错误。现在的实现把“检测冲突”前移成了“串行化创建”。

### 10.5 warm pool 机制

release 并不销毁容器，而是把实例放入 warm pool。warm pool 中保存的是仍在运行但当前未被活跃绑定的容器元数据及其释放时间。

这个设计解决的是典型的多轮对话冷启动问题。用户经常会在几十秒或几分钟内连续追问，如果每轮结束后立即销毁容器，那么下一轮很可能又要重新拉起容器并等待健康检查，体验和成本都很差。

warm pool 机制相当于把“释放”与“销毁”拆开：

- release 表示结束当前轮次占用，但保留实例供下一轮快速复用
- destroy 表示真正终止底层容器或远程实例

这也是容器模式能够兼顾隔离性和交互连续性的关键。

### 10.5.1 warm pool 在代码里如何表示

在 `backend/src/community/aio_sandbox/aio_sandbox_provider.py` 中，warm pool 使用一个字典保存，其键是 `sandbox_id`，值是 `(SandboxInfo, release_timestamp)` 二元组。

这个结构意味着 warm pool 记录的不是活动对象本身，而是“如何重新连接到底层运行中的实例”。当 `release()` 被调用时，Provider 会把活动缓存中的 `AioSandbox` 对象移除，但把它的 `SandboxInfo` 留在 warm pool 中。下次 `acquire()` 如果命中相同 `sandbox_id`，Provider 会基于这份 `SandboxInfo` 重新构造一个新的 `AioSandbox` 客户端对象并放回活动缓存。

这也是为什么 warm pool 可以跨轮次复用，却不要求 Python 进程始终持有同一个客户端对象。复用的本质不是“对象没销毁”，而是“底层容器还活着，连接信息仍然可恢复”。

### 10.6 副本数上限与软约束

Provider 支持 `replicas` 配置，用于限制并发保留的沙盒数量。但这里采用的是软限制，而不是硬性抢占。

实现逻辑是这样的：

- 活动沙盒和 warm pool 沙盒共同计入总量
- 达到上限后，系统优先驱逐最旧的 warm pool 实例
- 如果所有槽位都被活动沙盒占满，则不会强行中断正在服务的线程，而是允许临时超限，并记录告警

这说明系统把“不中断在途任务”放在“严格遵守资源上限”之前。对 Agent 系统来说，这是合理的权衡，因为杀掉活动环境会直接破坏当前执行语义。

### 10.7 空闲回收算法

Provider 内部有后台线程定期检查空闲实例。其回收策略分为两类：

- 活动沙盒：依据最近活跃时间计算空闲时长
- warm pool 沙盒：依据释放时间计算空闲时长

当空闲时间超过阈值时，实例会被标记为待销毁。真正销毁前，系统还会对活动沙盒进行二次确认，检查它在快照之后是否已被重新获取。如果已经重新活跃，则跳过销毁。

这个二次确认非常关键，它避免了“扫描线程看到它空闲，但在销毁前已经被新请求复用”的竞态误杀。可以把它理解为一种轻量级的乐观并发控制：先基于快照选出候选，再在执行破坏性操作前重新验证条件仍然成立。

### 10.7.1 获取、释放与销毁在代码层的区别

如果只看接口名，`acquire()`、`release()` 和 `destroy()` 很容易混淆，但它们在实现上职责完全不同。

- `acquire()`
  这是“拿到一个可用实例”的入口。其内部可能命中活动缓存、warm pool、后端发现或真实创建。实现重点是复用与建联。

- `release()`
  这是“结束本轮活跃占用”的入口。它会把实例从活动缓存中移除，解绑线程映射，并把元数据放入 warm pool。实现重点是退场但保温。

- `destroy()`
  这是“真正销毁底层资源”的入口。它会从活动缓存和 warm pool 中彻底删除该实例，并调用 Backend 执行容器停止或 provisioner 删除。实现重点是终结资源。

这三个函数共同构成了一个明确的状态机：活动中、已释放待复用、彻底销毁。文档中所有“复用”“回收”“关闭”的行为，最终都落实在这三个方法的状态迁移上。

### 10.8 优雅关闭

应用关闭时，Provider 会进入幂等的 shutdown 流程：

- 停止空闲检查线程
- 关闭全部活动沙盒
- 再销毁 warm pool 中尚未回收的容器

同时，Provider 还注册了 `atexit` 和系统信号处理逻辑，保证进程异常退出时也尽量完成清理。这样做的主要目的是降低孤儿容器和端口泄漏概率。

## 11. 本地容器后端与远程后端的差异

### 11.1 本地容器后端

本地容器后端直接在当前机器上启动容器。其核心算法要点有三项。

第一，运行时自动检测。在 macOS 上优先尝试 Apple Container，不可用时回退 Docker；其他平台默认 Docker。这个检测让开发环境的容器后端具备更好的平台适配性。

第二，端口分配带重试。系统会从基础端口开始寻找空闲端口，但即便端口看起来空闲，Docker 在短时间内仍可能因为释放延迟拒绝绑定。为此后端在检测到“端口已占用”类错误时会顺延端口并重试，而不是直接失败。

第三，容器名冲突转发现。由于容器名由 `sandbox_id` 确定性推导得来，如果运行时报告“名称已被占用”，系统不会立刻视为失败，而是进一步执行发现逻辑，尝试接管已经存在的容器实例。

这三点结合起来，使本地容器后端在实际运行中对重启抖动、端口竞态和跨进程复用都更稳健。

### 11.2 远程后端

远程后端本身不创建容器，而是把创建、销毁和发现委托给 provisioner 服务。Provider 仍然保留相同的获取、复用、warm pool 与空闲回收策略，但实例供给由远程 HTTP API 完成。

这种模式下，Provider 的角色更像“线程到远程执行资源的调度器”，而 provisioner 则是“真正的基础设施控制面”。对上层工具来说，两者仍然表现为同一套 `SandboxProvider` 语义。

### 11.3 远程实例为何仍由本地 Provider 管理状态

一个容易误解的点是：既然远程后端已经有 provisioner，为什么本地进程还要维护 `_sandboxes`、`_thread_sandboxes`、`_warm_pool` 和 `_last_activity` 这些状态。

原因是 provisioner 只负责“远端是否存在一个可用实例”，并不负责当前 Python 进程内的执行调度语义。Provider 仍然需要在本地维护：

- 哪个线程当前绑定了哪个 `sandbox_id`
- 哪些实例是本轮活跃的
- 哪些实例已释放但仍值得快速复用
- 哪些实例多久没被本进程访问过

也就是说，远程后端替代的是“资源创建机制”，不是“资源调度策略”。调度策略仍然由 `AioSandboxProvider` 统一持有，这也是为什么本地容器模式和远程 provisioner 模式能共享同一套上层算法。

## 12. 文件一致性算法

沙盒模块不只负责命令执行，也负责让线程文件视图在不同执行模式下保持一致。

### 12.1 上传文件同步

用户上传文件后，文件首先写入宿主机线程的 `uploads` 目录。如果当前是本地模式，这已经足够，因为本地沙盒最终访问的就是宿主机文件。

但在容器模式下，仅仅写宿主机目录并不足够。尤其是当容器视图不是自动共享到最新宿主机状态时，系统会显式调用沙盒的 `update_file`，把上传内容同步写入容器中的虚拟路径。若文件还被转换为 Markdown，也会把转换后的版本一并同步。

因此，上传流程在算法上遵循“双写策略”：

- 一份写入宿主机线程目录，作为持久化源数据
- 一份按需同步到非本地沙盒，作为运行时可见数据

这种策略确保无论后续访问来自 Gateway、Agent 工具还是外部下载接口，都能看到一致文件。

### 12.1.1 上传同步的代码落点

这一逻辑主要落在 `backend/src/gateway/routers/uploads.py` 中的 `upload_files()`。

它的执行顺序是：

- 先通过 `get_uploads_dir(thread_id)` 得到线程上传目录
- 再通过 `get_sandbox_provider().acquire(thread_id)` 获取当前线程对应沙盒
- 把上传内容写入宿主机 `uploads` 目录
- 如果当前不是本地模式，则调用 `sandbox.update_file(virtual_path, content)` 同步到沙盒内虚拟路径
- 如果文件扩展名需要转 Markdown，则在宿主机生成 `.md` 文件，并在非本地模式下继续同步该 Markdown 版本
- 最后调用 `provider.release(sandbox_id)` 结束这次同步流程

也就是说，上传路由本身就是沙盒模块的一部分外围实现，因为它负责把“外部输入文件”纳入线程级执行空间。

### 12.2 删除文件同步

删除上传文件时也遵循同样原则：

- 先删除宿主机线程目录中的文件
- 如果是非本地沙盒，再调用沙盒删除虚拟路径中的对应文件

这使得“宿主机状态”和“执行环境状态”始终同步收敛，而不会出现界面上删掉了文件、容器里却还能继续读取的幽灵状态。

### 12.2.1 删除同步的代码落点

对应的删除逻辑同样在 `backend/src/gateway/routers/uploads.py` 中。删除流程并不复杂，但它体现了项目对一致性的要求：

- 先删除宿主机线程目录中的目标文件
- 再根据当前 `sandbox_id` 判断是否为本地模式
- 若不是本地模式，则调用 `sandbox.delete_file("/mnt/user-data/uploads/...")`
- 最后释放沙盒

从代码组织上看，上传与删除都没有直接操作容器或远程 API，而是统一经由 `Sandbox` 抽象执行。这样保持了文件同步逻辑对底层后端的解耦。

### 12.3 产物路径解析

产物读取接口并不直接信任请求中的任意路径，而是要求其必须是线程虚拟路径，然后通过统一的虚拟路径解析逻辑映射到宿主机路径。随后还会再次校验是否越出线程根目录。

这套逻辑的重点是：对外暴露的下载与查看能力，虽然最终落到宿主机文件系统上，但入口语义仍然是线程范围内的虚拟文件，而不是任意真实路径。

## 13. 子代理与沙盒复用

lumen 的子代理系统不会为每个子代理额外创建一套全新沙盒，而是会把父代理的 `sandbox` 状态与 `thread_data` 状态透传给子代理执行器。这样一来，子代理和父代理看到的是同一个线程工作空间。

这种设计非常重要，因为很多复杂任务本质上是“多个执行者协作完成同一工作目录中的任务”。如果子代理默认使用全新隔离环境，那么主代理写下的中间文件、下载的依赖、上传的素材对子代理都不可见，协作就会退化成纯文本委派。

因此，项目在子代理层面选择的是“共享线程级环境，隔离逻辑角色”，而不是“隔离一切运行上下文”。

### 13.1 子代理复用在代码中的实现点

这部分逻辑位于 `backend/src/subagents/executor.py`。

`SubagentExecutor` 初始化时会接收来自父代理的 `sandbox_state` 和 `thread_data`。随后在 `_build_initial_state()` 中，这两个状态会被直接写入子代理的初始状态对象。

子代理创建自身 Agent 时仍会挂载 `ThreadDataMiddleware` 与 `SandboxMiddleware`，但这两个中间件被配置为懒初始化，并优先复用已经存在的父级状态。换句话说，子代理并不是绕过沙盒中间件，而是让中间件在看到现有状态时自然进入复用路径。

这是一种很稳的实现方式，因为它保留了与主代理一致的运行协议，而不是为子代理单独发明一套“共享沙盒”的特殊分支。

## 14. 典型调用链

为了避免文档停留在概念层，可以把一次典型的文件工具调用具体化为以下代码级链路。

当用户发起一个会触发 `read_file` 或 `bash` 的请求时，`backend/src/agents/lead_agent/agent.py` 构建出的 Agent 会先运行 `ThreadDataMiddleware`，将当前 `thread_id` 对应的三个线程目录路径写入状态。

随后模型决定调用某个沙盒工具，工具实现位于 `backend/src/sandbox/tools.py`。工具函数首先调用 `ensure_sandbox_initialized()`。如果状态里还没有沙盒，它就通过 `get_sandbox_provider()` 找到当前配置对应的 Provider，并调用 `acquire(thread_id)`。

如果当前配置是本地模式，这个调用会进入 `backend/src/sandbox/local/local_sandbox_provider.py`，返回固定的 `local` 单例沙盒。如果当前配置是容器模式，这个调用会进入 `backend/src/community/aio_sandbox/aio_sandbox_provider.py`，经历活动缓存检查、warm pool 检查、跨进程锁保护下的发现或创建，并最终返回一个 `sandbox_id`。

拿到实例后，工具会在本地模式下用 `replace_virtual_path()` 或 `replace_virtual_paths_in_command()` 把 `/mnt/user-data/...` 翻译成宿主机线程目录，再调用 `Sandbox` 实例执行真正的读写或命令动作。

如果是 `LocalSandbox`，最终执行会落到 `backend/src/sandbox/local/local_sandbox.py` 的方法中，通过宿主机文件系统和 `subprocess.run()` 完成。如果是 `AioSandbox`，最终执行会落到 `backend/src/community/aio_sandbox/aio_sandbox.py` 的方法中，通过 `agent_sandbox` 客户端把操作转成 HTTP 请求发给沙盒容器。

当这轮 Agent 执行结束后，`backend/src/sandbox/middleware.py` 中的 `SandboxMiddleware.after_agent()` 会被触发，并调用 Provider 的 `release()`。本地模式下这基本是无操作；容器模式下则进入 warm pool，从而为下一轮复用做准备。

这条调用链说明，项目在代码层并不是“某个地方统一处理所有沙盒逻辑”，而是把它拆成了：状态准备、中间件接入、工具懒加载、Provider 调度、后端执行、轮次释放这六个阶段。理解这一点后，再看各个文件的实现会清晰很多。

## 15. 失败语义与异常处理

沙盒模块的错误处理遵循一个实用主义原则：尽量把底层错误转换成对 Agent 可消费、可恢复的文本反馈，同时在关键边界上保留显式异常。

例如工具层在调用沙盒失败时通常会返回以 `Error:` 开头的文本，便于模型将其视为普通工具结果继续推理；而 Provider 在创建实例失败、路径解析越界、运行时缺少 `thread_id` 等场景下则会抛出更明确的异常，因为这些问题属于系统级状态错误，不适合静默吞掉。

从算法视角看，这种分层错误策略有两个优点：

- 工具执行错误不会中断整个 Agent 图，而是转化为可观察的推理输入
- 资源调度和安全校验错误会被尽早显式暴露，避免产生隐蔽的不一致状态

## 16. 设计权衡

沙盒模块并不是追求最强隔离或最简单实现，而是在多种目标之间做了平衡。

### 16.1 为什么本地模式使用单例

因为本地模式主要用于开发与轻量部署场景，容器级隔离不是首要目标。使用单例能显著简化实现并消除无意义的实例管理成本，而线程级数据隔离仍可通过目录模型实现。

### 16.2 为什么容器模式不在每轮结束后立即销毁

因为 Agent 交互天然是多轮的，立即销毁会导致下一轮冷启动、重装上下文和额外等待。warm pool 让系统把“隔离性”和“交互连续性”做了折中。

### 16.3 为什么要保留虚拟路径而不是直接暴露真实路径

因为 Agent 的认知模型需要稳定。若不同部署模式暴露不同路径语义，工具调用和提示词就会变得脆弱，而且会让路径安全校验分散在多个入口中。统一虚拟路径能把复杂性集中收敛到路径映射层。

### 16.4 为什么副本上限是软限制

因为停止正在服务的活跃沙盒会直接破坏当前请求。对于交互式 Agent 来说，任务正确性通常比资源上限更优先，因此系统只驱逐 warm pool 中的可替换实例。

## 17. 结论

lumen 的沙盒模块本质上不是单一组件，而是一套围绕线程执行环境建立的统一机制。它通过抽象接口屏蔽执行介质差异，通过虚拟路径统一 Agent 视角，通过线程目录模型组织输入与输出，通过中间件与工具懒加载降低开销，通过确定性标识与锁机制解决跨进程复用问题，并通过 warm pool 与空闲回收在性能和资源占用之间做平衡。

如果把整个项目看作一个可执行 Agent 平台，那么沙盒模块承担的是“把会话上下文变成可操作工作空间”的角色。Agent 之所以不仅能回答问题，还能真正读写文件、执行命令、处理上传内容并产生产物，核心支撑正来自这里。

从实现质量上看，这个模块最有价值的地方不在于单个接口有多复杂，而在于它把路径语义、会话隔离、资源复用、并发控制和部署形态统一进了一套相对一致的运行模型中。这也是整个 lumen 能从普通 LLM 对话系统演化成“Super Agent Harness”的关键基础之一。
