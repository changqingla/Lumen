# Lumen 项目 RagTokenizer 分词算法技术文档

更新时间：2026-04-01

## 1. 文档目标

本文档基于当前仓库实现，单独说明 `services/rag/core/nlp/rag_tokenizer.py` 里的主分词算法，重点回答四个问题：

1. 中文主分词到底使用了什么算法。
2. “前向最大匹配 + 后向最大匹配 + DFS 消歧 + 评分选最优切法”在代码里是怎么串起来的。
3. 词典树、词频和剪枝规则分别起什么作用。
4. 这套算法和英文分词、细粒度分词之间的边界分别是什么。

本文档重点讨论中文主分词流程；英文分词和细粒度分词会说明它们在整条链路里的位置，但不会展开到同样深度。

## 2. 一句话总结

当前项目的主分词器不是 `jieba`，也不是 Elasticsearch/IK，而是项目自己的 `RagTokenizer`：

“先把文本做标准化，再按中英文切片；中文片段先分别做前向最大匹配和后向最大匹配，若两者切分边界不一致，则对歧义片段用 DFS 枚举候选切法，再用词频分值、长词比例和分词数量综合评分，选择得分最高的结果，最后再做一次特殊串合并。”

## 3. 相关代码入口

这套算法的核心代码都在一个文件里：

1. `services/rag/core/nlp/rag_tokenizer.py`

其中最关键的函数分别是：

1. `RagTokenizer.__init__()`：加载词典树、初始化英文处理器。
2. `RagTokenizer.maxForward_()`：前向最大匹配。
3. `RagTokenizer.maxBackward_()`：后向最大匹配。
4. `RagTokenizer.dfs_()`：枚举歧义片段的候选切法。
5. `RagTokenizer.score_()`：给单个候选切法打分。
6. `RagTokenizer.sortTks_()`：按分数排序，取最优方案。
7. `RagTokenizer.tokenize()`：把整条主流程串起来。
8. `RagTokenizer.fine_grained_tokenize()`：第二阶段细粒度分词，不属于主分词算法本体。

## 4. 算法范围与边界

先把三个容易混淆的概念分开：

1. 中文主分词
   就是本文讨论的这套“前向最大匹配 + 后向最大匹配 + DFS 消歧 + 评分选最优切法”。
2. 英文分词
   不走这套中文词典算法，而是走 NLTK 的 `word_tokenize()`，再接词形还原和词干提取。
3. 细粒度分词
   不是重新从原始文本开始分词，而是对主分词结果再拆一层，用于补召回。

因此，这里说的“主算法”默认指中文粗粒度分词，不包括：

1. 英文 `word_tokenize()`
2. `fine_grained_tokenize()`
3. Elasticsearch 的 analyzer

## 5. 数据结构与词典基础

### 5.1 词典树是整个算法的底座

`RagTokenizer` 使用 `datrie.Trie` 存储词典，而不是每次分词时线性扫描词表。

这意味着它在做“某个片段是否是词”“某个片段是否是某个词的前缀”这类判断时会非常快，这正是最大匹配和 DFS 剪枝能工作的前提。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:37`
2. `services/rag/core/nlp/rag_tokenizer.py:172`

### 5.2 词典里存的不是原始频次，而是压缩后的频率分值

词典文件每行大致是：

`词汇 频率 词性`

加载时，代码会把频率转换成一个对数化后的整数分值，再存进 Trie：

`F = int(log(freq / DENOMINATOR) + 0.5)`

所以后面评分函数里累加的 `freq`，更准确地说是“词典里的频率分值”，不是原始语料频次本身。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:96-138`
2. `services/rag/core/nlp/rag_tokenizer.py:124-129`

### 5.3 前向查找和后向查找使用两套键

为了同时支持前向最大匹配和后向最大匹配，代码会为每个词生成两种键：

1. `key_(line)`
   正向键，用于普通查找。
2. `rkey_(line)`
   反向键，用于从右往左匹配时的前缀判断。

这也是后向最大匹配能高效跑起来的关键原因之一。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:57-85`

## 6. 主流程总览

主入口是 `tokenize()`。如果把它抽象成流程图，大致是：

1. 预处理文本
2. 按语言把文本拆成中文片段和英文片段
3. 英文片段走英文分词
4. 中文片段先做前向最大匹配
5. 中文片段再做后向最大匹配
6. 如果两边结果一致，直接采用
7. 如果两边结果不一致，对歧义片段用 DFS 枚举候选切法
8. 对候选切法打分，选最优
9. 拼回整段结果
10. 再做一次特殊串合并

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:666-773`

## 7. 预处理与语言切片

### 7.1 预处理做了什么

在真正分词前，`tokenize()` 会先做三件事：

1. 把非字母数字字符替换为空格。
2. 做全角转半角，并统一成小写。
3. 做繁体转简体。

这一步的目标不是直接完成分词，而是把输入标准化，减少后面词典匹配时的噪声。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:686-691`

### 7.2 为什么要先按语言切片

项目不是拿整段中英混合文本直接套一套统一规则，而是先用 `_split_by_lang()` 把文本拆成：

1. 中文片段
2. 非中文片段

然后分别处理。

比如类似：

`我在学习Python编程和machine learning算法`

会先被拆成多段，再分别进入中文和英文处理分支。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:628-664`
2. `services/rag/core/nlp/rag_tokenizer.py:693-700`

## 8. 中文主算法第一步：前向最大匹配

### 8.1 基本思路

前向最大匹配，也就是 `maxForward_()`，是从左到右扫描文本，每次尽量取当前位置能命中的最长词。

例如对一段中文串，从位置 `s` 开始：

1. 先尝试 1 个字符。
2. 如果这个片段还是某个词的前缀，就继续往右扩展。
3. 一直扩到不能再扩。
4. 再回退到“最后一个真实在词典中存在的词”。
5. 把这个词作为当前位置的切分结果。
6. 指针跳到下一个未处理位置，继续重复。

这是一个典型的贪心策略，偏向长词优先。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:524-566`

### 8.2 它为什么叫“最大匹配”

因为它不是“看到词就停”，而是：

1. 先用 `has_keys_with_prefix()` 判断当前串是不是某个词的前缀。
2. 只要还是前缀，就继续扩。
3. 最后再回退到词典中真实存在的最长词。

所以它追求的是“当前位置尽可能长的合法词”。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:547-556`

## 9. 中文主算法第二步：后向最大匹配

### 9.1 基本思路

后向最大匹配，也就是 `maxBackward_()`，和前向最大匹配正好相反：

1. 从右往左扫描文本。
2. 每次尽量匹配当前位置往左延伸的最长词。
3. 使用反向键和反向前缀判断加速。
4. 最后把结果反转回来，恢复原本的阅读顺序。

它的意义在于：

1. 有些歧义从左往右看更像一种切法。
2. 但从右往左看更像另一种切法。
3. 只跑单向最大匹配，容易把一部分歧义固定死。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:568-611`

### 9.2 为什么要同时跑前向和后向

因为中文分词里经常会出现“前向优先长词”和“后向优先长词”给出不同边界的情况。

也就是说：

1. 前向最大匹配适合快速给出一个强基线。
2. 后向最大匹配能从相反方向暴露潜在歧义。
3. 两者不一致的片段，才是后面 DFS 消歧真正需要关注的部分。

这也是当前实现的工程取舍：

“大部分没有歧义的片段，靠双向最大匹配就能很快处理掉；只有边界不一致的小片段，才进入更贵的 DFS 枚举与评分阶段。”

## 10. 双向结果如何定位歧义片段

`tokenize()` 并不是“前向跑完、后向跑完，然后二选一”。它的真实做法更细：

1. 先找出前向和后向结果的相同前缀。
2. 这些一致部分直接加入最终结果。
3. 对后面不一致的部分，逐步扩展左右边界。
4. 当两边覆盖到同一段原始字符串时，把这段公共原文视为“歧义片段”。
5. 再对这段歧义片段调用 `dfs_()` 穷举可能切法。

所以 DFS 不是对整句跑，而是只对“前后向切分边界不同的局部片段”跑。

这点非常重要，因为它解释了为什么这套算法既能处理歧义，又不会像全句穷举那样代价过高。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:718-769`

## 11. DFS 消歧到底做了什么

### 11.1 目标不是只找一条路，而是枚举候选切法

`dfs_()` 的输入是一段歧义片段，比如一小段连续中文串。它会：

1. 从当前位置出发，尝试不同长度的候选词。
2. 只要候选词在词典中存在，就继续递归搜索后面的剩余部分。
3. 把所有走到字符串末尾的切分路径都保存下来。

最后得到的不是单个结果，而是一组候选切法。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:319-386`

### 11.2 它为什么不会无脑爆炸

DFS 里有几层重要剪枝。

第一层剪枝是前缀剪枝：

1. 如果当前串已经不是任何词的前缀，就立即停止继续往后扩。
2. 这使得很多无意义候选在很早阶段就被截断。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:356-363`

第二层剪枝是起始位置预测：

1. 代码会根据当前位置的一字串、二字串是否仍可能组成合法前缀，调整枚举起点 `S`。
2. 本质上是在跳过一部分明显不优的“过早单字切分”候选。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:341-349`

第三层剪枝是连续单字约束：

1. 如果前面已经连续出现多个单字 token，且当前字符和前一个单字还能组成更长前缀，
2. 就优先避免继续走单字切分。

这条规则的目标很直接：

“减少连续单字切分，把搜索重心拉回更像正常词的候选方案。”

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:349-355`

### 11.3 找不到合法路径时怎么办

如果当前位置扩不出更好的合法路径，`dfs_()` 不会直接失败，而是会退化成：

1. 把当前单字符当作一个 token
2. 若不在词典中，则给它一个很低的默认分值
3. 再继续递归搜索后面部分

所以这套算法是“尽量词典命中，但允许回退到单字兜底”的。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:374-386`

## 12. 评分函数如何选出“最优切法”

### 12.1 评分公式

候选切法枚举出来之后，不是靠“第一个找到的方案”决定胜负，而是要进入 `score_()` 打分。

代码里的核心公式可以概括为：

`score = F + L + 30 / N`

其中：

1. `F`
   当前切法里所有 token 的词典频率分值之和。这里的分值是词典加载时保存的对数化频率分值，不是原始频次。
2. `L`
   长词比例，也就是长度大于等于 2 的 token 数量除以总 token 数。
3. `N`
   当前切法的 token 数量。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:441-469`

### 12.2 这三个分量分别在鼓励什么

这套评分其实体现了很明确的偏好：

1. `F` 大
   说明这套切法更多使用词典里更常见、更可信的词。
2. `L` 大
   说明切法里长词更多，通常比大量单字更稳定。
3. `30 / N` 大
   说明 token 数更少，算法不鼓励把一句话切得过碎。

如果用一句话概括这套评分偏好，就是：

“高频词优先、长词优先、少切优先。”

### 12.3 最终如何决出胜者

`sortTks_()` 会对所有候选切法：

1. 逐个调用 `score_()` 计算分数
2. 按分数从高到低排序
3. 取第 1 名作为最优切法

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:471-489`

## 13. 一个完整例子

为了便于说明，下面用一个“假设性的歧义片段”来展示流程。这里不要求它严格等于当前词典里的真实频率，只用来说明算法行为。

假设某段原文在某个局部片段上可能有这些切法：

1. 切法 A：`["北京大学"]`
2. 切法 B：`["北京", "大学"]`
3. 切法 C：`["北", "京", "大学"]`

算法的处理思路是：

1. 前向最大匹配可能先偏向长词，得到 A。
2. 后向最大匹配也可能得到 A，或者得到 B。
3. 如果前后向边界不同，就把这一段原始字符送进 DFS。
4. DFS 会把 A、B、C 这类合法路径都枚举出来。
5. 评分阶段通常会因为：
   长词更多
   token 更少
   词典频率分值更高
   而让 A 或 B 胜出。
6. C 这种连续单字较多的方案，通常会因为长词比例低、token 数多而吃亏。

这个例子体现的核心不是某个词一定怎么切，而是：

“双向最大匹配负责暴露歧义，DFS 负责枚举候选，评分函数负责在候选中选出最像正常中文词序列的那条路径。”

## 14. 最后一步：特殊串合并

主分词流程结束后，代码还会再走一次 `merge_()`。

它的作用不是重新分词，而是尝试把一部分被拆开的特殊串重新并回去。代码会：

1. 顺序扫描已经分好的 token
2. 尝试把最多连续 5 个 token 拼起来
3. 如果拼接后的串符合特定条件，且词典中存在，就把它们重新合并

这一步更像“后处理修复”，避免某些特殊表达被拆坏。

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:491-520`
2. `services/rag/core/nlp/rag_tokenizer.py:771-773`

## 15. 英文分词在这套算法里的位置

虽然本文重点是中文主分词，但为了完整性，还是要说明英文怎么处理：

1. 英文片段不走中文词典树。
2. 英文片段直接走 `word_tokenize()`。
3. 然后做 `WordNetLemmatizer` 词形还原。
4. 再做 `PorterStemmer` 词干提取。

所以：

1. 中文主算法是“词典 + 双向最大匹配 + DFS + 评分”
2. 英文主算法是“NLTK 分词 + 词形归一 + 词干化”

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:44-45`
2. `services/rag/core/nlp/rag_tokenizer.py:154-156`
3. `services/rag/core/nlp/rag_tokenizer.py:697-700`

## 16. 细粒度分词与主算法的关系

`fine_grained_tokenize()` 也会复用 `dfs_()`，但它不等于主分词算法本身。

两者区别是：

1. 主分词 `tokenize()` 处理原始文本。
2. 细粒度分词 `fine_grained_tokenize()` 处理的是已经分过词的 token 串。
3. 主分词目标是得到主语义稳定的切法。
4. 细粒度分词目标是再拆一层，用于补召回。

因此，如果有人说“这个项目用 DFS 做分词”，更精确的说法应该是：

“主分词流程先用双向最大匹配快速缩小歧义范围，再只对歧义片段使用 DFS；细粒度分词阶段也会复用 DFS，但用途是二次拆分，不是第一次主分词。”

对应实现：

1. `services/rag/core/nlp/rag_tokenizer.py:666-773`
2. `services/rag/core/nlp/rag_tokenizer.py:806-860`

## 17. 一句话结论

如果只用一句话概括这套中文主分词算法，可以写成：

“它是一套以词典树为底座、以双向最大匹配做主路径、以 DFS 枚举歧义候选、再用频率分值、长词比例和少切偏好来选最优切法的自定义中文分词器。”
