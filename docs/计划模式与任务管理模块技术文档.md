# lumen 计划模式与任务管理模块技术说明

## 1. 文档目标

本文详细介绍 lumen 中的 plan 模式，也就是任务管理模块。重点不是说明“怎么让模型列待办”，而是解释这个项目如何把计划能力接进主 Agent 运行时，以及为什么它能在长任务、上下文压缩和多轮会话中保持稳定。

阅读本文后，读者应能够回答以下问题：

- plan 模式在这个项目里到底是什么，不是什么
- 它是如何被启用的
- `write_todos` 工具为什么不在普通工具注册表中
- `todos` 状态是如何维护和更新的
- 为什么上下文被摘要截断后，模型仍然能继续追踪任务
- 这个模块和普通模式、摘要模式、子 Agent 模块之间是如何协同的

## 2. 核心结论

先给出结论。

lumen 的 plan 模式，不是一个独立的 planner-executor 图，也不是一个手写任务调度器。它更准确地说是：

- 由运行时开关启用的一种 Agent 工作模式
- 底层依赖 LangChain 的 `TodoListMiddleware`
- 项目在此基础上追加了一层上下文补偿逻辑
- 最终通过动态注入 `write_todos` 工具和 `todos` 状态，让模型在复杂任务中维持显式任务列表

如果把这套机制压缩成一句话，可以这样概括：

lumen 的计划模式，本质上是“主 Agent loop 上的一层任务状态管理中间件”，它通过待办列表工具和状态提醒，把复杂任务从隐式推理转成显式可跟踪的执行过程。

## 3. 模块定位

在这个项目里，plan 模式的职责不是替代主 Agent，而是增强主 Agent 在复杂任务中的可控性。它解决的是两个常见问题：

- 模型在多步骤任务中容易遗忘自己当前做到哪一步
- 用户很难看到任务进展，尤其是在长执行链或多工具协作场景下

因此，这个模块主要承担三件事：

- 让模型可以显式维护一份待办列表
- 把这份列表持久写入线程状态
- 在上下文窗口变化时，尽量保证这份列表不会从模型“视野”里消失

从角色上看，它不是一个新的 Agent，而是一层运行时能力。只有在 `is_plan_mode=True` 时，这层能力才会被接入主链路。

## 4. 代码分层与关键入口

与 plan 模式最相关的实现主要集中在以下位置：

- `runtimes/backend/src/agents/lead_agent/agent.py`
  负责读取运行时开关、创建 Todo 中间件，并将其插入主中间件链。

- `runtimes/backend/src/agents/middlewares/todo_middleware.py`
  这是项目自己的扩展层，负责在上下文被截断时补注入待办提醒。

- `runtimes/backend/src/agents/thread_state.py`
  定义 `todos` 状态字段，使任务列表成为线程状态的一部分。

- `runtimes/backend/src/client.py`
  负责把 `plan_mode` 映射到 `RunnableConfig.configurable.is_plan_mode`，并在配置变化时重建 Agent。

- `runtimes/backend/src/channels/manager.py`
  为通道调用提供默认运行上下文，默认关闭 `is_plan_mode`。

除此之外，还有一个很关键但不在本仓库源码里的基础依赖：

- LangChain 的 `TodoListMiddleware`
  它提供 `write_todos` 工具的动态注入和基础状态写入能力。lumen 不是从零实现待办工具，而是在它之上做定制。

## 5. plan 模式是什么，不是什么

### 5.1 它不是独立的图调度器

很多项目里的“规划模式”意味着一张新的执行图，例如 planner 节点先产出计划，再交给 executor 节点逐项执行。lumen 不是这种结构。

在这里，主智能体仍然是同一个 `create_agent()` 驱动的 lead agent。plan 模式并不会替换它，也不会引入新的主图节点，而只是决定：

- 是否向主 Agent 注入任务管理中间件
- 是否向模型暴露 `write_todos` 工具
- 是否把 `todos` 作为当前线程状态的一部分长期维护

所以它本质上是一种“工作模式切换”，而不是“智能体架构切换”。

### 5.2 它也不是强制规划

虽然模块名叫 plan 模式，但它并不意味着模型每次都必须写待办列表。项目给模型的约束是有条件的：

- 复杂多步骤任务时应使用
- 用户明确要求追踪任务时应使用
- 简单任务不应滥用

这说明它追求的不是“无论什么请求都先列计划”，而是“在复杂任务里显式化工作过程”。

## 6. 启用开关是如何进入运行时的

### 6.1 真正的控制位是 `is_plan_mode`

plan 模式的开关并不在全局配置文件里固定写死，而是通过运行时 `RunnableConfig.configurable.is_plan_mode` 传入。

这意味着它是一个“每次运行可选”的能力，而不是一个部署级常量。不同请求可以使用同一套 Agent 代码，但一个开启任务管理，一个不开启。

### 6.2 客户端是如何传入的

嵌入式客户端 `InsightFlowClient` 在构造运行配置时，会把 `plan_mode` 参数映射成 `is_plan_mode`。这说明 plan 模式是调用方主动请求的行为，而不是系统自动根据任务复杂度强行切换的模式。

同时，客户端在判断是否需要重建 Agent 时，也把 `is_plan_mode` 放进了缓存 key。这意味着：

- 普通模式与计划模式会对应不同的 Agent 运行实例
- 模式切换后会触发 Agent 重建，确保中间件链和工具集合与当前模式一致

这是一个很重要的实现细节，因为中间件注入发生在 Agent 构建阶段，而不是请求执行中途。

### 6.3 通道默认关闭

在通道管理器里，默认运行上下文把 `is_plan_mode` 设为 `False`。这说明系统的默认行为仍然是普通模式，plan 模式是显式增强而不是默认常态。

这个取舍很合理，因为对 IM、群聊或轻量交互场景来说，默认开启任务管理往往会引入额外 token 和冗余行为。

## 7. 计划模式是如何接进主 Agent 的

### 7.1 中间件装配点

主入口 `make_lead_agent()` 会从运行时配置里读取 `is_plan_mode`，然后把这个值传给 `_build_middlewares()`。后者再决定是否创建 Todo 中间件。

这说明 plan 模式的启用时机发生在 Agent 组装阶段，而不是模型首次思考时动态决定。

### 7.2 创建逻辑是条件性的

`_create_todo_list_middleware()` 的逻辑非常直接：

- 若 `is_plan_mode` 为假，返回 `None`
- 若为真，则构造一个 `TodoMiddleware` 实例

这里体现出一个很清晰的工程思想：禁用时不只是“不建议模型使用待办”，而是完全不把这层能力接入主链路。

也就是说，当 plan 模式关闭时：

- `write_todos` 工具不会存在
- 相关系统提示词不会注入
- `before_model` 补偿逻辑也不会运行

这种做法比仅靠 prompt 约束更彻底，也更节省上下文。

## 8. `write_todos` 工具为什么不在项目自己的工具系统里

这是这个模块最容易让人误判的地方。

项目里普通工具是通过 `get_available_tools()` 装配的，来源包括：

- `config.yaml` 中声明的工具
- builtins 工具
- MCP 工具
- 条件启用的视觉工具和子 Agent 工具

但 `write_todos` 不在这里面。它是由 LangChain 的 `TodoListMiddleware` 在中间件初始化时动态创建出来的。

这意味着 plan 模式的任务管理能力，并不是项目工具系统中的一个静态注册项，而是中间件自带的一项附加能力。

这个设计很重要，因为它说明：

- 任务管理是中间件级能力，而不是普通业务工具
- 它天然和状态模式绑定
- 它只有在计划模式启用时才会存在

换句话说，`write_todos` 更像“中间件向 Agent 注入的控制工具”，而不是“全局工具仓库里的一个固定成员”。

## 9. 底层 `TodoListMiddleware` 实际做了什么

从底层框架实现看，`TodoListMiddleware` 做了两件核心事情。

第一，它把自定义的 todo 系统提示词拼接到当前模型请求的 system prompt 上。

第二，它动态创建了一个 `write_todos` 工具。这个工具接收一个 todo 列表，并返回一个状态更新命令，把：

- `todos` 写进状态
- 一条对应的 `ToolMessage` 追加进消息历史

因此，待办列表不是模型“口头写出来的一段文本”，而是通过标准 tool call 协议提交进线程状态的结构化数据。

## 10. 项目为什么要自定义 `TodoMiddleware`

如果只有基础版 `TodoListMiddleware`，任务管理在短上下文里就够用了。但 lumen 还叠加了摘要中间件、长会话和复杂多工具任务，这会带来一个现实问题：

原始的 `write_todos` 调用和它对应的 ToolMessage，可能随着消息截断或摘要而滑出当前上下文窗口。

一旦发生这种情况，模型虽然在状态层面还有 `todos`，但消息层面已经看不到当初那份待办列表，于是就可能：

- 忘记继续更新任务状态
- 误以为当前没有待办列表
- 在多轮复杂任务中丢失执行进度感

项目自定义 `TodoMiddleware` 就是为了解决这个问题。

## 11. `TodoMiddleware` 的核心算法

### 11.1 它不是替代基础逻辑，而是补偿逻辑

项目自己的 `TodoMiddleware` 继承自 LangChain 的 `TodoListMiddleware`。这意味着它复用了：

- `write_todos` 工具注入
- 基础 todo system prompt 注入
- `PlanningState` 状态模型

它额外做的事情主要发生在 `before_model` 和 `abefore_model` 阶段，也就是模型再次调用之前。

### 11.2 检测条件

它在每次模型调用前会检查三件事：

第一，当前状态里是否仍然存在 `todos`。

第二，当前消息窗口里是否还能看到某条 AIMessage 含有 `write_todos` 调用。

第三，消息窗口里是否已经注入过名为 `todo_reminder` 的提醒消息。

只有满足以下组合条件时，它才会介入：

- 状态里仍有待办项
- 当前消息窗口已经看不到原始 `write_todos`
- 当前也还没有提醒消息

这个判断逻辑说明它不是每轮都塞提醒，而是专门补“状态还在、消息已丢”的缝隙。

### 11.3 提醒消息的注入方式

当检测到待办列表已脱离可见消息窗口时，它会把当前 `todos` 格式化成一个可读列表，然后注入一条新的 `HumanMessage`。

这条消息有两个很关键的特征：

- `name` 被标记为 `todo_reminder`
- `content` 被包在一个 system reminder 风格的文本里

内容大意是：

- 你之前的 todo 列表已经不在当前窗口中
- 但它仍然是活跃状态
- 这里是当前待办列表的最新状态
- 继续工作时要保持追踪，并在状态变化时调用 `write_todos`

这说明它采用的不是“重新恢复原始工具调用”，而是“向模型注入一条新的系统型提醒”。这是一个很有效的补偿方式，因为它不需要伪造旧消息，只需要确保模型重新获得状态感知。

## 12. 为什么这套补偿机制很重要

### 12.1 状态和消息不是一回事

lumen 的线程状态和模型实际可见的消息窗口并不是一一对应的。尤其在摘要中间件生效后，旧消息可能被压缩、移除或替换，但结构化状态还在。

`todos` 恰好属于这种情况：

- 它是线程状态字段
- 但模型理解它，通常还是要依赖消息上下文

自定义 `TodoMiddleware` 的核心价值，就是在“状态还在但消息已丢”时补一层桥。

### 12.2 它和摘要模块天然耦合

从代码注释就能看出来，项目作者明确把这个问题和 `SummarizationMiddleware` 联系在一起。也就是说，这个模块不是凭空设计的，而是对“长会话 + 自动摘要”组合场景下的现实问题做出的针对性修复。

这类实现非常体现工程经验，因为它不是停留在功能层，而是针对长期运行中的协议漂移做补偿。

## 13. `todos` 状态本身的设计含义

### 13.1 `todos` 是线程状态的一部分

`ThreadState` 里专门留了一个 `todos` 字段。这意味着待办列表不是中间件私有内存，而是和：

- `artifacts`
- `title`
- `uploaded_files`
- `viewed_images`

一样，都是当前线程的正式状态组成部分。

只要底层 checkpointer 生效，这份状态就可以随着线程跨请求持久存在。

### 13.2 它没有 reducer，反映了“整体替换”语义

和 `artifacts`、`viewed_images` 不同，`todos` 没有自定义 reducer。也就是说，每次 `write_todos` 调用本质上是用一份新的 todo 列表整体替换旧状态，而不是做增量合并。

这个选择其实很合理，因为任务列表强调的是“当前完整真相”，不是多个来源的并行累积。

如果对 todo 列表做自动合并，反而容易出现：

- 已删除任务残留
- 旧状态与新状态冲突
- 无法清晰表达当前唯一有效的任务序列

所以这个字段的设计更像“快照式状态”，而不是“append-only 状态”。

## 14. 项目对模型使用待办工具施加了哪些约束

lumen 并没有直接使用框架默认 prompt，而是给 `TodoListMiddleware` 注入了自定义 system prompt 和 tool description。

这些约束大致可以分成几类。

### 14.1 使用时机约束

模型被明确告知：

- 复杂多步骤任务适合使用
- 非平凡、需要计划的工作适合使用
- 用户明确要求待办追踪时适合使用
- 简单任务不应使用

这相当于为 `write_todos` 设定了“什么时候值得付出额外 token 成本”的门槛。

### 14.2 状态一致性约束

项目特别强调：

- 完成一个任务后要立刻标记完成，不能批量晚更新
- 正常情况下应只保持一个任务处于 `in_progress`
- 要实时更新任务列表，而不是最后一次性回填

这些约束都不是语法要求，而是为了让任务列表真正成为执行过程的在线状态，而不是事后总结。

### 14.3 质量控制约束

系统还强调：

- 未完全完成的任务不能标记成 completed
- 发现新的必要步骤时应增补任务
- 不再相关的任务应删除
- 被阻塞时要显式保留或新增阻塞项，而不是假装完成

这实际上是在把计划模式从“列一个 checklist”提升为“维护一份随执行演进的工作面板”。

## 15. plan 模式和普通模式的差异

如果从运行时角度比较，普通模式和计划模式的差异主要体现在以下几方面。

普通模式下：

- 没有 `write_todos` 工具
- 没有 todo system prompt
- 没有 `before_model` 的待办提醒补偿逻辑
- `todos` 状态字段通常不会被用到

计划模式下：

- 中间件链会插入 `TodoMiddleware`
- 模型得到额外的任务管理行为约束
- 线程状态中会主动维护 `todos`
- 当上下文截断时，系统会额外补注入提醒消息

这说明 plan 模式不是“多一个字段”，而是整套行为语义都变了。

## 16. plan 模式和摘要模块的关系

这两个模块之间的关系非常紧密。

### 16.1 摘要带来问题

摘要中间件的目标是压缩上下文，但它可能让原始 `write_todos` 调用离开当前窗口。这样模型失去对任务列表的直接感知。

### 16.2 TodoMiddleware 提供补偿

TodoMiddleware 的提醒注入，正是对这一问题的专门修复。它不和摘要竞争，而是在摘要之后补上“当前待办仍然活跃”的信息。

### 16.3 中间件顺序体现了这种协作

在 `_build_middlewares()` 中，摘要中间件在前，Todo 中间件在后。这是合理的，因为只有先经历可能的压缩，TodoMiddleware 才能判断“原始待办消息是否已经离开窗口”。

这说明中间件顺序本身就是 plan 模式正确性的组成部分。

## 17. plan 模式和子 Agent 的关系

plan 模式主要作用于主 Agent。子 Agent 是否拥有这套能力，取决于子 Agent 自己是否按相同方式构建中间件链。

从当前项目代码来看，主 Agent 的计划模式是通过 `_build_middlewares()` 明确接入的，而子 Agent 工具 `task` 主要是把任务隔离到独立上下文中执行。也就是说，主 Agent 的 todo 列表更偏向“总控层进度板”，而不是对子 Agent 内部每一步都做统一任务追踪。

这其实很合理，因为：

- 主 Agent 负责对用户可见的总体进度
- 子 Agent 更适合在隔离上下文中自主完成局部任务

换句话说，plan 模式更像 orchestration 层能力，而不是所有执行层都必须继承的能力。

## 18. plan 模式的几个关键 tricks

如果把这个模块里最值得借鉴的工程技巧提炼出来，主要有以下几点。

### 18.1 用中间件动态注入工具，而不是加入全局工具仓库

这样可以保证计划能力只有在需要时才存在，减少普通模式下的噪音和 token 开销。

### 18.2 用线程状态存 todo，而不是把计划只保留在消息文本里

这让待办列表具备了跨轮存在的能力，也更容易和其他状态统一管理。

### 18.3 用整体替换而不是增量合并

任务列表每次提交都代表最新真相，避免了增量合并带来的状态污染。

### 18.4 用提醒消息修复“状态存在但消息不可见”的断层

这正是项目在基础 `TodoListMiddleware` 之上最有价值的增强。

### 18.5 用 prompt 约束控制 `write_todos` 的使用频率

不是所有任务都应该列计划。通过明确“何时用、何时不用”，可以减少无意义待办列表。

### 18.6 把 `is_plan_mode` 纳入 Agent 重建 key

这样模式切换不会混用旧中间件链，保证运行时能力集合和当前配置严格一致。

## 19. 当前实现的能力边界

从现有代码看，计划模式也有一些明确边界。

- 它不做真正的自动任务调度，只做任务状态管理
- 它依赖模型遵循 prompt 约束，不是后端强制推进任务
- `todos` 状态是完整列表快照，不支持多方并发合并
- 它主要服务主 Agent 的复杂任务跟踪，不等于整个系统具备统一项目管理能力

这些边界不是缺陷，而是明确的架构取舍。它说明这个模块的目标是提高复杂任务的过程可见性和一致性，而不是演化成一个独立的工作流引擎。

## 20. 这个模块的本质是什么

如果只看表面，lumen 的 plan 模式像是“多了一个 `write_todos` 工具”。但从实现上看，它真正做的是把任务追踪变成主 Agent 运行时的一部分。

它完成了以下几件关键事情：

- 通过运行时开关决定是否接入计划能力
- 通过中间件动态暴露 `write_todos` 工具
- 把待办列表写入线程状态而不是只保留在自然语言里
- 用自定义 prompt 约束模型何时、如何维护任务列表
- 在上下文压缩后补注入提醒，防止任务感知丢失

所以，这个模块不是一个单纯的“待办功能”，而是一套围绕复杂任务执行建立的显式进度管理层。它让主 Agent 在面对长任务时，不再只依赖隐式推理记忆，而是拥有了一份可持续维护、可跨轮恢复、可对用户可见的任务状态。
