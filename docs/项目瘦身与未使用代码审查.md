# 项目瘦身与未使用代码审查

审查日期：2026-05-07

## 当前状态

当前工作区体量约 `404M`，已经不是最初那种数 GB 级别的状态。主要剩余体量来自 `node_modules`、`.git`、`services/rag`、`frontend/src`、`backend` 和 `runtimes/skills`。

本轮继续重点审查 `docker/docker-compose.yml`。结论是：完整产品同时启动多个服务有架构原因，但现在所有能力都被一个默认 Compose 串起来，确实偏重，尤其不适合本地开发和只调部分功能。

## Docker Compose 复审

当前 Compose 服务可以分为四层：

| 层级 | 服务 | 用途 | 判断 |
| --- | --- | --- | --- |
| 基础数据层 | `lumen_postgres`、`redis`、`lumen_minio` | 用户、会话、对象存储、队列、上传文件 | 核心必需 |
| 知识库/RAG 层 | `elasticsearch`、`rag` | 文档分块、向量化、ES 入库、知识库检索 | 知识库能力必需，纯 API 开发可选 |
| Agent Runtime 层 | `lumen_gateway`、`lumen_langgraph` | Agent loop、工具调用、产物、LangGraph 运行 | 当前聊天主流程必需，管理/笔记/登录可选 |
| 边缘层 | `lumen_nginx` | 静态前端、反向代理、TLS、MinIO 代理 | 生产必需，本地开发可选 |

## 是否正常

如果要一次性启动完整 Lumen 产品，这些服务数量是可以解释的：

| 功能 | 依赖 |
| --- | --- |
| 登录、用户、组织、笔记 | API + Postgres + Redis |
| 文件上传和预览 | API + MinIO |
| 文档入库和检索 | API + RAG + Elasticsearch + Redis |
| 当前聊天流式回答 | API + Gateway + LangGraph + Runtime state |
| Agent 工具和产物下载 | Gateway + LangGraph + MinIO + Runtime state |
| 生产 Web 入口 | Nginx + `frontend/dist` |

真正的问题不是“服务多”，而是缺少启动分层：

| 问题 | 影响 |
| --- | --- |
| 所有能力默认一起启动 | 新开发者成本高，排障面大 |
| API healthcheck 原来调用 `/api/ready` | API 容器健康状态被 Gateway/LangGraph 绑死 |
| `/api/ready` 只检查 Runtime | ready 语义不准，没有覆盖 DB/Redis/MinIO/RAG |
| Nginx 同时依赖 API/Gateway/LangGraph/MinIO | 生产合理，本地开发显得笨重 |
| Runtime 首启 `start_period: 600s` | 暗示启动慢，可能在动态准备运行环境 |

已执行的小优化：

| 文件 | 调整 |
| --- | --- |
| `docker/docker-compose.yml` | `lumen_api` healthcheck 从 `/api/ready` 改为 `/api/health`，让 API 自身健康检查不再依赖 Runtime |

## 建议的启动分层

建议把 Compose 改成“默认轻量 + 按需 profile”的方式。

推荐 profile：

| Profile | 服务 |
| --- | --- |
| 默认 | `lumen_postgres`、`redis`、`lumen_minio`、`lumen_api_migrations`、`lumen_api` |
| `knowledge` | `elasticsearch`、`rag` |
| `runtime` | `lumen_gateway`、`lumen_langgraph` |
| `edge` | `lumen_nginx` |

目标命令形态：

```bash
# 后端基础能力：登录、用户、组织、笔记、部分知识库元数据
docker compose --env-file docker/.env -f docker/docker-compose.yml up -d

# 增加知识库文档处理
docker compose --env-file docker/.env -f docker/docker-compose.yml --profile knowledge up -d

# 增加完整 Agent 聊天
docker compose --env-file docker/.env -f docker/docker-compose.yml --profile knowledge --profile runtime up -d

# 生产入口
docker compose --env-file docker/.env -f docker/docker-compose.yml --profile knowledge --profile runtime --profile edge up -d
```

另一种选择是拆 Compose 文件：

| 文件 | 内容 |
| --- | --- |
| `docker-compose.yml` | 基础数据层 + API |
| `docker-compose.knowledge.yml` | Elasticsearch + RAG |
| `docker-compose.runtime.yml` | Gateway + LangGraph |
| `docker-compose.edge.yml` | Nginx |

profile 方式文件少；多文件方式对新手更直观。这个项目目前已经足够复杂，我更倾向多文件方式，读起来更像“积木”，少一点隐藏开关。

## 继续优化建议

| 优先级 | 建议 | 说明 |
| --- | --- | --- |
| 高 | 拆分 `/api/ready` | 建议提供 `/api/ready/core` 和 `/api/ready/full`，分别检查核心 API 与完整 Runtime |
| 高 | 本地开发默认不启动 Nginx | 前端开发用 Vite proxy，生产再启动 Nginx |
| 高 | Runtime 独立 profile 或 compose 文件 | 登录/笔记/后台开发不应被 LangGraph 首启拖慢 |
| 中 | RAG 独立 profile 或 compose 文件 | 文档处理才需要 ES/RAG，普通后台 API 不需要 |
| 中 | 给 README 增加“最小启动/完整启动”两套命令 | 降低首次部署心理负担 |
| 中 | 预构建 Runtime venv 到镜像 | 避免容器启动时动态准备 Python 环境 |
| 低 | 为 Nginx 拆 HTTP 本地模板和 HTTPS 生产模板 | 本地无需证书路径和双 server 块 |

## 代码层面的关键观察

| 位置 | 观察 |
| --- | --- |
| `backend/app/main.py` | `/api/ready` 当前只探测 Gateway 和 LangGraph，和“API 是否能提供核心服务”不是一回事 |
| `backend/modules/chat/runtime_controller.py` | 当前聊天发送前会 `prepareChatRuntime`，因此聊天主流程确实硬依赖 Runtime |
| `frontend/src/features/chat/hooks/useRAGChat.ts` | 前端聊天 hook 默认走 Runtime 流式链路，没有轻量 simple chat fallback |
| `backend/utils/external_services.py` | 文档处理通过 `DOC_PROCESS_BASE_URL` 调 RAG 服务，知识库上传链路依赖 RAG |
| `docker/nginx/lumen.conf.template` | 同时代理 Backend、Gateway、LangGraph、MinIO，生产合理，本地偏重 |

## 结论

这个 Compose 对“完整生产拓扑”来说不算离谱，但对开发和轻量体验来说确实太重。下一步最有价值的优化不是继续删代码，而是把启动模式拆开：核心 API、知识库处理、Agent Runtime、生产 Nginx 分层启动。
