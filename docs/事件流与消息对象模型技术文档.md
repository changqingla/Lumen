# lumen 事件流与消息对象模型技术说明

## 1. 文档目标

这份文档专门解释 lumen 里“消息是怎么表示的、状态是怎么累积的、事件是怎么流出去的”。

它不讨论前端展示，也不按接口文档方式枚举字段，而是回答下面几个更底层的问题：

- 用户的一句话，进入系统后会先变成什么对象。
- 模型输出、工具调用、工具结果为什么都能放进同一条会话历史。
- 流式输出为什么既有增量事件，也有完整状态快照。
- 为什么系统要专门修补“悬空 tool call”。
- 子 Agent、渠道接入、嵌入式客户端虽然入口不同，但为什么还能共用同一套消息语义。

如果把智能体系统看成一个运行中的进程，那么消息对象模型决定了“数据长什么样”，事件流模型决定了“这些数据如何沿链路传播”。

## 2. 模块定位

lumen 的事件流与消息模型并不是单独一个目录下的封闭模块，而是由几层实现共同构成：

- LangChain/LangGraph 提供基础消息类型，例如 HumanMessage、AIMessage、ToolMessage、SystemMessage。
- `backend/src/agents/thread_state.py` 定义线程状态结构，规定这些消息如何与 artifacts、viewed_images、sandbox 等状态并存。
- `backend/src/tools/*` 和 `backend/src/agents/middlewares/*` 决定消息何时新增、替换、补丁或衍生。
- `backend/src/client.py` 把 LangGraph 的状态流转成嵌入式客户端可消费的 StreamEvent。
- `backend/src/channels/*` 把 LangGraph Server 的最终结果转成 IM 渠道可以发送的出站消息。

所以这个模块的本质不是“一个类”，而是一套统一的消息语义协议。

## 3. 核心设计：一切围绕 `messages` 状态字段展开

这个项目并没有为“用户消息”“模型消息”“工具结果消息”分别维护三套历史存储，而是把它们统一收敛到线程状态里的 `messages` 列表。

这样做有几个直接结果：

- 模型在下一轮读取上下文时，不需要额外拼接多张表或多个日志源，只需要读取 `messages`。
- 中间件可以基于同一份会话历史做二次加工，比如修补 ToolMessage、注入图片说明、插入 todo 提醒。
- checkpointer 持久化时，也只需要把线程状态整体保存，而不是自己维护另一套消息仓储。

这也是为什么很多工具并不直接返回纯字符串，而是返回 `Command(update=...)`。它们的真正作用不只是“给模型看一眼结果”，而是“把结果正式写进线程状态”。

## 4. 代码入口与对象边界

与这个模块最直接相关的入口主要有：

- `backend/src/agents/thread_state.py`
- `backend/src/client.py`
- `backend/src/channels/message_bus.py`
- `backend/src/channels/manager.py`
- `backend/src/agents/middlewares/dangling_tool_call_middleware.py`
- `backend/src/agents/middlewares/view_image_middleware.py`
- `backend/src/tools/builtins/present_file_tool.py`
- `backend/src/tools/builtins/view_image_tool.py`
- `backend/src/tools/builtins/task_tool.py`

这些文件分别负责：

- 线程状态建模。
- 流式事件输出格式化。
- 通道层入站/出站消息建模。
- LangGraph Server 结果到渠道回复的转换。
- 对消息历史做协议级修补。
- 把工具副作用转为显式消息或显式状态。

## 5. 会话里真正存在的消息类型有哪些

当前项目实际依赖的核心消息类型主要是四种：

- HumanMessage：表示用户输入，也表示系统在运行时向模型补充的人类视角消息。
- AIMessage：表示模型输出，包括普通文本回复和带 tool_calls 的动作请求。
- ToolMessage：表示工具执行结果，或者被系统合成出的“伪工具结果”。
- SystemMessage：主要存在于提示词层，不是这套运行时消息链路中的主角。

其中最重要的不是“谁说的话”，而是“它在协议上承担什么职责”。

HumanMessage 不一定总来自真实用户。比如 ViewImageMiddleware 会主动插入一条 HumanMessage，把图片细节重新喂回模型。TodoMiddleware 也会插入提醒消息，让待办事项即使脱离上下文窗口也仍能重新被模型看到。

也就是说，在这个系统里，HumanMessage 的语义是“以用户可见或用户语境的方式进入模型上下文的输入块”，而不只是“UI 输入框发来的文本”。

## 6. `ThreadState` 为什么是消息系统的状态底座

`backend/src/agents/thread_state.py` 里的 `ThreadState` 不是简单加了几个字段，而是规定了整个运行期状态的主结构。

它在 `AgentState` 基础上扩展了这些关键字段：

- `sandbox`
- `thread_data`
- `title`
- `artifacts`
- `todos`
- `uploaded_files`
- `viewed_images`

其中 `messages` 本身继承自 AgentState，不需要重复声明，但它与这些字段共同组成了“会话状态”。

这意味着消息列表并不是孤立存在的。它会和文件产物、图片缓存、线程路径、沙箱句柄一起被同一张状态表驱动。很多中间件正是利用这一点，在不改消息协议的前提下，把外部世界的副作用投射回会话上下文。

## 7. reducer 设计为什么对消息外状态很关键

这个模块里一个很容易被忽视、但工程上很重要的点，是 `artifacts` 和 `viewed_images` 不是普通字段，而是带 reducer 的聚合字段。

`merge_artifacts` 的语义是“合并并保持顺序去重”。

这样做的价值在于：

- 多个工具可以并发或连续地往 `artifacts` 写文件，而不会互相覆盖。
- 同一个文件被重复 present 时，不会不断膨胀历史状态。

`merge_viewed_images` 的语义更特别：

- 正常情况下是增量合并。
- 当新值是空字典时，不是“什么都不做”，而是“清空旧图片状态”。

这说明状态更新在这里不是简单赋值，而是带有明确语义的状态变换协议。事件流最终能否稳定，很大程度上取决于 reducer 是否表达了这些业务语义。

## 8. 一轮对话是如何进入消息流的

对嵌入式客户端来说，入口在 `backend/src/client.py` 的 `stream()`。

这一层会把用户文本先包成一条 HumanMessage，作为初始状态里的 `messages`。

同时它还会构造两类运行信息：

- `config`：例如 `thread_id`、`thinking_enabled`、`subagent_enabled`、`is_plan_mode`
- `context`：至少包含 `thread_id`

其中很关键的一点是，`thread_id` 同时存在于 configurable 和 context 里，但承担的职责不同：

- configurable 更偏向运行参数。
- context 更偏向中间件和工具的运行时取数。

像 ThreadDataMiddleware、SandboxMiddleware、各种工具函数，实际读取的就是 runtime context 里的 `thread_id`。

## 9. AIMessage 在这里不只是“文本回复”

AIMessage 在这个项目里承担两种不同模式：

- 纯文本输出。
- 动作规划输出，也就是包含 `tool_calls` 的 AIMessage。

当模型决定调工具时，它并不是马上执行 Python 函数，而是先生成一条 AIMessage，在其中声明：

- 要调用哪个工具。
- 调用参数是什么。
- 每个 tool call 的唯一 id 是什么。

所以 AIMessage 更像是“模型层的动作提案对象”。真正的工具执行、结果写回、甚至中断流程，都发生在这之后。

## 10. `tool_call_id` 为什么是消息协议里的关键纽带

ToolMessage 不是随便追加一条“工具执行成功”文本就行，它必须和前面的某个 tool call 对齐。

这个对齐关系就是靠 `tool_call_id` 完成的。

在当前实现里，这个 ID 有几层作用：

- ToolMessage 要告诉系统“我是给哪次工具调用的回执”。
- 中间件要判断一个工具调用是否已完成，本质上也是看对应 `tool_call_id` 是否已有 ToolMessage。
- 若调用被打断，DanglingToolCallMiddleware 需要给缺失回执的 tool call 补一条占位 ToolMessage，同样依赖这个 ID。
- 某些工具把 `InjectedToolCallId` 注入到工具函数里，也是为了能回写正确的 ToolMessage。

所以消息协议真正依赖的不是“先后顺序猜测”，而是“显式关联键”。

## 11. 为什么很多工具返回 `Command(update=...)`

像 `present_files`、`view_image` 这类工具，返回值并不是给上层拿去随便 print 的，而是一个带状态更新语义的 Command。

这背后的思路是：

- 工具不应该只产生一段文本。
- 工具应该显式声明自己对线程状态造成了什么影响。

例如：

- `present_files` 会更新 `artifacts`，同时追加 ToolMessage。
- `view_image` 会更新 `viewed_images`，同时追加 ToolMessage。
- `ask_clarification` 最终会被中间件转成写入 ToolMessage 并 `goto=END` 的控制命令。

这让事件流不再只是“模型说一句，工具回一句”的聊天式交替，而变成“状态被一次次事务性更新”的运行模型。

## 12. `view_image` 为什么拆成工具更新状态 + 中间件注入消息两段式

`view_image_tool` 自己并不直接把图片作为多模态输入送给模型，它只做两件事：

- 校验图片路径、格式、存在性。
- 把 base64 和 MIME 写入 `viewed_images`，再追加一条 ToolMessage。

真正把图片塞回会话消息流的，是 `ViewImageMiddleware`。

这个中间件会在下一次模型调用前检查：

- 最近一条 AIMessage 是否包含 `view_image` 调用。
- 这些工具调用是否都已经有对应 ToolMessage。
- 最近是否已经注入过图片说明消息。

满足条件后，它会额外插入一条 HumanMessage，其中包含文本说明和 `image_url` 内容块。

这种两段式设计的好处是：

- 工具阶段只做 I/O 和状态落地，职责清晰。
- 模型输入阶段才做上下文拼装，时机准确。
- 可以避免在工具尚未全部完成时过早把不完整图片上下文喂给模型。

## 13. 为什么要有 `DanglingToolCallMiddleware`

真实运行中，一个非常棘手的问题是：AIMessage 已经写下了 tool_calls，但对应 ToolMessage 还没落盘，执行就被取消、中断或者异常退出了。

这时下一轮模型再读取历史，就会看到一个不完整的工具协议片段：

- 有调用请求。
- 没有调用结果。

很多模型或框架在这种消息历史上会报错，或者出现错误推断。

因此 `DanglingToolCallMiddleware` 会在模型调用前扫描全部消息：

- 收集历史里已经存在的 ToolMessage 的 `tool_call_id`。
- 找出所有没有回执的 tool call。
- 在对应 AIMessage 后面立即插入一条错误状态的占位 ToolMessage。

这里最关键的实现选择是它用 `wrap_model_call`，而不是 `before_model`。

原因很简单：补丁消息必须插在发起它的那条 AIMessage 后面，顺序语义才是对的。如果只是粗暴地把补丁追加到末尾，消息因果链就断了。

## 14. 流式输出为什么同时有增量事件和状态快照

`backend/src/client.py` 的 `stream()` 不是简单把 LangGraph 原始事件原封不动透传，而是做了一层适配。

它最终发出三类事件：

- `messages-tuple`：面向 UI 或调用方的增量消息事件。
- `values`：当前完整状态快照。
- `end`：本轮流结束。

这种双轨设计非常实用。

增量事件适合即时显示：

- 新出现的 AI 文本片段。
- 新出现的工具调用。
- 新出现的 ToolMessage。

状态快照适合做稳态同步：

- 当前标题是什么。
- 当前整轮消息历史长什么样。
- 当前 artifacts 列表有哪些。

也就是说，这个系统不是纯 event sourcing，也不是纯 snapshot 同步，而是两者结合：

- 事件负责低延迟感知。
- 快照负责最终一致。

## 15. 为什么客户端要自己做消息去重

在 `stream()` 里，客户端会维护一个 `seen_ids` 集合，只处理还没见过的消息 id。

这是因为 `stream_mode="values"` 返回的是状态快照序列，而不是只返回“本次新增 delta”。同一条消息在后续多个 chunk 里可能反复出现。

如果不做去重：

- 前端会重复渲染相同消息。
- 工具调用和工具结果会被错误地多次展示。

所以这里其实做的是“从快照流中反推出增量流”。

这也是为什么 `messages-tuple` 在客户端层是派生事件，而不是底层天然提供的原始对象。

## 16. `StreamEvent` 说明了什么设计倾向

`StreamEvent` 被设计成一个很薄的 dataclass，只保留：

- `type`
- `data`

这说明项目并不想在客户端层再定义一套复杂事件类体系，而是故意让事件类型尽量贴近 LangGraph SSE 语义。

这样做的好处是：

- HTTP 流式与嵌入式调用可以共用同一套消费逻辑。
- 后续若接入更多渠道或 SDK，不需要重新设计一套厚重的事件对象层。
- 事件格式更偏协议而不是对象继承树，适合跨进程和跨语言边界。

## 17. 渠道模块为什么又重新定义了一套消息对象

`backend/src/channels/message_bus.py` 里的 InboundMessage 和 OutboundMessage，不是为了替代 LangChain 的消息对象，而是为了处理“外部通道接入”这个不同边界。

LangChain 消息对象服务于模型上下文。
渠道消息对象服务于系统集成。

两者关心的问题完全不同：

- LangChain 消息关心 role、content、tool_calls、tool_call_id。
- 渠道消息关心 channel_name、chat_id、thread_ts、attachments、topic_id。

所以这里不是重复建模，而是两个边界层使用不同的消息协议：

- 会话内部协议。
- 平台集成协议。

## 18. IM 渠道的事件流是如何复用主会话消息语义的

ChannelManager 并不自己维护一套独立的 Agent 对话逻辑，它只是：

- 从 MessageBus 取入站消息。
- 解析或创建 LangGraph thread。
- 调用 `runs.wait`。
- 从结果里的 `messages` 中提取最后一轮回复文本和产物。
- 再发布为 OutboundMessage。

也就是说，渠道模块并没有发明另一套会话执行引擎，它只是把平台消息映射到主线程，再把主线程结果映射回平台消息。

这一层最值得注意的是 `_extract_response_text()` 的实现策略：

- 倒序扫描消息。
- 一旦遇到最后一条 human 消息就停止。
- 优先识别 ask_clarification 的 ToolMessage。
- 再识别 AI 文本消息。

这说明渠道层并不依赖某个“final_answer”专用字段，而是依赖统一消息历史的后向解析。

## 19. 为什么渠道层要把澄清消息当正常回复处理

当 ClarificationMiddleware 把 `ask_clarification` 调用拦截为 ToolMessage 并 `goto=END` 时，渠道层并没有额外开一个“待审批事件”类型。

它仍然把这条 ToolMessage 视为当前轮的最终可发送文本。

这样做的工程价值很高：

- 渠道侧不需要理解 LangGraph 的内部控制流。
- 渠道只需要知道“本轮该发什么给用户”。
- 审批/澄清在外部平台上表现为一条自然语言追问，而不是一个特殊协议弹窗。

这也是当前项目很典型的设计哲学：尽量用已有消息协议表达控制语义，而不是再造一层复杂的前后端协商协议。

## 20. `artifacts` 在事件流里承担什么角色

`artifacts` 虽然不是消息列表的一部分，但它和消息流关系非常紧。

原因是文件产物有两种存在方式：

- 作为状态字段，被工具通过 reducer 更新。
- 作为自然语言线索，被客户端或渠道层转成“Created File”之类的文本补充。

在 ChannelManager 中，系统会扫描本轮 AIMessage 中的 `present_files` 调用，从里面抽取 `filepaths`，而不是直接把整个线程状态里的 `artifacts` 全部返回。

这说明项目刻意区分了：

- 线程级累计产物。
- 当前轮新产物。

这个区分非常重要，否则多轮会话里旧文件会不断被重复外发。

## 21. 为什么附件解析要再次做安全检查

渠道层对产物外发并不是完全相信上游状态，而是做了二次约束：

- 只接受 `/mnt/user-data/outputs/` 前缀。
- 解析后要求路径必须仍在当前线程 outputs 目录内。
- 文件不存在或路径越界会直接跳过。

这说明事件流里的“文件产物发布”不是无条件广播，而是一个受控的外发流程。

这一步属于消息系统和权限系统的交叉点：并不是任何进入状态的路径都能被当作附件发出去。

## 22. 子 Agent 为什么还能共用同一套消息对象模型

子 Agent 在 `backend/src/subagents/executor.py` 中也是通过 `create_agent()` 创建的，因此它内部依然使用：

- HumanMessage 作为任务入口。
- AIMessage 作为运行中产出。
- 同样的 ThreadState 结构。

它的特别之处不在消息类型，而在消费方式：

- 执行器用 `astream(..., stream_mode="values")` 逐步拿状态快照。
- 每当最新消息是新的 AIMessage，就把它序列化后追加到 `result.ai_messages`。
- 主代理的 `task_tool` 再通过 stream writer 把这些子 Agent 进展作为任务运行事件发出去。

这意味着子 Agent 并没有独立的事件协议。它只是把标准 AIMessage 再包装成“任务进度事件”。

## 23. 这个模块里的几个关键 tricks

### 23.1 用统一消息历史承载多种语义

用户输入、模型输出、工具结果、系统补丁、人类视角提示，全部落在同一条 `messages` 时间线上。这样中间件和模型都只需要面对一种主语义载体。

### 23.2 从快照流反推出增量流

底层流式接口给的是 values 快照，但客户端通过消息 id 去重，派生出更适合展示的增量消息事件。这让底层实现保持简单，上层消费保持流畅。

### 23.3 用 ToolMessage 表达控制流结果

澄清、失败、占位补丁都尽量写成 ToolMessage，而不是引入额外控制消息类型。这样上下文协议更稳定，外部集成也更简单。

### 23.4 用 reducer 把副作用状态做成可组合更新

图片、文件产物这种非文本状态，没有被塞进消息正文硬编码，而是由 reducer 管理，再在合适时机投影回消息流。

### 23.5 在边界层重新解释消息，而不是复制执行逻辑

客户端、渠道、子 Agent 进度流都没有重写一套对话引擎，只是在各自边界上重新解释同一份消息历史。

## 24. 当前实现的能力边界

这个模块当前也有一些明确边界：

- 流式客户端当前主要基于 `stream_mode="values"` 自己派生增量事件，而不是直接消费更细粒度 token 级事件。
- 渠道层更多是最终态分发，和嵌入式客户端相比，实时事件粒度更粗。
- 很多控制信号仍然通过普通消息对象承载，因此某些高级前端如果想做强结构化交互，需要再额外理解这些语义。
- 系统并没有独立的消息版本迁移层，因此对象字段变更会直接影响上下游兼容性。

## 25. 这个模块的本质是什么

lumen 的事件流与消息对象模型，本质上是在做一件事：

把“模型思考、工具执行、状态副作用、人工澄清、文件产物、渠道回传”这些原本分散的行为，全部折叠到一条可持久化、可重放、可修补、可流式观察的统一会话时间线上。

谁掌握了这条时间线，谁就真正理解了这个项目是如何运行起来的。
