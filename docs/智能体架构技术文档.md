# lumen 智能体架构技术说明

## 1. 这是什么类型的智能体架构

先给出结论。

lumen 的后端智能体架构，它的核心更准确地说是：

- 一个运行在 LangGraph 之上的单主代理架构
- 底层执行循环由 LangChain 的 `create_agent()` 提供
- 交互模式属于 ReAct 风格的工具调用智能体
- 但不是经典论文式的“Thought / Action / Observation”文本格式
- 而是基于模型原生 tool calling 的现代 ReAct 变体
- 在这个主循环之外，项目再叠加中间件链、线程状态、沙盒、记忆、技能、MCP 和子代理委派

换句话说，如果一定要给它贴范式标签，最接近的说法是：

这是一个“LangGraph 承载的、LangChain Agent Loop 驱动的、带中间件增强和子代理委派能力的 ReAct-style 工具调用智能体系统”。

## 2. 从代码入口看，智能体是如何启动的

整个智能体系统的图入口定义在 `backend/langgraph.json`。这个文件把 LangGraph Server 暴露出来的图名 `lead_agent` 绑定到 `src.agents:make_lead_agent`，同时配置了异步 checkpointer。

这意味着当外部通过 LangGraph 的 `/threads/*` 或 `/runs/*` 发起一次执行时，真正被调用的不是某个手写 graph node，而是 `backend/src/agents/lead_agent/agent.py` 中的 `make_lead_agent(config)`。

这一步非常重要，因为它决定了整个项目的 Agent 架构不是“静态定义好很多 graph node 再手动连线”，而是“在运行时构造一个 agent 实例”，然后把它交给 LangGraph 承载线程、流式输出和 checkpoint。

从实现分层上看：

- LangGraph 负责线程、run、checkpoint、流式事件和服务承载
- `make_lead_agent()` 负责组装真正的 Agent
- `create_agent()` 负责底层的模型-工具-模型循环
- 项目自定义中间件、工具和状态模式，负责把这个循环改造成完整的 super agent

## 3. 这个项目的核心是不是 ReAct

严格来说，是“ReAct 思想下的工具调用 loop”，但不是教科书里的原始 ReAct 提示格式。

经典 ReAct 的特点是：

- 模型先输出推理
- 再显式输出 Action
- 系统执行 Action
- 再把 Observation 塞回上下文
- 模型继续下一轮推理

lumen 的主代理在行为上就是这条链：

- 模型思考当前任务
- 模型决定是否调用工具
- 工具返回结果
- 结果进入消息历史
- 模型继续推理，直到直接回答用户

但在实现形式上，它不是靠模型输出一段自定义文本再由项目自己解析 `Action:` 字段，而是依赖支持 tool calling 的聊天模型和 LangChain/LangGraph 的标准工具消息协议。

所以更准确的说法是：

- 语义上，它是 ReAct-like
- 协议上，它是 tool-calling agent
- 工程实现上，它是 `create_agent()` 驱动的 agent loop

这也是为什么你在代码里看不到一个手写的“大循环解析器”。循环并没有消失，而是被封装进了 LangChain Agent runtime。

## 4. 它不是手写 Agent looper，而是把 looper 交给了 `create_agent`

整个项目判断智能体架构类型的关键点，就在 `backend/src/agents/lead_agent/agent.py`。

`make_lead_agent()` 最后会调用 `create_agent(...)`，并传入以下几类参数：

- `model`
- `tools`
- `middleware`
- `system_prompt`
- `state_schema`

这说明项目并没有自己写一个循环去做下面这些事：

- 调模型
- 判断是否有工具调用
- 执行工具
- 把工具结果塞回消息
- 再次调模型
- 判断是否终止

这些循环行为是 `create_agent()` 的职责。项目做的是：

- 决定用哪个模型
- 决定给模型哪些工具
- 决定状态结构长什么样
- 决定中间件如何在循环前后修改状态
- 决定系统提示词如何拼装

因此，从架构形态上，lumen 是“基于框架 agent loop 的组装式架构”，不是“从零写 agent loop 的自定义解释器架构”。

## 5. 主智能体是单入口架构，不是多主代理图

这个项目运行时只有一个主入口 Agent，也就是 `lead_agent`。

这一点在 `backend/README.md` 和 `make_lead_agent()` 的实现里都非常明确。系统没有定义多个一等主代理节点然后让 graph 在它们之间来回跳转；相反，它是由一个主代理承担绝大部分调度责任。

这个主代理负责：

- 模型选择
- 提示词组装
- 工具调用
- 文件操作
- 搜索与抓取
- 记忆注入
- 技能加载
- 子代理委派
- 结果汇总

也就是说，这个系统的顶层形态不是“planner 节点 -> executor 节点 -> verifier 节点”的显式图，而是“单 orchestrator agent + 丰富工具生态 + 可选子代理”的架构。

## 6. 主代理实例是如何构造出来的

`make_lead_agent()` 的实现可以拆成五步。

第一步，解析运行时配置。

它会从 `RunnableConfig` 的 `configurable` 段里读取一系列运行开关，例如：

- 是否启用 thinking
- 使用哪个模型
- 是否启用计划模式
- 是否启用子代理
- 最大并发子代理数
- 是否是 bootstrap 模式
- 当前 agent 名称

第二步，解析最终模型。

这里不是简单读取一个固定模型，而是按照“请求覆盖 > agent 自定义配置 > 全局默认配置”的优先级解析模型名，再通过 `create_chat_model()` 构造具体模型实例。

第三步，构建工具集合。

`get_available_tools()` 会把以下几类工具合并起来：

- 配置文件中定义的普通工具
- 内置工具，例如 `present_file`、`ask_clarification`
- 视觉模型场景下的 `view_image`
- 启用子代理时的 `task`
- 已初始化的 MCP 工具

第四步，构建中间件链。

这一步决定了主代理 loop 外围的行为增强方式，也是这个项目和“纯裸 agent loop”差异最大的地方。

第五步，拼装系统提示词并调用 `create_agent()`。

最终返回的对象就是 LangGraph 会运行的主代理图实例。

## 7. 从实现上说，真正的“智能体架构”分成两层

如果只看项目名，很容易以为智能体架构就是一段提示词加一堆工具。但从代码角度更准确的分层是：

第一层是底层 agent loop。

这层由 `create_agent()` 提供，负责完成：

- 读取消息历史
- 调用模型
- 接收 tool calls
- 执行工具
- 注入 ToolMessage
- 重复以上过程直到结束

第二层是外围运行时增强层。

这层由项目自己实现，包括：

- 自定义状态模型
- 中间件链
- 沙盒系统
- 上传文件注入
- 记忆系统
- 技能系统
- MCP 工具
- 子代理系统
- 澄清中断机制

所以，lumen 的智能体架构不是“自己写了一个 loop”，而是“把通用 loop 当内核，再在外面包一层非常厚的 orchestration runtime”。

## 8. 状态模型是这个架构的骨架

主代理不是在一个无状态的消息列表上工作，而是运行在自定义状态模型 `ThreadState` 上。

这个状态定义在 `backend/src/agents/thread_state.py`，它继承自 `AgentState`，并在此基础上添加了多种运行时字段：

- `sandbox`
- `thread_data`
- `title`
- `artifacts`
- `todos`
- `uploaded_files`
- `viewed_images`

其中有两个字段尤其重要。

`artifacts` 带有 reducer，会把多个阶段产生的文件路径合并去重。这说明状态不是简单覆盖，而是按项目语义进行增量归并。

`viewed_images` 也带有 reducer，用来在视觉处理流程中合并或清空图片上下文。

这意味着项目的 Agent 架构不是“模型循环 + 若干副作用”，而是“模型循环 + 一个不断被中间件和工具改写的显式线程状态”。

## 9. 中间件链是这个项目真正的架构中枢

如果要找 lumen 智能体架构最有辨识度的部分，不是工具列表，而是中间件链。

在 `backend/src/agents/lead_agent/agent.py` 里，`_build_middlewares()` 按固定顺序构造中间件。这个顺序不是装饰性的，而是整个智能体运行语义的一部分。

当前主链路大致是：

- `ThreadDataMiddleware`
- `UploadsMiddleware`
- `SandboxMiddleware`
- `DanglingToolCallMiddleware`
- 可选 `SummarizationMiddleware`
- 可选 `TodoMiddleware`
- `TitleMiddleware`
- `MemoryMiddleware`
- 可选 `ViewImageMiddleware`
- 可选 `SubagentLimitMiddleware`
- `ClarificationMiddleware`

这条链说明项目采用的不是“多 agent 图节点架构”，而是“单 agent loop + middleware pipeline”架构。

也就是说，很多本来可以用 graph node 单独表示的能力，在这里被实现成了运行时切面：

- 线程目录准备
- 上传内容注入
- 沙盒绑定
- 上下文压缩
- 标题生成
- 记忆更新
- 图片注入
- 澄清中断

所以从工程实现看，它更像“agent loop 内核 + middleware-based orchestration”，而不是“显式 planner/executor graph”。

## 10. 每个中间件在架构里的角色是什么

### 10.1 `ThreadDataMiddleware`

它负责根据 `thread_id` 计算当前线程的工作目录、上传目录和输出目录，并把这些路径写入状态。

这一步让后续工具、沙盒、上传和产物机制都能围绕同一线程上下文运行。

### 10.2 `UploadsMiddleware`

它会把用户上传文件的信息注入到最后一条 human message 前部，形成 `<uploaded_files>` 区块。这样模型在本轮推理时天然知道有哪些文件可读，而不是靠外层调用方再做额外说明。

### 10.3 `SandboxMiddleware`

它负责把线程与沙盒执行环境绑定起来。这里不是简单“有个 bash 工具”，而是让整个 agent loop 在工具调用前知道自己应该操作哪一个线程沙盒。

### 10.4 `DanglingToolCallMiddleware`

这个中间件负责修补消息历史中缺失 `ToolMessage` 的情况，防止模型在下一轮读取历史时因为消息结构不完整而报错。

这个点很工程化，也很关键。它说明项目不是把 agent loop 当黑盒使用，而是主动修复 loop 在中断、取消等异常条件下可能产生的消息结构裂缝。

### 10.5 `MemoryMiddleware`

它并不直接影响本轮回复生成，而是在 `after_agent` 阶段把过滤后的对话提交到记忆更新队列。也就是说，记忆是外挂式异步更新，而不是每轮同步抽取。

### 10.6 `ClarificationMiddleware`

这是整个架构里非常重要的“中断型中间件”。当模型调用 `ask_clarification` 工具时，它不会像普通工具一样执行完继续 loop，而是被中间件拦截，生成一个 `Command(goto=END)`，把本轮执行提前结束并把澄清问题返回给用户。

这说明项目不仅有普通 ReAct 式循环，还有“被工具调用触发的结构化中断”。

## 11. 系统提示词不是固定字符串，而是动态拼装层

主代理的系统提示词定义在 `backend/src/agents/lead_agent/prompt.py`，但真正运行时并不是直接用常量，而是通过 `apply_prompt_template()` 动态生成。

这个生成过程会把多个上下文层拼进去：

- 角色定义
- agent soul
- memory context
- clarification workflow
- skills section
- subagent section
- working directory 说明
- response style
- citations 规则
- critical reminders
- 当前日期

因此，这个项目的提示词架构不是“一个固定 system prompt”，而是“一个运行时模板系统”。

这也解释了为什么项目可以在不修改底层 loop 的前提下，动态切换：

- 是否启用子代理
- 当前 agent 的人格和配置
- 当前可用技能
- 当前注入的长期记忆

## 12. 工具系统决定了主循环能做什么

`create_agent()` 的 loop 本身只是一个“模型遇到工具时继续循环”的通用机制，真正决定这个 Agent 能做什么的是工具系统。

在 `backend/src/tools/tools.py` 里，`get_available_tools()` 会把工具按运行时条件组装起来。

这里有几类工具：

- 配置型业务工具
- 内置控制工具
- 沙盒文件与命令工具
- MCP 工具
- 子代理工具

从架构上看，这意味着主代理并没有很多内部节点，它的大部分能力都是通过工具空间扩展出来的。

所以，如果把这个项目和传统“多模块 agent graph”比较，它明显更偏向：

- 一个强主代理
- 一组富工具
- 少量结构化中断和增强中间件

而不是：

- 多个显式 graph node 各自承担固定职责

## 13. 子代理系统让它从单 agent 变成分层 agent

虽然顶层只有一个主代理，但一旦启用 `task` 工具，系统就进入“主代理 + 子代理”的分层架构。

`task` 工具实现位于 `backend/src/tools/builtins/task_tool.py`。主代理调用它时，不是简单触发一个普通工具函数，而是会：

- 根据 `subagent_type` 读取子代理配置
- 继承父代理的一部分上下文
- 重新构造一个新的子代理执行器
- 在后台线程池中运行子代理
- 轮询结果并把状态流式写回

这里最关键的设计点有三个。

第一，子代理不是另一个 graph 顶层入口，而是主代理通过工具动态派生出来的。

第二，子代理会继承父代理的 `sandbox`、`thread_data` 和部分模型上下文，因此它和父代理不是完全隔离的世界。

第三，子代理默认不能再继续调用 `task`，从而避免无限递归套娃。

因此，从系统结构上看，lumen 是：

- 顶层单主代理
- 运行时可派生多个有类型的子代理
- 子代理由工具调用触发，而不是固定 graph 边触发

## 14. 子代理本身也是 agent，不是普通 worker 函数

这一点很重要。

在 `backend/src/subagents/executor.py` 中，子代理不是简单地执行一个函数，而是再次调用 `create_agent()` 创建出一个新的 agent 实例。也就是说，子代理本质上也是一个工具调用智能体，只不过：

- 使用更小的提示词范围
- 可用工具更受限
- 共享父线程环境
- 运行在单独上下文中

这意味着整个项目不是“一个 agent + 一堆非智能 worker”，而是“一个主智能体 orchestrator + 若干可嵌套但受控的次级智能体”。

不过它仍然不是完全自由递归的 agent society，因为：

- 子代理类型是预定义的
- 并发上限可配置
- 主代理每轮的 `task` 调用数有限制
- 子代理默认禁用再次委派

所以更准确的说法是“受控的分层多智能体架构”。

## 15. 从 loop 角度看，一次主代理执行是怎么跑的

如果把一次典型执行链路展开，顺序大致如下。

第一步，LangGraph Server 收到某个线程上的一次 run 请求。

第二步，LangGraph 根据 `langgraph.json` 找到 `lead_agent -> make_lead_agent()`，并构造主代理实例。

第三步，主代理实例进入 `create_agent()` 提供的执行循环。

第四步，中间件链先后运行，对状态和消息进行修饰，例如：

- 注入线程目录
- 注入上传文件列表
- 绑定沙盒
- 修补悬空工具消息
- 注入记忆或视觉上下文

第五步，模型根据系统提示词、消息历史、状态和工具定义生成下一步输出。

第六步，如果模型直接回答，则本轮 loop 结束。

第七步，如果模型发起工具调用，则工具执行结果会被写入消息历史，loop 继续。

第八步，如果工具是 `ask_clarification`，则 `ClarificationMiddleware` 会拦截并提前结束 run，等待用户回复。

第九步，如果工具是 `task`，则主代理会派生子代理执行，并在本轮中等待其结果后继续综合。

这说明整个项目的主循环仍然是一个标准 agent loop，只不过在“每次循环前后”和“特定工具调用点”插入了大量增强逻辑。

## 16. 为什么说它不是显式 Planner-Executor Graph

很多 LangGraph 项目会显式定义：

- planner node
- executor node
- critic node
- router node

然后通过图边控制执行路径。

lumen 不是这种做法。它没有在顶层 graph 中显式定义这些节点，而是把这些角色折叠进主代理的提示词、工具和中间件里。

例如：

- “planner” 行为主要由提示词中的思考规范和 Todo 中间件承担
- “executor” 行为主要由工具系统和沙盒系统承担
- “critic / clarification” 行为主要由提示词约束和 `ClarificationMiddleware` 承担
- “parallel worker” 行为主要由 `task` 工具和子代理执行器承担

因此，这个项目不是显式 graph-based multi-node planner-executor 架构，而是“隐式角色折叠进单 agent loop 的 orchestration 架构”。

## 17. 为什么它更像“Agent Runtime”而不只是“一个 Agent”

如果只从 `create_agent()` 看，它只是一个 agent。

但从整个工程结构看，lumen 已经不是单纯的 Agent Prompt + Tool Demo，而是一套完整的 Agent Runtime，原因在于它补齐了一个生产级执行环境通常需要的要素：

- 线程与 checkpoint
- 运行时状态模型
- 沙盒执行空间
- 文件上传与产物管理
- 记忆抽取与注入
- MCP 扩展
- 技能系统
- 子代理委派
- 中断式澄清
- 标题生成与上下文摘要

所以更准确的理解方式是：

- 底层内核是一个 tool-calling agent loop
- 上层工程形态是一套 super agent runtime

## 18. 最终结论

lumen 的智能体架构，不是 React，也不是项目自己手写的低层 Agent looper。它的核心是由 LangChain `create_agent()` 提供的工具调用循环，运行在 LangGraph 的线程与 checkpoint 框架之上。

如果从范式上概括，它最接近：

- ReAct-style tool-calling agent
- 单主代理 orchestrator
- middleware-based runtime augmentation
- 可选的受控分层多智能体委派

如果从实现上概括，它可以被拆成一句话：

项目把“推理-调用工具-接收结果-继续推理”的基础 loop 交给框架，把“线程状态、文件系统、记忆、技能、澄清、子代理、产物管理”等生产级能力做成外围运行时层，最终形成一个可持续执行复杂任务的 super agent 架构。

这也是为什么你在代码里既能看到标准 agent loop 的影子，又能看到大量不像传统 ReAct demo 的工程化部件。真正的架构不在某一个函数里，而在这两层叠加之后形成的整体。
