# lumen 工具权限与审批机制模块技术说明

## 1. 文档目标

这份文档专门解释项目里的“工具到底是怎么被允许、被限制、被审批、被外发控制”的。

这里要先说明一个很重要的事实：

lumen 当前并没有一个独立命名为“Permission Service”或“Approval Engine”的中心化权限模块。

它的工具权限与审批机制，是由多层约束共同组成的：

- 配置层决定哪些工具存在。
- Agent 层决定某个运行实例能看到哪些工具。
- 模型能力层决定某些工具是否应该暴露。
- 子 Agent 配置进一步做 allowlist 或 denylist。
- 工具实现层自行校验路径、文件类型和运行前提。
- 中间件层拦截特殊工具调用，把它们升级为“审批型中断”。
- 网关与渠道层限制哪些文件能真正外发给用户。

所以这个模块的真实形态，是分层权限体系，而不是单点权限开关。

## 2. 模块定位

与这个模块最相关的文件包括：

- `backend/src/tools/tools.py`
- `backend/src/config/tool_config.py`
- `backend/src/config/app_config.py`
- `backend/src/agents/lead_agent/agent.py`
- `backend/src/tools/builtins/clarification_tool.py`
- `backend/src/agents/middlewares/clarification_middleware.py`
- `backend/src/tools/builtins/present_file_tool.py`
- `backend/src/tools/builtins/view_image_tool.py`
- `backend/src/sandbox/tools.py`
- `backend/src/config/paths.py`
- `backend/src/channels/manager.py`

这些文件分别对应：

- 工具注册与装配。
- 配置模型。
- 运行时工具过滤。
- 审批型工具语义。
- 路径和文件级安全校验。
- 产物外发权限控制。

## 3. 第一层权限：工具先要“存在”

项目里的工具不是自动扫描目录就全部暴露，真正可用工具首先来自配置。

`ToolConfig` 只定义三个核心字段：

- `name`
- `group`
- `use`

这里的设计很克制，但效果很强：

- `use` 决定这个工具最终映射到哪个实际实现。
- `group` 决定它属于哪个工具组。
- `name` 决定它在配置和运行时的稳定标识。

也就是说，工具权限的第一层不是“运行时是否允许调用”，而是“配置里有没有把它纳入系统可注册集合”。

## 4. 第二层权限：主 Agent 运行时是否把它装进工具空间

真正决定当前 Agent 能看到哪些工具的，是 `get_available_tools()`。

它会组合几类工具来源：

- 配置文件声明的常规工具。
- 内置工具。
- MCP 工具。
- 条件性附加工具，例如子 Agent 工具、视觉工具。

这一层的关键点在于，系统不是一次性把所有工具无脑暴露给所有 Agent，而是会在装配期根据运行参数和模型能力做裁剪。

所以“工具存在”不等于“本轮运行可见”。

## 5. `groups` 过滤为什么是主权限开关之一

`get_available_tools()` 接受 `groups` 参数。当这个参数不为空时，只会保留 group 命中的配置工具。

这意味着项目把一部分权限边界前移到了“工具组”这个抽象上。

好处在于：

- 不需要为每个 Agent 重复列出完整工具清单。
- 可以按能力域组织工具，例如文件工具、搜索工具、代码工具。
- 自定义 Agent 只要声明允许哪些工具组，就能切出一个受控工具空间。

这是一种偏工程化的权限建模方式：不是基于用户角色做 RBAC，而是基于 Agent 能力包做 capability slicing。

## 6. 第三层权限：自定义 Agent 的工具白名单

在 `make_lead_agent()` 中，如果当前运行指定了 `agent_name`，系统会加载对应 Agent 配置。

其中一个关键作用就是：

- 如果 Agent 配置里声明了 `tool_groups`，主图装配时就只会给它对应组的工具。

这说明自定义 Agent 的差异不只是 prompt 或模型差异，而是真正的能力空间差异。

从权限角度看，这比“让模型自己克制不用某些工具”更可靠，因为它是在装配期直接从工具列表里删掉了那些工具。

## 7. 第四层权限：模型能力也会影响工具暴露

当前项目里最典型的例子就是 `view_image_tool`。

这个工具只有在运行时解析出的模型配置满足 `supports_vision=True` 时才会加入工具集合。

这说明工具权限并不是只看“业务上要不要给”，还看“底层模型有没有处理这个工具结果的能力”。

这样设计能避免两类问题：

- 给无视觉能力模型暴露图片工具，导致工具调用后无法消费结果。
- 让 prompt 里出现与模型能力不匹配的操作暗示。

这属于一种“能力感知型权限裁剪”。

## 8. 第五层权限：子 Agent 的工具过滤更严格

子 Agent 的权限策略比主 Agent 更保守。

在 `SubagentExecutor` 里，所有可用工具还会再经过 `_filter_tools()` 过滤：

- 若定义了 allowlist，则仅保留名单内工具。
- 若定义了 denylist，则强制剔除名单内工具。

内置的 `general-purpose` 和 `bash` 两类子 Agent 都明确禁用了：

- `task`
- `ask_clarification`
- `present_files`

这一点非常关键，因为它避免了三种风险：

- 子 Agent 再递归创建新的子 Agent，导致任务树失控。
- 子 Agent 在无人监督下把执行中断给用户，打乱主流程。
- 子 Agent 直接把文件对外呈现，绕过主 Agent 的最终整理。

也就是说，子 Agent 虽然能拿到不少工具，但它不是一个拥有完整用户交互权和发布权的主体。

## 9. 当前项目的审批机制不是弹窗式，而是会话式

这里必须说清楚一个实现事实：

项目当前没有独立的“审批中心页面”或“工具调用批准弹窗后端”。

它的审批机制主要通过 `ask_clarification` 这条协议链实现。

这条链由三部分组成：

- prompt 负责定义哪些场景必须请求用户确认。
- `ask_clarification_tool` 作为协议锚点暴露给模型。
- `ClarificationMiddleware` 在运行时拦截，并把调用转成中断执行的 Command。

所以它的审批不是 GUI 弹窗审批，而是“把高风险决策转写成一条向用户发起的澄清消息，然后暂停主循环”。

## 10. 提示词层为什么已经在做权限前置

在 `lead_agent/prompt.py` 里，系统显式规定了五类必须先澄清再行动的场景：

- 缺失信息。
- 需求歧义。
- 方案选择。
- 风险操作。
- 建议征求批准。

尤其是“Risky Operations”部分，已经把删除文件、修改生产配置、覆盖现有代码或数据，定义成必须先确认的行为。

这说明项目的审批第一道闸门其实在 prompt 层。

这听起来像软约束，但它有现实价值：

- 能在模型规划动作之前就改变其决策路径。
- 避免很多高风险工具调用根本不发生。
- 让审批语义能覆盖“还没执行”的意图，而不是只在执行瞬间拦截。

## 11. 为什么还需要中间件把审批做成硬中断

如果只有 prompt，没有运行时硬约束，模型仍然可能偏航。

所以系统又加了 ClarificationMiddleware 这道硬闸：

- 只要工具名是 `ask_clarification`，就不走普通工具执行。
- 直接构造 ToolMessage。
- 直接 `goto=END`。

这一步的意义是把“审批”从语言建议升级成执行控制。

因此当前审批链是双层的：

- prompt 负责告诉模型何时必须申请批准。
- middleware 负责把批准申请真正变成一次中断。

## 12. `ask_clarification_tool` 为什么是占位工具

`ask_clarification_tool` 的函数体几乎没有业务逻辑，只返回一个占位字符串。

这不是没做完，而是刻意设计：

- 它的职责不是自己去处理审批流程。
- 它只是让模型能以标准 tool call 语义发起澄清请求。
- 真正的处理逻辑由中间件接管。

这样做的好处是：

- 模型侧仍然觉得这是普通工具，学习成本低。
- 框架侧可以保持统一 tool call 协议。
- 审批流程的控制权保留在编排层，而不是散落进单个工具函数里。

## 13. 为什么说当前审批机制是“用户确认型”，不是“系统授权型”

当前实现能做得很好的，是这类审批：

- 我推荐这样改，你确认吗。
- 这个操作有风险，我要不要继续。
- 有多种方案，你选哪一个。

但它没有实现的是另一类更重的授权体系：

- 针对不同用户身份发不同权限。
- 针对不同工具建立细粒度 ACL。
- 针对每次工具调用发服务端审批票据。
- 支持审批链追踪、审批日志、审批人签名。

所以用更准确的话说，这个项目现在实现的是“会话中的用户确认机制”，而不是企业级授权工作流引擎。

## 14. 工具实现层是如何做本地权限校验的

除了“能不能看到某工具”，更重要的是“调用了以后能不能为所欲为”。

当前项目在工具实现层做了大量本地权限校验。

这些校验不是统一入口，而是按风险点内聚在具体工具里。

这是一种很实用的工程策略：把最了解风险边界的校验，放在离实际副作用最近的地方。

## 15. `present_files` 的权限边界为什么很硬

`present_files` 并不是任意文件都能展示给用户。

它会把路径归一化后强制要求：

- 路径必须位于当前线程的 outputs 目录内。
- 不接受越界到 uploads、workspace 或任意宿主机路径。
- 若传入的是虚拟路径，也会先解析到当前线程的真实 outputs 目录再验证。

这说明项目明确把“可以对用户发布的文件”和“仅供内部处理的文件”分开了。

只有 outputs 才被视为正式对外交付区。

## 16. `view_image` 的权限边界说明了什么

`view_image_tool` 会做一整套校验：

- 路径必须是绝对路径。
- 文件必须存在。
- 不能是目录。
- 扩展名必须属于支持的图片类型。

如果运行在本地沙箱，还会先把虚拟路径映射到当前线程真实路径。

它说明了当前系统的安全策略不是“工具看到路径就照做”，而是“工具必须先证明自己操作的是合法资源”。

## 17. 沙箱工具层的权限控制更接近资源约束

在 `sandbox/tools.py` 里，像 `bash`、`ls`、`read_file`、`write_file`、`str_replace` 这些工具，首先要经过几层预处理：

- 确保沙箱已初始化。
- 必要时创建线程目录。
- 若是本地沙箱，则把 `/mnt/user-data/...` 映射到当前线程真实路径。

它们没有在这一层实现一个花哨的“权限矩阵”，但通过沙箱和路径映射完成了资源隔离：

- 工具默认工作在当前线程对应的数据域。
- 工具看到的是虚拟路径语义，不是整个宿主机绝对路径空间。
- 真正的 I/O 执行仍受沙箱实现限制。

这属于环境级权限控制，而不是单工具函数内部的业务判断。

## 18. `thread_id` 校验其实也是权限系统的一部分

`Paths.thread_dir()` 对 `thread_id` 做了严格正则校验，只允许字母、数字、下划线和短横线。

这一步看起来像普通输入校验，实际上是权限系统的一部分。

因为一旦 `thread_id` 可注入路径分隔符或 `..`，线程级数据隔离就会立刻失效。

所以这里的 thread_id 约束，本质上是在保护：

- 线程目录边界。
- 路径解析安全。
- 工具访问域隔离。

## 19. `resolve_virtual_path()` 为什么是高价值安全点

`Paths.resolve_virtual_path()` 做了两类关键保护：

- 路径必须以虚拟前缀开头。
- 解析后的真实路径必须仍然相对属于当前线程的 user-data 根目录。

这意味着即便有人构造出看似合法的 `/mnt/user-data/...` 路径，只要最终 realpath 脱离了线程目录，就会被拒绝。

它是本项目很多权限边界的基础设施：

- artifacts 路由依赖它。
- present_files 的路径归一化依赖它。
- channels 附件解析依赖它。

## 20. Gateway 对产物下载为什么还要再做一遍限制

即使文件已经被工具加入 `artifacts` 或能在虚拟路径里解析出来，Gateway 和渠道层仍然会再次限制其访问边界。

在 artifacts 路由中：

- 路径非法会返回 400 或 403。
- 越界访问会被拒绝。

在 ChannelManager 中：

- 只有 `/mnt/user-data/outputs/` 下的路径才允许作为附件外发。
- 解析后仍必须留在 outputs 目录内。

这说明“文件能被工具处理”与“文件能被用户下载或通过 IM 收到”是两道不同权限闸门。

## 21. 为什么 outputs 目录是发布权限的核心边界

从整体设计看，系统把线程目录分成了三类：

- uploads：用户输入区。
- workspace：内部工作区。
- outputs：对外交付区。

这个划分看似是目录规划，实际上同时也是权限模型。

其中最重要的隐含规则是：

- uploads 可以读，不代表可以直接外发。
- workspace 可以写，不代表可以直接展示。
- outputs 才是发布白名单。

这是一种非常朴素但很有效的权限设计。它不需要复杂策略引擎，只要保证所有外发路径都必须经过 outputs 边界。

## 22. 为什么子 Agent 被禁止 `present_files`

这点很能体现项目的审批与发布理念。

子 Agent 可以帮助主 Agent 做探索、执行命令、修改文件，但它不能自己决定把什么作为正式产物展示给用户。

原因是：

- 子 Agent 的上下文更窄，更适合执行，不适合做最终对外判断。
- 文件发布通常意味着“这就是本轮交付物”，属于主 Agent 级别的责任。
- 若子 Agent 可以随意 present，主流程会失去统一的交付口。

所以这里的 denylist 不只是权限限制，也是在维护系统的责任边界。

## 23. 为什么当前没有统一的“工具审批表”

从代码实现看，项目并没有为每个工具做一张全局审批表，例如：

- 哪些工具必须审批。
- 哪些工具可直接执行。
- 哪些工具只读。
- 哪些工具 destructive。

当前更接近“分层隐式表达”：

- prompt 里规定高风险动作要先 ask_clarification。
- 子 Agent denylist 限制高风险交互工具。
- 文件发布路径限制决定了哪些结果可对外。
- 具体工具函数自己校验输入边界。

这套方式的优点是实现简单、容易扩展；缺点是策略分散，不像统一策略引擎那样一眼可审计。

## 24. 这个模块里的几个关键 tricks

### 24.1 把“可见性权限”和“执行时权限”分开

先通过工具组、模型能力、自定义 Agent 配置决定工具是否进入工具空间，再由具体工具和路径解析决定它执行时能做什么。

### 24.2 用 `ask_clarification` 把审批问题转成会话协议

当前系统没有单独审批服务，但通过 prompt 加中间件，把审批自然地嵌进了主会话流程。

### 24.3 用目录语义做发布权限边界

outputs 目录不是普通文件夹，而是“允许对外展示”的白名单区域。这个约束既简单又非常稳。

### 24.4 用子 Agent denylist 保护主流程主权

子 Agent 能做很多执行性工作，但不能随意二次委派、打断用户、或直接发布结果。

### 24.5 把高风险校验内聚在离副作用最近的地方

路径解析、文件存在性、格式合法性、目录归属校验，都尽量放在具体工具或路径解析工具中，而不是依赖一个远端统一判断。

## 25. 当前实现的能力边界

这个模块当前的边界也很明确：

- 没有统一的企业级授权中心或审批工作流引擎。
- 没有按用户身份、租户、组织做细粒度权限模型。
- 风险操作主要靠 prompt 约束加会话确认，而不是强制的系统策略表。
- 某些工具的“风险级别”仍然是隐式表达，需要靠文档和实现理解，而不是配置即可审计。

## 26. 这个模块的本质是什么

lumen 的工具权限与审批机制，本质上不是一个单体模块，而是一套分层防线：

- 装配期防止不该出现的工具进入工具空间。
- 运行期防止工具越权访问错误资源。
- 会话期防止高风险决策在没有用户确认时继续推进。
- 外发期防止内部文件绕过交付边界直接暴露。

它的风格不是重型策略引擎，而是工程上非常务实的多层约束体系。

也正因为如此，理解这个模块时不能只看某一个类，而要看整个系统是如何把“能不能用、能不能做、做完能不能发出去”拆成三道不同的门。
