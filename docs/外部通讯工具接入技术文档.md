# lumen 外部通讯工具接入技术文档

## 1. 文档目标

这份文档专门说明 lumen 是如何连接外部通讯工具的。这里说的“外部通讯工具”，主要指项目当前内置支持的三类即时通讯平台：

- 飞书
- Slack
- Telegram

本文重点解释的是接入机制、消息链路、会话映射、附件发布、安全边界和运维方式，而不是逐行解释代码实现。

## 2. 先给结论

lumen 连接外部通讯工具的方式，不是把每个平台单独做成一套完整业务逻辑，而是抽象成统一的通道系统。

这套系统的核心思路是：

- 每个通讯平台只负责收消息和发消息。
- 所有平台消息都会先被转换成统一的入站消息。
- 统一的通道管理器负责把入站消息转交给 LangGraph Server。
- LangGraph 线程返回结果后，再由通道系统把结果发回原来的平台。

换句话说，飞书、Slack、Telegram 只是“外部入口和外部出口”，真正的对话执行内核仍然是 lumen 自己的主 Agent 与 LangGraph 线程系统。

## 3. 当前项目支持哪些通讯平台

从当前仓库实现看，项目已经内置了三种通道适配器：

- 飞书通道
- Slack 通道
- Telegram 通道

三者都被纳入同一套 `channels` 配置体系中统一管理。

从当前仓库的运行配置看：

- 飞书通道已启用
- Slack 通道默认未启用
- Telegram 通道默认未启用

从当前日志可以看出，飞书链路已经实际建立过连接，并且能够接收用户消息、写入总线并尝试转交给通道管理器处理。

## 4. 整体架构怎么分层

这个项目的外部通讯接入，一共分成五层。

### 4.1 配置层

配置入口在项目根目录的 `config.yaml` 中，统一挂在 `channels` 节点下。

这一层定义：

- LangGraph 服务地址
- Gateway 服务地址
- 所有通道共享的默认会话参数
- 每个平台自己的凭证和开关
- 按通道、按用户覆盖 assistant、上下文和运行参数的能力

环境变量会在配置加载阶段被自动解析，所以凭证通常不直接写死在配置文件里，而是通过 `.env` 或环境变量注入。

### 4.2 生命周期管理层

Gateway 启动时会尝试启动 ChannelService，也就是通道服务。

这一层负责：

- 读取 `channels` 配置
- 创建统一的消息总线
- 创建会话映射存储
- 创建通道管理器
- 按配置实例化并启动已启用的渠道适配器

也就是说，外部通讯工具不是单独跑一个独立进程，而是作为 Gateway 生命周期中的一部分被拉起和关闭。

### 4.3 平台适配层

平台适配层对应飞书、Slack、Telegram 三个通道类。它们各自负责：

- 以适合该平台的方式建立连接
- 把平台原生事件解析成统一的消息对象
- 在收到回复后，按平台能力把文本和附件发回去

这一层只关心平台协议，不关心 Agent 内部推理。

### 4.4 通道编排层

通道编排层的核心是 ChannelManager。

它负责：

- 从消息总线读取入站消息
- 判断是普通聊天还是命令
- 为外部会话创建或复用内部 LangGraph 线程
- 把消息提交给指定 assistant
- 从运行结果里提取本轮文本回复和本轮新产物
- 把结果重新发布成出站消息

这一层相当于外部通讯平台和内部 Agent 运行时之间的桥。

### 4.5 状态映射层

状态映射层由 ChannelStore 承担。

它的作用是把“平台侧会话”映射到“lumen 内部线程”。

如果没有这层映射，用户在飞书或 Slack 里连续发几句话，系统就无法知道这些消息应该落到同一个内部线程，还是应该开启一条新的会话。

## 5. 为什么这个项目不需要公网回调

这个项目的外部通讯接入，有一个很明显的设计特点：三种平台都采用“主动向外连”的模式，而不是等平台从公网回调进来。

具体来说：

- 飞书使用 WebSocket 长连接
- Slack 使用 Socket Mode
- Telegram 使用长轮询

这样设计的直接好处是：

- 本地开发更简单
- 内网环境更容易部署
- 不需要专门暴露公网回调地址
- 减少反向暴露服务的安全面

这也是配置文件里明确强调“所有通道都使用出站连接，无需公网 IP”的原因。

## 6. 配置是如何驱动接入行为的

`channels` 配置不只是决定“开还是不开”，它还决定整条消息链路的运行方式。

### 6.1 全局配置

通道系统会先读取两类全局地址：

- `langgraph_url`：用来把消息发给 LangGraph Server，做线程管理和运行等待
- `gateway_url`：用来处理命令类查询，例如模型列表和记忆状态

### 6.2 默认会话配置

`channels.session` 是所有通讯平台共享的默认会话层。

这一层可以统一规定：

- 默认使用哪个 assistant
- 运行配置，例如递归上限
- 运行上下文，例如是否开启 thinking、是否启用计划模式、是否启用子代理

### 6.3 通道级覆盖

某个通道可以单独覆盖默认会话设置。

这意味着项目支持这样的运营方式：

- 网页端和 IM 端使用不同 assistant
- 手机消息渠道关闭部分高成本能力
- 某个渠道开启更保守或更激进的运行参数

### 6.4 用户级覆盖

在单个通道内部，还可以针对某个用户再做一层覆盖。

这让项目具备了比较强的精细化能力，例如：

- 某个 VIP 用户走另一个 assistant
- 某个测试用户开启子代理
- 某个管理员拥有更高的递归上限

通道管理器在真正发起一次运行前，会按“默认层、通道层、用户层”的顺序合并这些配置。

## 7. 消息是怎么从外部平台进入项目的

外部消息进入项目，大致会经历七步。

### 7.1 平台连接建立

每个通道启动后，会先建立自己与外部平台之间的连接：

- 飞书建立 WebSocket 连接
- Slack 建立 Socket Mode 连接
- Telegram 启动轮询线程

只有连接建立成功，这个平台才算真正处于运行状态。

### 7.2 收到平台原生事件

当用户在平台里发消息时，平台适配器会收到原生事件对象。

适配器先做本平台的预处理，例如：

- 忽略机器人自己的消息
- 忽略空文本
- 对某些平台执行用户白名单过滤
- 判断消息是否属于某个已有回复链

### 7.3 转换成统一入站消息

随后，平台原生事件会被转成统一的 InboundMessage。这个统一对象会保留几类关键标识：

- 来源平台名
- 平台会话 ID
- 平台用户 ID
- 文本内容
- 是否为命令
- 平台线程标识
- 主题标识
- 附加元数据

这一步很重要，因为从这里开始，后面的通道管理器就不用再关心“这条消息原来来自飞书还是 Telegram 的什么格式”。

### 7.4 平台侧即时反馈

在把消息正式交给主系统处理之前，平台适配器通常还会先给用户一个即时反馈，告诉对方消息已经收到。

项目当前的做法比较统一，通常会包含两类反馈：

- 一个“已收到”的反应或标记
- 一条“正在处理”的临时回复

这样做有两个目的：

- 缓解大模型响应较慢带来的等待焦虑
- 让用户明确知道机器人已经接单，而不是没有反应

### 7.5 写入消息总线

处理完成的入站消息会被发布到 MessageBus 中。

消息总线的作用不是复杂路由，而是做一个解耦层：

- 平台适配器只负责把消息放进去
- 通道管理器只负责从里面拿消息

这样平台接入和对话分发可以彼此独立演进。

### 7.6 通道管理器消费消息

通道管理器会持续监听消息总线，并按并发限制处理每一条入站消息。

它会先判断消息类型：

- 以斜杠开头的，按命令处理
- 其他普通文本，按聊天处理

### 7.7 转交给 LangGraph

对于普通聊天消息，通道管理器会把用户文本包装成标准的人类消息，然后通过 LangGraph SDK 调用内部线程运行接口，并等待最终结果返回。

## 8. 会话连续性是怎么保证的

项目能在外部通讯工具里维持连续对话，关键不在平台本身，而在“平台主题”和“内部线程”之间的映射。

### 8.1 ChannelStore 的作用

ChannelStore 会把平台侧会话信息保存到磁盘中的一个 JSON 文件里。

它保存的不是聊天内容，而是映射关系，例如：

- 某个平台
- 某个会话
- 某个主题
- 对应到哪个内部线程
- 最初由哪个用户创建
- 创建和更新时间

这样即使服务重启，只要映射文件还在，系统仍然知道下一条消息应该继续落到哪条线程上。

### 8.2 topic_id 的作用

系统并不是简单按 `chat_id` 复用线程，而是进一步引入了 `topic_id` 概念。

它的含义是：在同一个平台会话里，哪些消息属于同一条对话主题。

只要 `topic_id` 相同，系统就会复用同一个内部线程；如果 `topic_id` 不同，就会新建线程。

### 8.3 三个平台的主题判定方式

飞书的主题判定方式是：

- 如果消息是在已有线程里回复，使用根消息 ID 作为主题
- 如果是新的独立消息，使用当前消息 ID 作为主题

Slack 的主题判定方式是：

- 使用 `thread_ts` 作为主题标识
- 在线程消息里，整条线程共用同一个根时间戳
- 非线程消息则天然形成新的主题

Telegram 的主题判定方式是：

- 如果用户回复了某条消息，就用被回复消息的 ID 作为主题
- 如果没有回复任何消息，就用当前消息 ID 开启新主题

### 8.4 命令如何影响会话

系统内置了一组面向 IM 通道的命令：

- `/new`：为当前会话或主题创建一个新的内部线程
- `/status`：查看当前会话绑定的内部线程
- `/models`：通过 Gateway 查询模型列表
- `/memory`：通过 Gateway 查询记忆状态
- `/help`：显示帮助信息

其中最关键的是 `/new`，因为它会直接重置当前会话映射，让后续消息转入新的内部线程。

## 9. 返回消息是怎么发回平台的

当 LangGraph 线程完成本轮运行后，通道管理器会进入“结果回传”阶段。

### 9.1 从运行结果中提取最终回复

项目没有依赖某个单独的“最终答案字段”，而是从消息历史里倒序查找本轮最后可发送的文本。

它会优先识别：

- 澄清场景下的提示文本
- 普通 AI 文本回复

这样做的好处是，外部通讯渠道不需要理解太多 Agent 内部状态，也能把用户真正需要看到的话发回去。

### 9.2 只提取本轮新产物

如果这一轮生成了文件，系统不会把线程历史上所有旧文件都再发一遍，而是只提取本轮新产生的产物。

项目用这种方式避免了多轮对话里重复下发旧附件的问题。

### 9.3 先发文本，再发附件

统一的通道基类规定，出站时先发送文本，再逐个上传附件。

这样做的理由很实际：

- 如果文本发送失败，就不要只发文件，避免用户只收到一个孤零零的附件
- 如果某个附件上传失败，其他附件仍然可以继续尝试发送

### 9.4 附件失败时的文本兜底

即使附件上传被跳过或失败，系统也会尽量在文本里补充“创建了哪些文件”的说明。

这样至少能保证用户知道本轮确实产出了文件，不会因为平台附件能力或上传失败而完全失去感知。

## 10. 文件附件为什么是受控发布，而不是直接外发

外部通讯工具接入里，文件外发是一个非常敏感的环节，所以项目专门做了二次安全限制。

### 10.1 只允许发布 outputs 目录

系统只允许把 `/mnt/user-data/outputs/` 下的文件作为附件发出去。

这背后的权限逻辑非常明确：

- uploads 是用户输入区，不等于可以直接外发
- workspace 是内部工作区，更不能直接外发
- outputs 才是对外交付区

也就是说，只有明确被主流程当成“交付物”放进 outputs 的文件，才有资格通过 IM 通道外发。

### 10.2 解析后还要检查是否越界

即使某个路径看起来像 outputs 下的路径，系统也不会直接相信。

它还会继续检查：

- 解析后的真实路径是否仍然位于当前线程的 outputs 目录内
- 文件是否真的存在
- 是否发生了路径穿越

只要有任何异常，这个附件就会被跳过。

### 10.3 安全设计的意义

这意味着项目明确区分了两件事：

- 文件能不能在内部被工具处理
- 文件能不能对外发送给用户

这是一个很成熟的边界设计，因为“内部可见”不应该自动等于“对外可发”。

## 11. 三个平台各自是怎么接入的

虽然三种平台共用统一框架，但它们的接入方式并不完全一样。

### 11.1 飞书

飞书通道采用 WebSocket 长连接模式。

它的特点是：

- 不需要公网回调
- 启动后会建立到飞书消息前端的持续连接
- 收到消息后会先加反应，再回一条“正在处理”提示
- 最终回复默认以飞书卡片消息形式发出
- 如果消息原本在飞书线程里，系统会继续在线程中回复

飞书通道还支持文件上传，并区分图片和普通文件：

- 图片和普通文件走不同的飞书上传接口
- 图片大小限制更严格
- 普通文件会按后缀推断文件类型

另外，飞书 SDK 的事件循环与主服务事件循环存在兼容性处理，所以项目把飞书连接单独放进一个线程运行。这属于接入层面对第三方 SDK 运行模型做的适配。

### 11.2 Slack

Slack 通道采用 Socket Mode。

它的特点是：

- 同样不需要公网回调
- 使用 Bot Token 和 App Token 双令牌
- 可以通过 `allowed_users` 做用户白名单
- 支持私聊消息和被提及消息
- 用线程时间戳来维持会话主题

Slack 在回传消息时，会先把普通 Markdown 转成 Slack 能更好识别的格式，再发回平台。

它还会通过 emoji 给出状态反馈：

- 收到时给原消息加已读型反应
- 完成时给线程根消息加完成反应
- 发送失败时尝试加失败反应

Slack 文件发送走平台文件上传接口，支持把生成产物直接挂在线程里。

### 11.3 Telegram

Telegram 通道采用长轮询模式。

它的特点是：

- 使用 Bot Token 接入
- 可选用户白名单
- 通过命令处理器和普通文本处理器分别接收命令与聊天内容
- 通过回复关系模拟连续对话链

Telegram 没有像 Slack 那样天然清晰的线程模型，所以项目采用了一个实用策略：

- 记录最近一次机器人消息
- 后续回复优先挂在这条机器人消息下

这样可以在 Telegram 的交互习惯里尽量维持“这是同一轮对话链”的感觉。

Telegram 发送附件时也区分图片和普通文档，并且做了平台大小限制控制。

## 12. Gateway 在这个体系里承担什么角色

很多人第一次看这个项目时，会以为外部通讯平台直接把消息发给 LangGraph。实际上并不是这样。

Gateway 在外部通讯接入里有三个关键角色。

### 12.1 负责启动和关闭通道服务

通道服务是跟着 Gateway 生命周期启动的，所以 Gateway 是外部通讯接入的宿主。

### 12.2 提供渠道运维接口

Gateway 暴露了专门的渠道管理接口，用来做两个动作：

- 查看通道服务和各平台通道状态
- 重启指定通道

这让运维层可以不重启整个系统，就针对某一个平台做检查和恢复。

### 12.3 提供辅助命令数据

IM 渠道里的 `/models` 和 `/memory` 这类命令，本质上不是直接问 LangGraph，而是由通道管理器转去调用 Gateway API，再把结果回给用户。

因此，Gateway 不只是“托管通道”，它也是一部分命令能力的数据提供方。

## 13. 运行时可以观测到哪些现象

如果通道接入正常，通常可以在日志中看到这样几类现象：

- 通道服务启动成功
- 某个渠道已启动
- 与平台建立连接
- 收到原始事件
- 入站消息写入总线
- 通道管理器开始处理消息
- 调用 LangGraph 线程运行
- 回传文本或附件

如果链路异常，最常见的问题点通常在下面几层：

- 平台凭证缺失或错误
- 对应 SDK 未安装
- Gateway 或 LangGraph 地址不可达
- 第三方平台连接已断开
- 产物路径不在 outputs 目录
- 平台附件大小超过限制

## 14. 这套设计为什么值得保留

这个项目的外部通讯接入设计，最大的优点不是“支持三个平台”，而是它把平台接入抽象成了一套统一边界。

这样带来的长期收益有四个：

- 新增平台时，只需要新增一个适配器，不必重写整套 Agent 流程
- 会话状态和线程状态被清晰分离，问题定位更容易
- 文件外发有明确白名单边界，安全性更高
- 平台能力差异被隔离在适配层，不会污染主 Agent 逻辑

从工程角度看，这是一种很适合 Agent 产品继续扩展的接入方式。

## 15. 对当前项目的落地理解

如果结合当前仓库来看，可以把外部通讯工具接入理解成下面这条完整链路：

- 在 `config.yaml` 中声明要启用哪些平台和默认会话策略
- Gateway 启动时拉起 ChannelService
- 每个平台适配器主动连接对应平台
- 用户在平台中发消息
- 平台适配器把消息转换成统一入站消息并送入 MessageBus
- ChannelManager 通过 ChannelStore 创建或复用内部线程
- ChannelManager 调用 LangGraph Server 执行主 Agent
- 运行结果中的文本和新产物被转换成统一出站消息
- 平台适配器再把文本和附件发回原平台

所以，本项目连接外部通讯工具的本质，不是“在 IM 平台里直接嵌一段机器人代码”，而是“把外部通讯平台纳入 lumen 自己的线程与交付体系中”。
