# lumen 提示词编排模块技术说明

## 1. 文档目标

本文详细介绍 lumen 中的提示词编排模块。重点不是分析某一段 prompt 的写法，而是说明这个项目如何把多个动态上下文来源组合成最终系统提示词，以及为什么提示词在这里是运行时拼装的，而不是一段静态文本。

阅读本文后，读者应能够回答以下问题：

- 系统提示词的主体是如何组织的
- 为什么 memory、skills、SOUL、subagent 这些内容不是直接硬编码在一段文本里
- 当前日期、工作目录规则、澄清策略、响应风格等是如何统一进入 prompt 的
- 提示词编排和模型能力、技能系统、自定义 Agent 是如何耦合的

### 1.1 先给出四个直接答案

- 系统提示词主体如何组织：项目不是维护一整段固定字符串，而是以 `SYSTEM_PROMPT_TEMPLATE` 为骨架，再把 memory、skills、SOUL、subagent 等动态片段按区块插入。
- 为什么这些内容不直接硬编码：因为它们都依赖运行时状态和开关，既可能按 `agent_name` 切换，也可能按能力是否启用而决定是否注入。
- 当前日期、工作目录规则、澄清策略、响应风格如何统一进入 prompt：它们都在 `runtimes/backend/src/agents/lead_agent/prompt.py` 中被编排成系统级协议片段，最终一起渲染成完整提示词。
- 提示词编排如何与模型能力、技能系统、自定义 Agent 耦合：提示词不是孤立模板，而是消费记忆系统、技能加载结果、自定义 Agent 的 SOUL/名称以及运行时能力开关的一层总装逻辑。

## 2. 模块定位

在 lumen 中，提示词不是一个“固定的系统指令字符串”，而是一层运行时编排逻辑。它承担的是把多个动态来源折叠成模型可读控制面的工作，包括：

- Agent 身份
- SOUL
- 持久化记忆
- 技能清单
- 子 Agent 协作规则
- 工作目录语义
- 澄清策略
- 输出风格
- 当天日期

因此，这个模块更准确的定位不是“提示词模板文件”，而是“系统行为协议的拼装器”。

## 3. 核心设计原则

从实现看，这个模块有几个非常明确的设计原则。

第一，静态模板与动态片段分离。主体框架写在 `SYSTEM_PROMPT_TEMPLATE` 中，而 memory、skills、soul、subagent 这些上下文是运行时生成的插槽。

第二，不把所有信息一开始全量注入，而是按场景裁剪。例如 skills 只注入索引，memory 只注入可控长度摘要，subagent 只在启用时注入。

第三，提示词不仅描述角色，也约束协议。像 `ask_clarification` 的使用规则、技能渐进加载模式、文件输出约束，都是写进系统提示词的运行时协议。

第四，提示词和中间件是互补关系。很多能力不是只靠代码，也不是只靠 prompt，而是两者配合实现。

## 4. 代码入口与分层

与提示词编排最相关的代码主要在：

- `runtimes/backend/src/agents/lead_agent/prompt.py`
  这是绝对主入口，定义系统模板、动态片段生成函数，以及最终拼装函数。

- `runtimes/backend/src/config/agents_config.py`
  负责读取自定义 Agent 的 `SOUL.md`。

- `runtimes/backend/src/agents/memory/prompt.py`
  负责把长期记忆转成可注入文本。

- `runtimes/backend/src/skills/loader.py` 与 `runtimes/backend/src/agents/lead_agent/prompt.py`
  共同决定 skills 片段如何注入。

- `runtimes/backend/src/agents/lead_agent/agent.py`
  负责在创建 Agent 时调用 `apply_prompt_template()`。

因此，提示词模块虽然主要集中在一个文件里，但它依赖多个子系统共同提供动态片段。

## 5. 主模板为什么采用大块 XML 风格结构

`SYSTEM_PROMPT_TEMPLATE` 不是一段纯自然语言，而是由多个显式标签片段组成，例如：

- `<role>`
- `<thinking_style>`
- `<clarification_system>`
- `<working_directory>`
- `<response_style>`
- `<citations>`
- `<critical_reminders>`

这种写法的好处在于：

- 结构清晰，便于后续插入或裁剪某一块
- 不同系统级约束之间边界分明
- 动态片段更容易按区块插入，而不会把整段 prompt 搅成一团

从工程角度看，这其实是在把系统提示词做成一个“声明式结构文档”，而不是一段无法维护的大字符串。

## 6. 提示词里有哪些静态核心协议

虽然系统提示词是动态拼装的，但它里面有几类内容是相对稳定的基础协议。

### 6.1 角色声明

`<role>` 区块定义当前模型扮演的身份名称。默认是 `lumen`，但在自定义 Agent 模式下会被替换成 Agent 自己的名字。

### 6.2 思考风格约束

`<thinking_style>` 区块规定：

- 先分析任务，再行动
- 不要在思考阶段写最终答案
- 必须在思考后提供真实可见响应

这类约束不是功能性 prompt，而是行为形态 prompt。

### 6.3 澄清优先协议

`<clarification_system>` 是项目里非常关键的一块。它把“什么时候必须调用 `ask_clarification`”写成了一套明确规则，而不是模糊建议。

这说明提示词在这个项目里的作用之一，是定义工具调用的决策前提。

### 6.4 工作目录协议

`<working_directory>` 明确告诉模型：

- 上传目录在哪里
- 工作目录在哪里
- 最终输出目录在哪里
- 文件应如何流转

这块内容非常重要，因为它把路径语义提升成系统级规则，而不是依赖模型自行推测。

### 6.5 输出风格协议

`<response_style>` 和 `<critical_reminders>` 共同决定了模型的默认输出行为，例如：

- 少做无关 meta 说明
- 输出文件时不要泄露原始沙盒路径
- 保持与用户语言一致

这类约束让系统输出风格更稳定。

## 7. 为什么 memory 是动态片段，而不是静态模板内容

memory 的内容显然不能硬编码，因为它依赖：

- 当前是否启用持久化记忆
- 当前 Backend 签发的用户 `memory_scope`
- 当前是默认 Agent 分区还是自定义 Agent 子分区
- 当前记忆文件里到底有什么内容
- 当前允许注入多少 token

静态 graph prompt 不携带 scope，也不能在建图时捕获某个用户的画像。`ScopedMemoryPromptMiddleware` 在每次 model call 时从可信 Runtime context 解析 scope，再调用 `_get_memory_context()`：

- 检查配置是否启用
- 校验 scope，并读取对应 scope/agent 分区
- 将其格式化为注入文本
- 决定是否插入 `<memory>` 区块

这样做的意义在于：

- 没有记忆时不会引入空片段
- 记忆更新后，后续 model call 可以看到新内容
- 同一 graph 实例可服务不同用户而不复用前一个用户的记忆
- guest 和缺少可信 scope 的直接调用不会注入持久记忆
- 自定义 Agent 在每个用户 scope 内拥有独立子分区

## 8. memory 注入为什么要单独做长度裁剪

持久化记忆的数据结构比提示词实际需要的信息多得多。直接把记忆 JSON 原样塞进去既浪费 token，也会让模型关注过多低价值细节。

所以当前实现选择：

- 先把记忆转成适合系统提示词的摘要文本
- 再按 `max_injection_tokens` 控制上限

这说明提示词编排层不仅负责“注入”，还负责“裁剪后再注入”。这种裁剪是 prompt 层的工程优化，而不是记忆模块自己决定一切。

## 9. skills 为什么只注入索引而不是全文

skills 是另一个典型的动态片段。`get_skills_prompt_section()` 的实现不是把所有技能正文拼进 prompt，而是只列出：

- 技能名
- 技能描述
- 技能主文件路径

然后再通过提示词要求模型：

- 若某技能相关，就用 `read_file` 读取该技能文件
- 再按需读取引用的资源

这是一种非常重要的 progressive loading 设计。它能带来两个收益：

- 初始系统提示词体积可控
- 技能系统规模扩大时不会直接拖垮上下文

这说明提示词编排模块在这里扮演的是“目录服务”，而不是“全文广播器”。

## 10. skills 注入与容器路径的关系

skills 片段中暴露给模型的不是宿主机路径，而是容器语义路径，例如 `/mnt/skills/...`。这说明提示词编排层已经和沙盒挂载语义打通了。

如果没有这一步，技能文件即使存在，也只是后端资源，模型无法正确引用。

因此，提示词编排模块在这里不是孤立工作的，它和：

- 技能模块
- 沙盒模块
- 路径配置模块

共同完成了“技能可读性”这件事。

## 11. SOUL 为什么也是动态片段

SOUL 由 `get_agent_soul(agent_name)` 在运行时读取。它之所以不能静态写死，是因为：

- 默认 Agent 与自定义 Agent 的 SOUL 不同
- 某些 Agent 可能根本没有 SOUL 文件
- SOUL 内容可以通过管理接口更新

因此，SOUL 必须是运行时装配项。

从当前实现看，SOUL 被包裹进 `<soul>` 片段，直接参与系统提示词。这说明 SOUL 并不是 UI 信息，而是模型行为约束的一部分。

## 12. 子 Agent 相关提示词为什么是条件注入

当前模板里，子 Agent 相关内容主要来自两部分：

- 一个完整的 `<subagent_system>` 区块
- 若启用子 Agent，则额外插入到 `critical_reminders` 和 `thinking_style` 中的提醒文字

这样设计的好处是：

- 当 `subagent_enabled=False` 时，系统提示词不会被这套复杂规则污染
- 当启用时，模型会得到完整的并发上限、批次拆分和编排原则

这说明提示词编排模块非常明确地在做“能力开关驱动的 prompt 裁剪”，而不是默认把所有能力说明全塞进去。

## 13. 子 Agent 提示词为什么写得这么重

`_build_subagent_section()` 不只是告诉模型“你可以用 task 工具”，而是详细约束：

- 必须先判断能否拆解任务
- 每轮最多调用多少个 `task`
- 超过上限必须分批
- 多批次执行后再综合

这其实不是纯文案风格问题，而是因为项目知道：

- 单靠后端截断超额 `task` 调用不够
- 模型还需要在推理阶段主动做批次规划

所以这里的 prompt 更像一套并发调度协议，而不是能力介绍。

## 14. `apply_prompt_template()` 为什么是整个模块的中心

`apply_prompt_template()` 做的事情不是简单 `.format()`，而是：

- 读取 memory 片段
- 构建子 Agent 片段
- 生成 subagent reminders
- 读取 skills 片段
- 读取 SOUL
- 把这些片段统一填入主模板
- 最后附加当前日期

这意味着它是真正的提示词编排器。只要这些动态来源中任意一项发生变化，下次调用它时，最终系统提示词就会不同。

所以，这个模块从本质上看更像一个 prompt runtime builder。

## 15. 当前日期为什么最后才拼进去

`apply_prompt_template()` 最后附加 `<current_date>` 标签，而不是把日期写在静态模板里。

这个细节很合理，因为日期本质上是最典型的运行时信息：

- 它每次请求都可能不同
- 它不属于配置，也不属于长期上下文

把它放在最后拼接，也说明作者希望主模板保持结构稳定，而把最瞬时的上下文放到末尾作为附加元信息。

## 16. 提示词编排和自定义 Agent 的关系

自定义 Agent 并不是一套新 prompt 模板，而是通过 `apply_prompt_template()` 的参数来影响编排结果。主要影响点包括：

- `agent_name`
- SOUL
- Agent 级长期记忆

这说明自定义 Agent 模块与提示词编排模块之间的关系，不是替换，而是参数化。

从架构角度看，这是一种非常高性价比的做法：

- 保持主模板只有一份
- 通过动态片段产生角色差异

## 17. 提示词编排和中间件链的关系

这个模块不能脱离中间件链理解。很多规则如果只有 prompt 而没有中间件配合，就只是“建议”；而在当前项目里，它们往往是双保险。

最典型的几个例子：

- prompt 规定要用 `ask_clarification`，而 ClarificationMiddleware 真正拦截并终止执行
- prompt 规定技能按需读取，skills 模块和沙盒挂载保证路径真的可读
- prompt 规定子 Agent 并发上限，而 SubagentLimitMiddleware 在后端做硬截断

这说明提示词编排在这个项目里承担的是“声明式协议层”，而中间件链承担的是“执行与补偿层”。

## 18. 这个模块里的几个关键 tricks

如果把提示词编排模块里最值得借鉴的工程技巧提炼出来，主要有以下几点。

### 18.1 静态骨架 + 动态插槽

这样主模板可维护，动态上下文也能按需组合。

### 18.2 只注入索引，不注入全文

skills 和记忆都经过摘要或索引化处理，极大节省上下文。

### 18.3 让 prompt 成为协议层，而不是纯人设层

这个项目的 prompt 不只是“你是谁”，更是“你如何使用工具、如何处理澄清、如何管理文件”的操作协议。

### 18.4 按能力开关裁剪 prompt

subagent 等能力只有启用时才注入，避免普通模式下无意义膨胀。

### 18.5 与路径语义和沙盒语义协同

工作目录和技能路径的说明不是孤立文本，而是和真实文件系统布局严格对应。

## 19. 当前实现的能力边界

从现有代码看，这个模块也有一些明确边界。

- 主要依赖字符串模板和动态片段，没有引入更复杂的 prompt AST
- `USER.md` 虽有管理接口，但当前看不到被真正注入 prompt 的路径
- prompt 模块负责声明规则，不直接保证规则一定被执行

这些边界不是缺陷，而是说明该模块明确把自己定位为“行为协议编排层”，而不是“一切逻辑都在 prompt 中解决”的万能层。

## 20. 这个模块的本质是什么

如果只看表面，lumen 的提示词编排模块像是一份很长的系统提示词字符串。但从实现上看，它真正做的是：

- 把长期记忆、技能、身份、并发规则和文件语义拼成统一系统上下文
- 让不同运行模式共享一套主模板而不丢失灵活性
- 把多模块共同依赖的协议集中表达给模型

所以，这个模块不是“prompt 文案仓库”，而是整个 Agent 运行时的声明式控制面。
