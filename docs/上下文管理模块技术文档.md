# lumen 上下文管理模块技术说明

## 1. 文档目标

本文系统介绍 lumen 中与上下文管理有关的技术实现。重点回答以下问题：

- 一次对话中的上下文到底由哪些部分组成
- 会话是如何被线程化管理和持久化的
- 当上下文逼近或超过模型上下文上限时，系统如何处理
- 为什么这个项目的上下文管理不只是“保存消息历史”
- 项目里有哪些为了稳定性、成本和可恢复性而加入的上下文管理技巧

本文不介绍代码块用法，而是从架构和实现机制出发，说明项目在代码层面如何组织上下文。

### 1.1 先给出五个直接答案

- 一次对话中的上下文由哪些部分组成：不是只有历史消息，还包括工具结果、线程状态字段、系统提示词动态片段、上传文件注入、图片细节注入、长期记忆注入、摘要消息以及工作目录语义。
- 会话如何被线程化管理和持久化：项目以 `thread_id` 为核心，把消息和结构化状态都放进 LangGraph 的 thread state，并通过 checkpointer 决定这些状态是否能跨请求、跨进程、跨重启保留。
- 当上下文逼近或超过模型上限时如何处理：系统不会只靠硬截断，而是结合摘要中间件、记忆分层、动态注入裁剪等机制，把“真正重要的上下文”尽量保留下来。
- 为什么这里的上下文管理不只是保存消息历史：因为模型每轮实际看到的是“原始历史 + 派生信息 + 运行时注入 + 压缩结果”的组合，而不是数据库里原封不动的一串聊天记录。
- 有哪些为了稳定性、成本和可恢复性加入的技巧：代表性做法包括 thread state 结构化建模、checkpointer 持久化、摘要中间件、长期记忆分层、上传与图片信息按需注入，以及把高成本上下文控制逻辑前移到中间件链。

## 2. 核心结论

lumen 的上下文管理不是单一模块，而是一套分层系统。它至少包含三层上下文：

- 短期线程上下文：当前 thread 的消息历史、工具结果、标题、产物、图片状态、沙盒状态等
- 线程派生上下文：上传文件列表、图片细节、会话摘要等，这些内容不是原始消息，但会在运行时注入模型上下文
- 长期跨线程记忆：从历史对话中提炼出的用户背景、偏好、事实与近期关注点

如果把整个系统压缩成一句话，可以这样概括：

lumen 用 LangGraph 的 thread 和 checkpointer 管会话级短期状态，用中间件链动态加工“喂给模型的实际上下文”，用记忆系统承接跨会话长期上下文，并用摘要机制在上下文过长时进行主动压缩。

## 3. 这个项目里的“上下文”到底是什么

在很多简单聊天系统里，“上下文”几乎等于“历史消息列表”。lumen 不是这种模型。

在这个项目中，模型每次调用前真正可见的上下文，来自多种来源的叠加：

- 历史消息
- ToolMessage 工具结果
- 线程状态字段
- 动态拼装的系统提示词
- 上传文件信息注入
- 长期记忆注入
- 图片细节注入
- 摘要中间件压缩后的历史
- 当前线程对应的工作目录语义

因此，这里的上下文管理本质上不是“存聊天记录”，而是“维护一个会随时间变化、会被派生和压缩、还会跨层注入的上下文系统”。

## 4. 从代码结构看，上下文管理分布在哪些模块

与上下文管理最相关的实现主要分布在以下位置：

- `runtimes/backend/langgraph.json`
  定义了主图入口 `lead_agent` 与 checkpointer，决定了 thread 和状态持久化的承载方式。

- `runtimes/backend/src/agents/thread_state.py`
  定义线程状态模式 `ThreadState`，这是会话期短期上下文的结构骨架。

- `runtimes/backend/src/agents/lead_agent/agent.py`
  在这里组装中间件链，并把 `SummarizationMiddleware`、`TitleMiddleware`、`MemoryMiddleware`、`UploadsMiddleware`、`ViewImageMiddleware` 等接入主 Agent 循环。

- `runtimes/backend/src/agents/lead_agent/prompt.py`
  动态拼装系统提示词，包括长期记忆注入、技能注入、工作目录说明和日期注入。

- `runtimes/backend/src/agents/middlewares/*`
  这些中间件构成了上下文加工流水线，负责把“原始线程状态”变成“模型实际看到的上下文”。

- `runtimes/backend/src/config/summarization_config.py`
  定义自动摘要的触发阈值和保留策略，是超长上下文处理的核心配置入口。

- `runtimes/backend/src/agents/memory/*`
  实现长期记忆的过滤、排队、更新与注入。

- `runtimes/backend/src/agents/checkpointer/*`
  实现 LangGraph 会话状态持久化后端，决定线程状态是否能跨进程或跨重启恢复。

- `runtimes/backend/src/agents/middlewares/uploads_middleware.py`
  实现上传文件上下文注入，这部分常被忽视，但它是线程上下文的重要派生层。

- `runtimes/backend/src/agents/middlewares/view_image_middleware.py`
  实现图片细节注入，这会显著影响模型的实际输入内容和 token 占用。

## 5. 会话是如何管理的

### 5.1 会话的基本单位是 thread

lumen 的会话管理不是围绕“浏览器 tab”或“用户连接”展开，而是围绕 LangGraph 的 `thread_id` 展开。

每次运行时，系统都会从运行上下文中读取 `thread_id`。这个标识有三重作用：

- 它是 LangGraph 短期会话状态的主键
- 它是沙盒工作目录与上传目录的命名空间
- 它是记忆更新时的来源标识

也就是说，在这个项目里，“会话”不是一个抽象概念，而是被 `thread_id` 同时绑定到了：

- graph checkpoint
- 文件系统
- 工具执行环境
- 记忆提取来源

### 5.2 短期会话状态由 `ThreadState` 承载

`runtimes/backend/src/agents/thread_state.py` 中定义的 `ThreadState` 是当前会话的短期上下文容器。它不是简单的字典，而是一个有合并规则的状态模式。

里面主要有这些字段：

- `sandbox`
  记录当前线程绑定到哪个沙盒实例

- `thread_data`
  记录当前线程工作区、上传目录和输出目录的真实路径

- `title`
  记录线程标题

- `artifacts`
  记录当前线程已产出的文件路径，带 reducer，会在多轮中增量合并

- `todos`
  在计划模式下维护待办状态

- `uploaded_files`
  记录本轮新上传的文件元数据

- `viewed_images`
  记录已经通过 `view_image` 读取过的图片内容及 MIME 信息

因此，线程上下文不仅是消息，还包括模型执行过程中的结构化状态。

### 5.3 会话持久化依赖 checkpointer

LangGraph 线程状态能否跨请求、跨重启保留，取决于 checkpointer。

在 `runtimes/backend/langgraph.json` 中，主图配置了异步 checkpointer 工厂；在 `runtimes/backend/src/agents/checkpointer/provider.py` 与 `async_provider.py` 中，系统支持三种后端：

- `memory`
  仅进程内有效，进程重启后状态丢失

- `sqlite`
  持久化到本地文件，适合单机服务

- `postgres`
  持久化到 PostgreSQL，适合更正式的部署场景

这意味着会话管理分成两种模式：

- 如果未配置持久化 checkpointer，则 thread 只在当前进程生命周期内有效
- 如果配置了 sqlite 或 postgres，则 thread 状态可以跨进程重启恢复

这个区别非常关键，因为它直接决定了“历史消息和线程状态是否真的可持续”。

### 5.4 标题也是会话状态的一部分

`TitleMiddleware` 会在首轮完整往返之后为线程生成标题，并把标题写回 `ThreadState`。这说明标题不是 UI 层单独维护的元数据，而是会话状态本身的一部分。

从上下文管理角度看，标题有两个作用：

- 给线程一个便于检索的语义摘要
- 作为持久化状态被 checkpointer 一起保存

## 6. 模型每次真正看到的上下文是如何形成的

主 Agent 在每次调用模型之前，并不是直接把 thread 历史原样发送给模型，而是会经过一层运行时加工。

从代码上看，这个加工过程主要由中间件链完成。它的顺序本身就是上下文构造逻辑的一部分。

大体顺序是：

- 线程路径准备
- 上传文件注入
- 沙盒绑定
- 悬空工具消息修补
- 可选会话摘要压缩
- 可选 Todo 状态维护
- 标题生成
- 记忆更新排队
- 可选图片内容注入
- 可选子代理调用数限制
- 澄清拦截

这说明项目采用的不是“消息历史原封不动进入模型”，而是“短期会话状态在进入模型前会被加工、扩充、压缩和修补”。

## 7. 上下文过长时是如何处理的

这是这个模块最核心的问题之一。

### 7.1 唯一明确的主动压缩机制是 `SummarizationMiddleware`

从项目代码来看，系统对“上下文过长”的主动处理主要依赖 LangChain 提供的 `SummarizationMiddleware`，由项目在 `runtimes/backend/src/agents/lead_agent/agent.py` 中按配置决定是否启用。

其接入过程是：

- `AppConfig.from_file()` 读取 `config.yaml`
- 如果存在 `summarization` 配置，则通过 `load_summarization_config_from_dict()` 写入全局摘要配置
- `_create_summarization_middleware()` 读取该配置，并构造真正的 `SummarizationMiddleware`
- `_build_middlewares()` 把它放进主代理中间件链中

因此，超长上下文处理不是一个隐藏特性，而是一个显式可配置的上下文压缩层。

### 7.2 它何时触发摘要

摘要触发条件由 `SummarizationConfig.trigger` 控制，支持三种规格：

- `messages`
  按消息数量触发

- `tokens`
  按 token 数触发

- `fraction`
  按模型最大上下文窗口的比例触发

并且 `trigger` 可以是单个阈值，也可以是多个阈值列表。只要满足任意一个，就触发摘要。

这套设计有一个很实用的工程价值：它不把“上下文长度”锁死在单一指标上。

- 如果团队关心推理链条长度，可以按消息数触发
- 如果团队更关心真实成本和窗口占用，可以按 token 触发
- 如果需要跨不同模型自适应，可以按 fraction 触发

### 7.3 摘要后保留什么

摘要不是把历史全部压成一段文字后就完事，系统还定义了一个 `keep` 策略。

`keep` 同样支持：

- 按消息数保留
- 按 token 数保留
- 按模型窗口比例保留

它的含义是：在压缩历史后，仍然显式保留最近的一部分原始上下文，不把所有内容都抽象成摘要。

这是一个非常重要的 trick。因为如果只保留摘要，不保留最近原始消息，那么模型会失去短期细节敏感性；如果只保留原始消息，不压缩远端历史，那么上下文又会持续膨胀。`keep` 的作用就是在“抽象历史”和“保留近期细节”之间做平衡。

### 7.4 为什么有 `trim_tokens_to_summarize`

摘要本身也要吃上下文。如果历史已经很长，直接把全部历史送给摘要模型本身就会很贵，甚至再次逼近摘要模型的上下文上限。

因此 `SummarizationConfig.trim_tokens_to_summarize` 提供了一个额外保险：

- 在生成摘要前，先把待摘要内容裁到一个可控 token 规模
- 默认值是 4000
- 也可以显式设为 `null` 关闭这一步

这个设计体现了一个典型的工程技巧：对“压缩器”本身也做输入限流，避免为了压缩而再次制造上下文问题。

### 7.5 摘要用什么模型

如果配置里显式提供 `model_name`，摘要会使用指定模型。

如果没有提供，系统会调用 `create_chat_model(thinking_enabled=False)` 构造一个轻量默认模型来执行摘要。这背后的工程考虑很明显：

- 摘要是后台压缩任务，不需要高成本深度思考
- 用轻量模型可以显著降低持续会话的成本
- 摘要本身是服务主循环的辅助手段，不应与主回答模型争抢预算

### 7.6 如果没有启用摘要会怎样

从代码实现看，项目内唯一明确的主动超长缓解机制就是 `SummarizationMiddleware`。如果该配置关闭，项目侧不会再额外插入另一层自动压缩中间件。

这意味着在未启用摘要时：

- 历史会话将继续按原始增长趋势积累
- 上传注入、图片注入、工具结果等派生内容也会继续增加输入体积
- 系统将更依赖模型提供方和底层 runtime 对超长输入的处理能力

换句话说，若你担心上下文窗口被打满，摘要配置不是锦上添花，而是核心防线。

## 8. 除了摘要，系统还有哪些上下文“减噪”手段

项目里并不是只有摘要一种上下文治理机制。还有一组更细粒度的“减噪”和“防污染”技巧。

### 8.1 记忆系统会主动过滤工具过程消息

`MemoryMiddleware` 不会把整段原始消息历史直接喂给记忆更新器。它先过滤掉：

- ToolMessage
- 含有 `tool_calls` 的 AI 中间消息
- 上传文件注入块

只保留：

- 用户真实输入
- 不带 `tool_calls` 的最终 AI 回复

这是一个很重要的 trick。因为工具过程消息往往冗长、低信号，而且强烈依赖当前轮次执行细节。如果把它们写入长期记忆，未来会产生大量噪声。

### 8.2 纯上传轮次不会写入长期记忆

上传文件块是会话级临时资源，不适合进入长期记忆。项目在两个层面做了保护：

- `MemoryMiddleware` 过滤消息时会移除 `<uploaded_files>` 区块
- `MemoryUpdater` 在最终保存前还会再次移除与上传事件相关的描述和事实项

这是一种双保险设计。因为上传文件是非常高频又非常“短期”的上下文，如果不做过滤，长期记忆很快就会被临时文件路径和上传事件污染。

### 8.3 悬空工具调用会被修补

如果一次工具调用中途被取消或中断，历史消息里可能出现一个 AIMessage 发起了 tool call，但没有对应 ToolMessage 的情况。

`DanglingToolCallMiddleware` 会在模型调用前扫描消息历史，如果发现这种“悬空工具调用”，就补一条带错误标记的合成 ToolMessage。

这个技巧虽然看起来不直接与 token 长度相关，但它对上下文稳定性极其关键。因为未修补的消息历史会破坏后续模型对消息结构的理解，甚至导致下一轮直接报错。换句话说，它解决的是“上下文完整性”问题。

### 8.4 澄清会提前截断当前执行

`ClarificationMiddleware` 在发现模型调用 `ask_clarification` 时，不会继续本轮工具循环，而是直接中断 run 并把问题返回给用户。

这也是一种上下文治理技巧。它的作用不是减 token，而是避免在缺失信息的情况下继续膨胀上下文和生成错误轨迹。先中断、后补充、再继续，比“边猜边做再返工”更节省上下文预算。

## 9. 上传文件是如何进入上下文的

### 9.1 上传文件不只是文件系统事件，也是上下文事件

在这个项目里，上传文件不会仅仅保存在磁盘里。`UploadsMiddleware` 会在每次进入 Agent 前检查当前 human message 的 `additional_kwargs.files`，并结合线程上传目录中的历史文件，构建一个 `<uploaded_files>` 区块，然后前置注入到最后一条 human message 中。

这意味着上传文件在模型眼里不是“外部资源列表”，而是本轮上下文的一部分。

### 9.2 为什么既注入新文件又注入历史文件

中间件会同时区分：

- 本轮新上传文件
- 之前消息中上传但仍可用的历史文件

这样做的原因是，线程内的文件上下文是持续性的。用户可能在前几轮上传了 PDF，在这一轮才要求你分析。如果每次只注入本轮新增文件，模型就会丢失线程内已有文件视图。

### 9.3 这是一个很“贵”的上下文层

上传文件块虽然极大提升了可用性，但它也会推高 token 消耗，尤其是文件多、文件名长、历史上传多时。因此它本身就是上下文膨胀源之一。

这也解释了为什么项目需要：

- 过滤纯上传消息不写入长期记忆
- 在必要时启用摘要机制
- 把文件真正内容留在文件系统，通过 `read_file` 延迟读取，而不是把文件内容直接塞进对话历史

这个设计本质上是在做“元数据注入而非内容内联”，这是一个重要的上下文节流技巧。

## 10. 图片上下文是如何管理的

### 10.1 图片不会在一开始就直接进入上下文

用户上传图片并不会自动把图片 base64 直接塞进上下文，这会非常昂贵。项目采用的是显式读取策略：

- 模型先调用 `view_image` 工具
- 工具读取图片，写入 `viewed_images` 状态
- 之后 `ViewImageMiddleware` 在合适时机把图片细节注入到模型上下文中

这意味着图片上下文采用的是“按需延迟注入”。

### 10.2 为什么要等工具全部完成后再注入

`ViewImageMiddleware` 会检查最近一条 assistant 消息里是否包含 `view_image` 工具调用，并确认这些工具调用是否都已经有对应 ToolMessage。

只有在工具结果完整时，它才会注入一条新的 human message，其中包含：

- 图片路径说明
- 图片 MIME 类型
- base64 图像数据

这个技巧能避免模型在工具结果不完整时提前看到半成品图片上下文。

### 10.3 图片上下文的工程权衡

图片注入会显著增加模型输入体积，所以项目只在模型支持视觉能力时才启用 `ViewImageMiddleware`，并且必须由工具显式触发图片读取。

这是一种典型的成本控制设计：能力是可选的，注入是按需的，状态是可追踪的。

## 11. 长期记忆如何和短期会话上下文协同

### 11.1 记忆不是线程状态的一部分

长期记忆并不存储在 LangGraph thread state 里，而是存储在 Backend 签发的用户 scope 下；自定义 Agent 再在该 scope 内使用独立子分区。默认布局为 `{LUMEN_HOME}/memories/{memory_scope}/memory.json` 和 `.../agents/{agent_name}/memory.json`。

这意味着项目明确区分了：

- 线程级短期状态
- 跨线程长期记忆

这种分层很重要，因为短期状态强调过程完整性，长期记忆强调高密度、有用、跨会话的用户画像。

### 11.2 记忆写入是异步防抖的

`MemoryUpdateQueue` 会在会话结束后把需要处理的上下文放进队列，并使用一个可配置的防抖窗口延迟处理。去重键是 `(memory_scope, agent_name, thread_id)`，相同 thread ID 不能跨用户互相替换任务。

这带来几个好处：

- 避免每轮对话都立刻触发一次额外 LLM 调用
- 多轮密集交互时只保留某线程的最新待处理上下文
- 减少频繁更新记忆带来的抖动和成本

这是一个很典型的工程 trick：长期记忆更新不是强一致同步写，而是延迟批处理。

当前队列只存在于 Runtime 进程内，硬崩溃可能丢失尚未处理的派生更新；长期记忆因此不能作为必须一次不丢的业务事实存储。

### 11.3 记忆注入时也会做 token 截断

在 `format_memory_for_injection()` 中，系统会先把记忆组织成结构化文本，再按 `max_injection_tokens` 做 token 预算控制。如果超出预算，会根据 token 比例估算允许保留的字符数并截断。

这说明长期记忆虽然跨会话，但也不能无限制注入。它本身也有严格预算，否则就会反过来吞掉短期上下文空间。

### 11.4 这是一种“抽象层级更高”的上下文

长期记忆保留的不是完整历史，而是提炼后的：

- 工作背景
- 个人偏好
- 近期关注点
- 历史背景

因此它和摘要不同。

- 摘要压缩的是同一线程内的历史
- 记忆抽取的是跨线程、跨时间的用户画像

这两个机制都在减少上下文成本，但作用层次不同。

## 12. 提示词拼装也是上下文管理的一部分

`apply_prompt_template()` 会在每次构造主代理时动态拼装系统提示词，把以下内容组合起来：

- role
- soul
- memory_context
- clarification_system
- skills_section
- subagent_section
- working_directory
- response_style
- citations
- critical_reminders
- current_date

从上下文管理角度看，这意味着系统提示词不是一个固定常量，而是一层“策略性上下文”。

这层上下文有两个重要作用：

- 通过记忆注入和技能注入，把结构化辅助信息送进模型
- 通过工作目录、澄清优先级、子代理约束等规则，约束模型如何使用上下文

所以在这个项目中，系统提示词本身就是上下文治理的一部分，而不是纯说明文字。

## 13. 会话目录和文件系统为什么也是上下文管理的一部分

lumen 把每个线程映射到独立的 `workspace`、`uploads` 和 `outputs` 目录。这个设计不仅服务于沙盒隔离，也服务于上下文管理。

它带来的好处是：

- 线程内资源有天然命名空间
- 文件不需要全部内联到消息历史里
- 模型只需感知路径语义，按需读取文件内容
- 上传文件与产物文件可以在上下文之外长期保留

这实际上是一种很有效的“上下文外置”技巧：

- 把大体量原始材料留在文件系统
- 把必要的索引信息注入模型
- 让模型按需调用工具拉取局部内容

相比把所有资料直接塞进 prompt，这种方式更可扩展，也更省窗口。

## 14. 技术上最值得注意的几个 tricks

### 14.1 用 thread 把消息、状态、文件系统和执行环境绑到一起

很多系统只有消息线程，没有执行线程。lumen 则把 `thread_id` 同时用于：

- LangGraph checkpoint
- 线程目录
- 沙盒环境绑定
- 记忆更新来源

这让“会话”成为跨模块统一主键，极大降低了上下文错位风险。

### 14.2 摘要不是简单 truncate，而是“压缩 + 保留尾部细节”

`keep` 策略让系统不会因为摘要而丢掉最近的原始消息。这个细节非常关键，因为模型最需要的是近期交互细节，而不是远端原样历史。

### 14.3 对长期记忆和会话摘要分别做预算控制

系统既限制摘要输入大小，也限制记忆注入大小。也就是说，它不是只对主消息历史做预算，而是对所有可能膨胀上下文的层次都做预算治理。

### 14.4 上传和图片都采用延迟内容注入

上传文件默认只注入索引元数据，图片默认必须通过工具显式读取后才注入 base64 数据。这是非常典型的“按需加载上下文”思路。

### 14.5 修补悬空工具调用，保证历史结构合法

这不是传统“上下文压缩”技巧，但它是上下文稳定性 trick。消息结构一旦断裂，后续模型调用的上下文语义就会被破坏，因此项目专门用中间件修补这一点。

### 14.6 用澄清中断避免上下文污染

在信息不充分时中断当前 run，而不是继续生成错误轨迹，是一种很有效的上下文保护手段。它避免把错误假设、错误工具调用和返工痕迹堆进线程历史。

## 15. 一次典型请求里，上下文是怎么流动的

可以把一次典型请求的上下文流转理解为九个阶段。

第一阶段，LangGraph 根据 `thread_id` 取回该线程的历史状态和消息。

第二阶段，`ThreadDataMiddleware` 为当前线程准备工作目录、上传目录和输出目录路径。

第三阶段，`UploadsMiddleware` 根据当前消息和线程上传目录，把文件索引前置注入到最后一条 human message。

第四阶段，`SandboxMiddleware` 绑定线程对应的执行环境。

第五阶段，`DanglingToolCallMiddleware` 修补历史中未闭合的工具消息。

第六阶段，如果启用了摘要并达到阈值，`SummarizationMiddleware` 会先压缩历史，再保留最近的一部分原始上下文。

第七阶段，系统提示词会通过 `apply_prompt_template()` 注入长期记忆、技能和工作目录信息。

第八阶段，如果上一轮读取过图片且当前模型支持视觉，`ViewImageMiddleware` 会把图片细节补成一条新的 human message。

第九阶段，模型在这一整套加工后的上下文之上做出下一步推理或工具调用。

这条流转链说明，模型最终看到的上下文是“线程状态 + 动态注入 + 必要压缩 + 规则提示”的综合体，而不是简单历史回放。

## 16. 最终结论

lumen 的上下文管理模块，本质上是一套多层次上下文治理系统，而不是一个单独的“消息存储模块”。

它通过以下组合完成上下文管理：

- 用 LangGraph thread 和 checkpointer 承载短期会话状态
- 用 `ThreadState` 保存结构化线程上下文
- 用中间件链动态加工模型实际可见的上下文
- 用 `SummarizationMiddleware` 在上下文接近上限时主动压缩
- 用上传文件索引和按需图片注入控制上下文膨胀
- 用长期记忆系统承接跨会话信息，并严格做过滤与 token 预算
- 用悬空工具修补和澄清中断保证上下文结构稳定

如果把它和普通聊天系统相比，最大的差别在于：

它不把上下文视为“消息列表”，而是把上下文视为“线程状态、文件系统、工具结果、长期记忆和运行时派生信息的联合体”。也正因为如此，这个项目才能在复杂任务、多轮对话、文件处理和子代理协作场景下保持相对稳定的上下文质量。
