# lumen 子 Agent 模块技术说明

## 1. 文档目标

本文详细介绍 lumen 中的子 Agent 模块。重点不在工具使用示例，而在于说明它的实现逻辑、运行模型、状态流转、并发控制以及一些很关键的工程技巧。

阅读本文后，读者应该能够回答以下问题：

- 子 Agent 在整个系统中扮演什么角色
- 主 Agent 是如何触发子 Agent 的
- 子 Agent 与普通工具调用有什么本质区别
- 子 Agent 的执行状态是如何管理的
- 为什么这个模块采用双线程池和后台任务存储
- 子 Agent 与父 Agent 之间共享和隔离了哪些上下文
- 项目用了哪些 trick 来避免递归失控、上下文污染和执行卡死

### 1.1 先给出七个直接答案

- 子 Agent 在系统中扮演什么角色：它不是替代主 Agent，而是主 Agent 可选的受控委派 worker，用来隔离高噪声执行、并行探索或长任务处理。
- 主 Agent 如何触发子 Agent：不是直接跳图，也不是内部函数调用，而是通过内置 `task` 工具进入子 Agent 执行链。
- 子 Agent 与普通工具的本质区别是什么：普通工具通常执行一个函数后直接返回结果，而 `task` 背后会启动一个完整的二级智能体，并把结果作为工具返回值桥接回主 Agent。
- 子 Agent 的执行状态如何管理：执行器用 `SubagentResult` 记录状态，并通过全局后台任务存储让任务可轮询、可流式观察、可保留中间过程消息。
- 为什么采用双线程池和后台任务存储：因为项目把“调度”和“执行”拆开，避免长任务把任务入口、状态更新和超时管理一起堵死。
- 父子 Agent 共享和隔离了哪些上下文：它们共享同一个线程工作区和文件空间，但隔离思考上下文、任务边界和大部分主链路增强能力。
- 项目用了哪些 trick 避免失控：核心做法包括禁用子 Agent 继续调用 `task`、只挂最小中间件集合、用后台状态对象承接执行过程，以及通过轮询和超时控制避免执行卡死。

## 2. 模块定位

lumen 的主架构是“单主 Agent + 可选子 Agent 委派”。子 Agent 模块的作用，不是替代主 Agent，而是作为主 Agent 的一种扩展执行机制，用来处理那些适合隔离上下文、并行探索或长输出执行的任务。

从职责上看，主 Agent 是 orchestrator，子 Agent 是受控的 delegated worker。但这里的 worker 并不是普通函数，也不是写死逻辑的 executor，而是另一个通过 `create_agent()` 生成的完整智能体。

因此，子 Agent 模块本质上提供的是：

- 一套“受主 Agent 调用”的二级智能体体系
- 一套后台执行与状态跟踪机制
- 一套受控的多智能体并行能力

这让 lumen 不只是一个单智能体系统，而是一个带受控分层委派能力的多智能体运行时。

## 3. 从代码结构看，子 Agent 模块由哪些部分组成

和子 Agent 最相关的实现主要分布在这些位置：

- `backend/src/tools/builtins/task_tool.py`
  这是主 Agent 触发子 Agent 的唯一正式入口。主 Agent 并不是直接调用执行器，而是通过 `task` 工具进入子 Agent 流程。

- `backend/src/subagents/config.py`
  定义 `SubagentConfig`，即子 Agent 的静态配置模型，包括名称、提示词、工具白名单、拒绝名单、模型策略、最大轮数和超时。

- `backend/src/subagents/builtins/*`
  定义内置子 Agent 类型，目前主要有 `general-purpose` 和 `bash` 两种。

- `backend/src/subagents/registry.py`
  提供子 Agent 配置注册表，并负责把 `config.yaml` 中的超时覆盖应用到内置配置上。

- `backend/src/subagents/executor.py`
  这是子 Agent 模块的核心。它负责创建子 Agent、执行任务、后台调度、状态记录、超时控制、消息流式采集和任务清理。

- `backend/src/agents/middlewares/subagent_limit_middleware.py`
  这是对主 Agent 模型输出进行硬限制的中间件，防止一轮响应里生成过多 `task` 调用，导致子 Agent 并发失控。

- `backend/src/tools/tools.py`
  决定什么时候把 `task` 工具加入主 Agent 的工具集合。

- `backend/src/agents/lead_agent/prompt.py`
  在启用子 Agent 时，向主 Agent 注入专门的 orchestrator 提示词，指导模型如何拆解、批次化和综合子任务。

## 4. 子 Agent 不是默认启用，而是运行时可选能力

项目并不是默认总给主 Agent 打开子 Agent 能力，而是通过运行时的 `subagent_enabled` 开关决定是否启用。

从实现上看有两层控制：

- 在工具层，`get_available_tools()` 只有在 `subagent_enabled=True` 时才会把 `task` 工具加入可用工具列表
- 在提示词层，`apply_prompt_template()` 只有在启用时才会注入 `<subagent_system>` 相关提示词和并发批次规则

这意味着子 Agent 不是一个永远存在的底层机制，而是一项按需打开的高级能力。这样做的直接好处是：

- 普通简单对话不会引入额外复杂性
- 未启用时主 Agent 的工具空间更干净
- 可以针对不同渠道或不同任务类型控制是否允许委派

## 5. 子 Agent 的触发入口为什么是 `task` 工具

主 Agent 触发子 Agent，不是通过直接 graph 跳转，也不是内部函数调用，而是通过一个内置工具 `task`。

这意味着从主 Agent 视角看，子 Agent 仍然是一种“工具”。但与普通工具相比，`task` 有两个关键区别：

- 它不会立刻返回单步结果，而是启动一个独立的二级智能体执行链
- 它会在后台持续跟踪这个二级智能体的状态，并最终把结果作为工具结果返回给主 Agent

这个设计有很大的工程价值：

- 主 Agent 不需要知道子 Agent 的实现细节
- 主 Agent 仍然维持统一的“工具调用”心智模型
- 子 Agent 可以自然接入已有的工具调用循环，而不用为主图引入额外的显式节点类型

从架构上讲，这是一种“用工具接口承载多智能体委派”的做法。

## 6. 当前内置了哪几种子 Agent

目前系统内置两种子 Agent。

### 6.1 `general-purpose`

这是通用型子 Agent，适用于复杂、多步骤、既需要探索也需要执行的任务。

它的特点是：

- 默认继承父 Agent 的全部工具
- 但通过拒绝名单禁用 `task`、`ask_clarification` 和 `present_files`
- 默认继承父模型
- 最大轮数默认较高，适合多步探索

它本质上是一个“上下文受限但能力完整”的通用工作代理。

### 6.2 `bash`

这是命令执行型子 Agent，专门处理终端、构建、Git、批量命令等高输出任务。

它的特点是：

- 工具白名单非常窄，只保留沙盒相关工具
- 仍然禁用 `task`、`ask_clarification` 和 `present_files`
- 适合把高噪声命令输出从主上下文中隔离出去

这个设计体现了一个很实用的思路：不是所有子 Agent 都应该是“全能型”，有些子 Agent 更适合作为专门的上下文隔离器。

## 7. 子 Agent 配置模型是怎样设计的

`SubagentConfig` 是一个 dataclass，字段不多，但设计得很实用。

主要包括：

- `name`
  子 Agent 的逻辑名称

- `description`
  告诉主 Agent 在什么场景下应该使用它

- `system_prompt`
  子 Agent 自己的系统提示词

- `tools`
  工具白名单；为 `None` 时表示继承父 Agent 的全部工具

- `disallowed_tools`
  工具拒绝名单，用于在继承基础上进一步剔除危险或不合适的工具

- `model`
  指定模型，或者使用 `"inherit"` 继承父模型

- `max_turns`
  子 Agent 的最大递归轮数

- `timeout_seconds`
  单次子 Agent 执行的时间上限

这个配置模型最大的优点是，它不是绑定某种具体执行器实现，而是从“行为约束”的角度定义子 Agent。这样未来扩展新的子 Agent 类型时，主要是补配置而不是重写框架。

## 8. 子 Agent 配置如何被注册和覆盖

项目采用“内置注册表 + 配置文件覆盖”的方式管理子 Agent。

### 8.1 内置注册表

`backend/src/subagents/builtins/__init__.py` 里有一个 `BUILTIN_SUBAGENTS` 字典，把子 Agent 名称映射到内置配置。

这意味着内置子 Agent 不是从磁盘动态扫描出来的，而是明确注册的。好处是：

- 可预测
- 可测试
- 配置变更不会破坏内置集合结构

### 8.2 配置文件覆盖

`backend/src/config/subagents_config.py` 支持在 `config.yaml` 中为子 Agent 系统配置默认超时，也支持对单个子 Agent 做超时覆盖。

`registry.get_subagent_config()` 在读取内置配置后，会再应用这些覆盖项。这里最值得注意的点是：它会返回一个覆盖后的副本，而不是直接修改内置对象本身。

这个 trick 很重要，因为它避免了全局配置对象被原地篡改，进而导致跨测试或跨请求状态污染。

## 9. 子 Agent 的真正核心是执行器，而不是 `task` 工具

`task` 工具只是入口，真正把任务变成一个后台运行智能体的是 `SubagentExecutor`。

执行器承担了几类职责：

- 根据配置和父上下文创建子 Agent
- 构造子 Agent 初始状态
- 运行子 Agent 的异步执行逻辑
- 实时收集 AIMessage
- 把结果写入后台任务存储
- 处理超时、失败和清理

所以，整个子 Agent 模块真正的核心不是“有个 task 工具”，而是“有个能把 Agent 当后台任务管理的执行器”。

## 10. 子 Agent 本身也是通过 `create_agent()` 创建的

这是理解这个模块时最关键的一点。

子 Agent 不是手写循环，不是 if-else 任务器，也不是某个预定义脚本集合。`SubagentExecutor._create_agent()` 会再次调用 `create_agent()` 构造一个新的 agent 实例。

这意味着子 Agent 从本质上看，仍然是一个完整的工具调用智能体。只是它与主 Agent 相比有几个收缩：

- 系统提示词更聚焦
- 工具集合更受限
- 不负责直接面向最终用户
- 一般不允许继续委派子 Agent
- 默认关闭 thinking 增强

因此，lumen 的子 Agent 模块不是“主 Agent 调普通 worker”，而是“主 Agent 调受控的次级 Agent”。

## 11. 父 Agent 的哪些上下文会传给子 Agent

子 Agent 不是从零开始，它会继承父 Agent 的一部分执行上下文。

主要包括：

- `sandbox_state`
  也就是当前线程绑定的沙盒环境

- `thread_data`
  当前线程工作区、上传目录和输出目录路径

- `thread_id`
  用于工具访问线程级资源

- `parent_model`
  用于 `"inherit"` 模式解析最终模型

- `trace_id`
  用于父子链路日志追踪

这些内容会通过 `SubagentExecutor._build_initial_state()` 和执行配置一起传入子 Agent。

这意味着父子关系不是纯文本委派，而是带执行环境继承的委派。这样做的好处是：

- 子 Agent 能看到同一个线程工作区
- 主 Agent 下载的文件、创建的中间结果对子 Agent 可见
- 子 Agent 生成的内容也自然落回同一个线程空间

这是一个很重要的 trick：父子 Agent 隔离的是“思考上下文”和“任务边界”，而不是完全隔离执行环境。

## 12. 子 Agent 也会挂中间件，但只挂最小集合

子 Agent 创建时并不会复用主 Agent 的完整中间件链，而是只挂载最小必需集合：

- `ThreadDataMiddleware`
- `SandboxMiddleware`

而且这两个中间件都采用懒初始化模式。

这背后体现了一种很稳的工程取舍：

- 子 Agent 仍然遵循和主 Agent 一样的基础运行协议
- 但不额外挂上标题生成、记忆更新、图片注入、澄清中断等主链路增强

这样既保证了工具和沙盒行为一致，又避免子 Agent 执行链被主链路的所有附加能力拖重。

## 13. 为什么子 Agent 默认不允许继续调用 `task`

无论是 `general-purpose` 还是 `bash`，它们的工具限制都明确禁用了 `task`。

这是整个模块里最关键的防爆炸设计之一。因为如果子 Agent 默认还能继续派生子 Agent，就会带来几个风险：

- 无界递归委派
- 并发数失控
- 背景任务状态难以追踪
- 主 Agent 对整体工作图失去控制

项目通过工具拒绝名单直接切断了这条路径。也就是说，当前的多智能体形态是“单层扇出”，而不是“任意层级的 agent society”。

这是一个非常务实的设计：先把一层委派做好，再避免递归复杂性。

## 14. 子 Agent 的执行状态是如何表示的

执行器用 `SubagentResult` 表示后台任务状态，它包含：

- `task_id`
- `trace_id`
- `status`
- `result`
- `error`
- `started_at`
- `completed_at`
- `ai_messages`

其中最有价值的是 `ai_messages`。项目不会只记录最终结果，还会持续收集子 Agent 在执行过程中生成的 AI 消息。

这带来了两个好处：

- 前端或调用方可以实时看到子 Agent 的中间进展
- 即使最终失败，也能保留过程轨迹，便于调试和解释

这说明子 Agent 模块不是一个黑盒异步任务器，而是一个带过程可观测性的执行框架。

## 15. 为什么要有全局后台任务存储

执行器内部维护了一个全局 `_background_tasks` 字典，用 `task_id` 映射到当前 `SubagentResult`。

这个设计的意义是把子 Agent 执行状态从调用栈里剥离出来，变成可轮询、可流式观察、可在不同阶段访问的后台任务对象。

如果没有这层存储，`task` 工具就只能同步阻塞到最终结果，无法做到：

- 中间状态流式回传
- 跨轮询周期查看状态
- 在超时或失败时保留部分过程信息

因此，全局后台任务存储是“子 Agent 作为后台智能任务”这一模型成立的前提。

## 16. 为什么采用双线程池，而不是一个线程池搞定

这是这个模块最有意思的工程细节之一。

执行器内部维护了两个线程池：

- 调度线程池 `_scheduler_pool`
- 执行线程池 `_execution_pool`

两者职责不同。

调度线程池负责：

- 创建后台任务入口
- 更新任务状态
- 把真正执行提交给执行线程池
- 管理超时等待

执行线程池负责：

- 运行子 Agent 的实际执行逻辑

这种拆分的好处是：

- 调度逻辑不会被长时间执行任务占满
- 可以更稳定地做超时管理和状态更新
- 避免“调度线程自己阻塞在执行逻辑上”导致整个任务系统可用性下降

换句话说，项目不是把线程池当成简单的“并发容器”，而是明确区分了 orchestration 和 execution 两类工作。

## 17. 为什么执行器内部要再创建事件循环

`SubagentExecutor.execute()` 里会用 `asyncio.run()` 包裹实际异步执行逻辑。

这样做的原因很直接：

- 子 Agent 可能会使用只支持异步的工具，例如部分 MCP 工具
- 子 Agent 运行在线程池线程中，而这些线程默认没有事件循环

所以执行器不能简单在工作线程里直接调用异步逻辑，而是必须在该线程内显式创建并运行一个新的事件循环。

这是一个很重要的兼容性 trick。没有这一层，很多异步工具在子 Agent 中会直接失效。

## 18. 子 Agent 的状态流转是怎样的

一个任务通常会经历这些状态：

- `PENDING`
  已创建后台任务，但尚未真正开始执行

- `RUNNING`
  已进入执行阶段

- `COMPLETED`
  成功拿到最终结果

- `FAILED`
  执行过程中出现异常

- `TIMED_OUT`
  超过超时限制

值得注意的是，这不是纯理论状态机，而是有精确实现落点的：

- `execute_async()` 先创建 `PENDING`
- 调度线程开始工作时切到 `RUNNING`
- 执行线程正常返回后写成 `COMPLETED`
- 捕获异常则写成 `FAILED`
- 超时等待触发则写成 `TIMED_OUT`

这个明确状态机使得前端流式展示和后续清理逻辑都更简单。

## 19. `task` 工具如何与后台执行器协同

`task` 工具本身并不只是“启动后台任务然后立即返回 task_id”。它实际上做了三件事：

- 启动后台执行
- 循环轮询后台任务结果
- 通过 stream writer 持续向外发出事件

它会发送的事件类型包括：

- `task_started`
- `task_running`
- `task_completed`
- `task_failed`
- `task_timed_out`

这说明 `task` 工具的设计目标不是给 LLM 一个“任务句柄”，而是把一个后台智能体执行过程包装成“可观测、可等待、最终可综合”的工具调用。

这也是为什么主 Agent 使用 `task` 时，虽然底层是后台执行，但上层仍可获得最终同步结果。

## 20. 为什么说它是“异步执行，同步消费”

从系统角度看，子 Agent 是异步执行的：

- 进入后台线程池
- 独立运行
- 过程状态持续更新

但从主 Agent 视角看，`task` 工具会一直轮询，直到拿到终态再返回。因此主 Agent 的体验更像是一个同步工具调用，只不过这个工具背后是一个完整后台任务。

这个设计的价值在于：

- 后端可以获得异步执行和过程可观测性
- 主 Agent 不需要显式学习任务句柄管理和二次轮询协议
- 对模型来说，`task` 仍然符合“调用工具然后等结果”的自然模式

这是一种非常实用的桥接设计。

## 21. 超时机制为什么做了双保险

子 Agent 的超时控制不是单层的，而是双保险：

第一层是执行线程池等待超时。

调度线程在等待执行线程结果时，会调用带 timeout 的 `future.result(timeout=...)`。超时后任务会被标记为 `TIMED_OUT`。

第二层是 `task` 工具侧的轮询超时保护。

它会根据 `timeout_seconds` 推导一个轮询次数上限，公式里还额外加了 60 秒缓冲。这样即使底层线程池超时机制因为某些边缘情况没有及时生效，工具侧仍然不会无限等待。

这是一个很典型的工程 trick：对长任务使用双层超时保护，避免单点超时失效造成悬挂。

## 22. 为什么要额外加一层并发限制中间件

主 Agent 的系统提示词已经明确告诉模型每轮最多发起多少个 `task` 调用，但项目仍然增加了 `SubagentLimitMiddleware` 做硬限制。

原因很简单：提示词约束永远不是安全边界。

`SubagentLimitMiddleware` 会在模型输出后检查最后一条 AIMessage 中的 `tool_calls`，如果 `task` 调用数超过上限，就只保留前若干个，其余直接截断。

这体现了一个非常成熟的设计思路：

- 提示词负责引导
- 中间件负责兜底

也就是典型的“软约束 + 硬约束”双层治理。

## 23. 为什么子 Agent 模块对上下文污染更友好

子 Agent 最大的价值之一，不只是并行，而是上下文隔离。

把复杂探索、长命令输出或大段中间推理放在子 Agent 里，有几个直接收益：

- 主 Agent 上下文不会被大量命令输出淹没
- 主 Agent 不需要记录所有探索分支的详细过程
- 主 Agent 最终只拿到结构化的任务结果摘要
- 复杂任务的局部上下文被封装在子 Agent 内部

因此，子 Agent 模块可以理解为一种“上下文压舱石”。它不是直接减少工作量，而是把高噪声执行过程隔离在次级上下文中，保护主 Agent 的工作记忆质量。

## 24. 几个很值得注意的工程 tricks

### 24.1 用配置覆盖返回副本，避免污染内置注册表

子 Agent 注册表在应用 timeout 覆盖时会返回替换后的配置副本，而不是修改内置配置对象本身。这能有效避免全局状态污染。

### 24.2 用最小中间件集合复用父环境

子 Agent 既没有脱离主架构运行协议，又避免把主链路所有增强都背过来。这让它在复用能力和控制复杂性之间取得了平衡。

### 24.3 禁止 `task` 嵌套调用，主动砍掉递归树

这不是能力缺失，而是系统设计上的主动收缩。它让整个多智能体拓扑维持在可控的一层扇出结构。

### 24.4 采集中间 AI 消息，而不仅仅保留最终结果

这让任务具备过程可观测性，也让流式事件输出更有价值。

### 24.5 异步执行、同步消费，兼顾工程和模型心智

对后端来说是后台任务，对主 Agent 来说仍然像普通工具调用，这个桥接非常自然。

### 24.6 调度池和执行池分离

这降低了长任务拖垮整个调度层的风险，是长期运行服务中非常关键的一点。

### 24.7 双超时保护

线程池等待超时和轮询兜底超时同时存在，避免悬挂任务吞掉系统资源。

## 25. 一次典型子 Agent 调用是怎么流动的

一条典型链路大致如下。

第一步，主 Agent 在思考后决定调用 `task` 工具。

第二步，`task_tool` 根据 `subagent_type` 从注册表中取出配置，并叠加：

- 技能提示词片段
- 调用时覆盖的 `max_turns`
- `config.yaml` 中的 timeout 配置

第三步，`task_tool` 从父运行时提取：

- 沙盒状态
- 线程目录状态
- `thread_id`
- 父模型名
- `trace_id`

第四步，创建 `SubagentExecutor`，并为它准备过滤后的工具集合。

第五步，执行器创建后台任务记录，状态设为 `PENDING`，然后把调度逻辑提交到调度线程池。

第六步，调度线程把状态改为 `RUNNING`，再把真正执行逻辑提交给执行线程池。

第七步，执行线程在新事件循环中运行子 Agent，期间不断把新 AIMessage 追加到 `ai_messages`。

第八步，`task_tool` 在外层轮询后台任务状态，并把 `task_running` 等事件通过 stream writer 往外发。

第九步，任务完成、失败或超时后，`task_tool` 返回最终结果文本，并清理终态后台任务。

这条链路说明，子 Agent 模块不是单个类的功能，而是“工具入口 + 配置注册表 + 执行器 + 后台状态机 + 流式事件桥接”共同组成的完整子系统。

## 26. 最终结论

lumen 的子 Agent 模块，本质上是一个“受控分层多智能体执行系统”。它不是简单的任务函数封装，也不是完全自由递归的智能体社会，而是在单主 Agent 架构中提供了一层可观测、可并行、可隔离上下文的二级智能体能力。

它的实现有几个核心特点：

- 通过 `task` 工具把子 Agent 纳入主 Agent 的工具调用语义
- 通过 `SubagentExecutor` 把子 Agent 作为后台智能任务执行
- 通过状态机和全局任务存储管理生命周期
- 通过双线程池分离调度与执行
- 通过继承沙盒和线程上下文实现父子环境协作
- 通过禁用嵌套委派、硬限制并发和双层超时保护维持系统可控

如果把主 Agent 看作 orchestrator，那么子 Agent 模块做的事情就是：在不破坏主循环心智模型的前提下，为主 Agent 增加一套真正可落地的“受控委派执行能力”。这也是 lumen 从单智能体助手进一步走向 super agent runtime 的关键部件之一。
