# lumen 持久化记忆模块技术说明

## 1. 文档目标

本文详细介绍 lumen 中的持久化记忆模块。重点不是泛泛而谈“模型有长期记忆”，而是解释这个项目在代码层面如何实现一套可落盘、可注入、可防污染、可按 Agent 隔离的长期记忆机制。

阅读本文后，读者应能够回答以下问题：

- 这个项目里的“记忆”与线程上下文有什么边界
- 记忆数据存在哪里，数据结构是什么
- 记忆更新为什么不是同步立即写盘，而是走过滤、排队和防抖
- 记忆更新到底由谁完成，是规则逻辑还是 LLM
- 为什么上传文件、工具中间步骤等内容不会进入长期记忆
- 全局记忆和自定义 Agent 记忆是如何隔离的

### 1.1 先给出六个直接答案

为了方便读者快速建立全局认识，先把文档开头这六个问题直接回答掉，后文再展开到具体代码位置。

#### 1.1.1 这个项目里的“记忆”与线程上下文有什么边界

边界非常清晰：

- 线程上下文是当前会话的运行态，主要存在于 LangGraph 的 thread state、消息历史和工具执行过程里
- 持久化记忆是跨会话、跨线程、跨重启仍然存在的长期画像，存放在独立 `memory.json` 文件中

所以这个模块不是把 thread 历史“存久一点”，而是把历史里真正值得保留的高价值信息提炼成另一层长期状态。线程里会出现大量临时执行细节，而长期记忆只保留未来仍然有用的稳定背景、偏好、目标和事实。

#### 1.1.2 记忆数据存在哪里，数据结构是什么

默认情况下，全局记忆落在 `{base_dir}/memory.json`；若是自定义 Agent 记忆，则落在 `{base_dir}/agents/{agent_name}/memory.json`。如果配置了 `memory.storage_path`，全局记忆可以改写到指定路径，但 Agent 级记忆仍然优先使用各自目录下的独立文件。

记忆本体是结构化 JSON，而不是一段纯文本。顶层结构包含：

- `version`
- `lastUpdated`
- `user`
- `history`
- `facts`

其中：

- `user` 下有 `workContext`、`personalContext`、`topOfMind`
- `history` 下有 `recentMonths`、`earlierContext`、`longTermBackground`
- `facts` 是离散事实列表，每条包含 `id`、`content`、`category`、`confidence`、`createdAt`、`source`

这意味着系统用的是“摘要分区 + 离散事实”双轨结构，而不是把长期记忆全部塞成一段自由摘要。

#### 1.1.3 记忆更新为什么不是同步立即写盘，而是走过滤、排队和防抖

因为同步立即写盘会把长期记忆更新放到用户请求主路径上，直接带来三个问题：

- 每轮对话都同步调 LLM，会增加用户等待时间
- 高频连续追问会重复触发总结，浪费 token 和模型调用
- 同一线程里还没沉淀稳定的信息就被反复写盘，长期记忆很容易碎片化

所以当前实现把它拆成了三步：

- 先过滤，只保留适合进入长期记忆的会话内容
- 再入队，由 `MemoryUpdateQueue` 按线程去重并等待 `debounce_seconds`
- 最后在异步阶段统一调用 `MemoryUpdater` 做摘要、合并和写盘

本质上，这是一种“阶段性整合”策略，而不是“每轮立刻落盘”策略。

#### 1.1.4 记忆更新到底由谁完成，是规则逻辑还是 LLM

答案是混合架构，但职责分工非常明确：

- 规则逻辑负责边界控制：过滤哪些消息能参与更新、何时入队、如何防抖、如何按 `agent_name` 选文件、如何执行置信度阈值、事实上限、原子写盘和上传痕迹清理
- LLM 负责语义理解：阅读“当前记忆 + 新对话”，输出结构化 JSON 增量，决定哪些摘要分区该更新、哪些新事实值得添加、哪些旧事实应删除

所以不是“纯规则”也不是“完全交给模型”。准确说法是：

规则逻辑负责流程与护栏，LLM 负责抽取与归纳，最终写盘仍由本地程序受控完成。

#### 1.1.5 为什么上传文件、工具中间步骤等内容不会进入长期记忆

因为这些内容天然是会话级、线程级、执行级噪声，不具备长期稳定性。

- 工具中间步骤会被 `MemoryMiddleware` 过滤掉，包括 `ToolMessage` 和带 `tool_calls` 的 AI 中间消息
- 用户消息里的 `<uploaded_files>` 区块会在进入记忆管线前被剥离
- 如果一轮消息除了上传区块外没有真实用户问题，那么这条 human 消息和它配对的 assistant 回复会一起被丢弃
- 即便前面漏掉了某些上传痕迹，`MemoryUpdater` 在写盘前还会再做一次 `_strip_upload_mentions_from_memory()` 清洗

这样做是为了避免把临时文件路径、临时工具输出或中间推理痕迹写成长期画像，防止后续会话反复引用已经失效的资源。

#### 1.1.6 全局记忆和自定义 Agent 记忆是如何隔离的

隔离不是只发生在文件路径这一层，而是贯穿整条记忆链路。

当没有传入 `agent_name` 时，系统读写的是全局 `memory.json`。当传入 `agent_name` 时：

- `MemoryMiddleware(agent_name=...)` 会把这个作用域附带进更新队列
- `MemoryUpdateQueue` 会把 `agent_name` 和会话上下文一起保存
- `MemoryUpdater` 会按同一个 `agent_name` 读取和写回对应的记忆文件
- 记忆缓存 `_memory_cache` 也是按 `agent_name` 分桶的
- 主 Agent 在系统提示词里注入记忆时，也会按相同 `agent_name` 读取对应记忆

因此，自定义 Agent 不只是“目录不同”，而是从更新、缓存、持久化到提示词注入全链路都使用自己的记忆作用域，不会和全局记忆或其他 Agent 的记忆混用。

## 2. 模块定位

lumen 的持久化记忆模块，不是短期对话历史的替代品，而是一个独立于线程状态之外的长期用户画像层。

它主要解决的是以下问题：

- 同一个用户跨多轮、跨线程甚至跨重启后，系统还能保留稳定背景信息
- 模型后续对话时能获得长期偏好、历史工作脉络和高价值事实
- 这些长期信息不会被单轮会话里的临时噪声污染

因此，这个模块和 thread 上下文的职责边界非常明确：

- 线程状态负责当前会话的短期执行上下文
- 持久化记忆负责跨会话的长期稳定信息

如果把它压缩成一句话，可以这样概括：

lumen 的持久化记忆，是一套“异步 LLM 摘要 + 结构化 JSON 存储 + 系统提示词注入”的长期用户画像系统。

## 3. 代码分层与关键入口

持久化记忆相关实现主要分布在以下位置：

- `backend/src/config/memory_config.py`
  负责记忆系统配置，包括是否启用、存储路径、防抖时间、事实上限和注入策略。

- `backend/src/agents/middlewares/memory_middleware.py`
  负责在每轮 Agent 执行后过滤消息并把记忆更新任务送入队列。

- `backend/src/agents/memory/queue.py`
  负责记忆更新任务的防抖、按线程去重和异步批处理。

- `backend/src/agents/memory/updater.py`
  负责读取、缓存、更新和持久化保存记忆文件，是整个模块的核心执行层。

- `backend/src/agents/memory/prompt.py`
  负责两件事：一是定义“如何让 LLM 生成记忆增量”的更新提示词，二是把已有记忆格式化成系统提示词注入文本。

- `backend/src/agents/lead_agent/prompt.py`
  负责把记忆注入主 Agent 的系统提示词。

- `backend/src/gateway/routers/memory.py`
  提供查询、重载和状态读取接口。

从架构上看，这不是一个单文件模块，而是一条完整的数据流。

## 4. 持久化记忆和上下文管理的边界

很多系统会把“历史消息”直接当作长期记忆，但这个项目明显不是这样做的。

在 lumen 里，长期记忆和短期上下文被刻意分开：

- 短期上下文存在于 LangGraph thread 状态和消息历史中
- 长期记忆存在于独立 JSON 文件中

这意味着一个信息只有经过记忆管线加工后，才会被提升为“长期记忆”。这种分层有几个直接好处：

- 长期记忆可以跨线程共享，而不依赖某个 thread 的 checkpoint
- 线程里的临时行为不会自动污染长期画像
- 记忆注入可以按 token 上限进行专门裁剪，而不是被动吃下整段历史

也就是说，这个模块不是“把历史存得更久”，而是“把历史中的高价值部分抽成另一层状态”。

## 5. 数据是如何持久化存储的

### 5.1 全局记忆文件与 Agent 级记忆文件

记忆文件路径由 `_get_memory_file_path()` 决定。它支持两种模式：

- 全局记忆
- 按 Agent 隔离的记忆

当没有传入 `agent_name` 时，系统使用全局记忆文件。这个文件默认位于基础目录下的 `memory.json`。

当传入 `agent_name` 时，系统会改用对应 Agent 目录下的 `memory.json`，也就是每个自定义 Agent 可以拥有独立长期记忆。

这说明项目的记忆体系不是单一的全局画像，而是支持：

- 一个共享的默认长期记忆
- 多个自定义 Agent 各自隔离的长期记忆

这种设计很适合“一个用户拥有多个不同人格或用途 Agent”的场景。

### 5.2 路径解析的优先级

全局记忆文件的路径解析顺序也有明确规则：

- 如果配置了 `storage_path`，优先使用它
- 若该路径是绝对路径，则直接使用
- 若是相对路径，则相对于 `Paths.base_dir` 解析
- 若未配置，则回落到默认的 `{base_dir}/memory.json`

这里的关键点是，相对路径不是相对于 backend 当前工作目录，而是相对于统一的 base_dir。这样做可以避免不同启动位置导致记忆文件落盘位置漂移。

### 5.3 数据结构为什么是 JSON 而不是数据库

当前实现将记忆保存为 JSON 文件，而不是数据库表。其优势很明显：

- 结构清晰，便于调试和人工查看
- 单机部署成本低
- 读写逻辑简单，适合当前“低频更新、高价值读取”的使用模式

从工程取舍看，这个模块优先追求的是易理解、易维护和本地可用性，而不是大规模分布式存储能力。

## 6. 记忆数据的内部结构

### 6.1 三大区域：版本、上下文分区、事实列表

空记忆结构由 `_create_empty_memory()` 定义，主要包含：

- `version`
- `lastUpdated`
- `user`
- `history`
- `facts`

这说明系统不是把长期记忆存成一段自由文本，而是把它拆成多个结构化分区。

### 6.2 `user` 分区的设计意图

`user` 下包含三个子分区：

- `workContext`
- `personalContext`
- `topOfMind`

它们分别对应：

- 相对稳定的工作背景与技术环境
- 个人偏好、语言、沟通习惯、兴趣等
- 当前近期最关注的事情

这个切法很有意思，因为它把“用户是谁”和“用户最近在想什么”分开了。后者更新频率更高，更接近动态工作集，而前者更像背景画像。

### 6.3 `history` 分区的设计意图

`history` 下包含：

- `recentMonths`
- `earlierContext`
- `longTermBackground`

它不是按精确时间线存原始事件，而是按时间粒度分层保留摘要。这意味着系统并不试图实现一份完整事件日志，而是更接近“分时间桶的长期摘要”。

这样设计的好处是：

- 便于控制注入长度
- 便于 LLM 在更新时用不同粒度整合新旧信息
- 比无限累加事件更不容易失控

### 6.4 `facts` 列表的角色

除了摘要型分区，系统还维护一个事实列表。每条事实都有：

- 唯一 ID
- 内容
- 类别
- 置信度
- 创建时间
- 来源线程

这说明 facts 更像是“高价值离散事实存储”，适合保留：

- 明确偏好
- 技术能力
- 项目背景
- 目标与行为模式

而大段叙述和时间脉络则交给 `user` 与 `history` 摘要分区。

换句话说，这个模块实际上用了“摘要 + 离散事实”双轨记忆结构。

## 7. 读取与缓存策略

### 7.1 不是每次都读磁盘

`get_memory_data()` 内部维护了一个按 `agent_name` 维度区分的内存缓存。缓存内容包括：

- 当前记忆数据
- 该文件上次读取时的 mtime

这样做的目的是避免每次提示词注入或 API 查询都重新打开磁盘文件。

### 7.2 缓存不是永久有效，而是基于 mtime 失效

当调用 `get_memory_data()` 时，系统会读取当前文件的修改时间，并与缓存里的 mtime 对比。若文件已被外部修改，缓存会自动失效并重载。

这说明这个模块采用的是“带文件版本感知的轻量缓存”，而不是简单单例缓存。

这种策略很适合当前架构，因为：

- 记忆文件可能被外部接口或运维手工修改
- 读取路径很固定，mtime 检测成本低
- 不需要更复杂的通知机制

### 7.3 强制重载入口

除了自动失效，系统还提供 `reload_memory_data()` 强制重读并刷新缓存。这使得：

- Gateway 接口可以显式重载
- 调试和外部脚本修改后可以立即刷新

这也是一个很务实的设计。

## 8. 记忆更新为什么不是同步立即发生

这是这个模块最关键的设计点之一。

如果每次对话结束都同步调用 LLM 更新记忆并立即写盘，会带来几个问题：

- 响应路径变长，影响用户等待时间
- 高频多轮对话会反复触发记忆更新，浪费 token
- 同一线程连续追问时，记忆会被过度细碎地重写

lumen 的解决方式是：

- 在 `after_agent` 阶段只负责把更新请求送入队列
- 由队列做防抖和批处理
- 真正的记忆更新在异步延后阶段完成

这说明持久化记忆被设计成“后处理型系统”，而不是同步主路径逻辑。

## 9. `MemoryMiddleware` 的作用

### 9.1 它只在执行后触发

`MemoryMiddleware` 挂在 `after_agent` 上，而不是 `before_model`。这很合理，因为记忆更新的输入应该是“这一轮真实发生过的对话结果”，而不是模型调用前的状态。

### 9.2 它不直接写状态，只做投递

这个中间件本身不会修改线程状态，也不会立刻写文件。它只做以下几步：

- 检查记忆功能是否启用
- 从运行时上下文取出 `thread_id`
- 从状态中取出消息列表
- 过滤掉不适合进入长期记忆的消息
- 验证过滤后至少有一条用户消息和一条 assistant 消息
- 把结果送进记忆更新队列

这说明它在整个记忆系统里的角色是“采样器 + 投递器”，而不是“更新器”。

### 9.3 为什么要求至少有用户和助手各一条消息

这个判断很重要，因为长期记忆更新必须建立在完整的一轮交互之上。如果只有用户消息没有最终回复，或只有系统噪声而没有真正对话，就不值得更新长期记忆。

这也是模块避免噪声更新的一道前置门槛。

## 10. 为什么要过滤消息再送入记忆

记忆系统最大的风险不是“记不住”，而是“记错了不该记的东西”。项目在进入记忆队列前就做了一次非常关键的过滤。

### 10.1 工具中间步骤不会进入长期记忆

过滤逻辑会移除：

- ToolMessage
- 带 `tool_calls` 的 AIMessage

这意味着系统不会把中间工具执行轨迹写进长期记忆，只保留对用户真正可见的自然对话结果。

这是非常关键的，因为工具中间步骤常常包含：

- 临时命令输出
- 中间推理痕迹
- 与用户画像无关的执行噪声

### 10.2 上传文件区块不会进入长期记忆

用户消息里如果包含 `<uploaded_files>` 区块，过滤器会先把这段内容剥掉。若剥掉后整条 human 消息为空，则连同其配对 assistant 回复一起丢弃。

这个逻辑解决的是一个非常现实的问题：上传文件路径是会话级、线程级资源，不应该被长期记住。否则后续会话中，模型可能反复提到已失效的上传文件路径，造成严重混淆。

### 10.3 多模态内容也被保守处理

如果 human 消息 content 是列表形式，过滤器会尽量提取其中的文本部分，再继续走上传过滤流程。这说明实现者已经考虑到多模态消息形态，不是假设消息永远是纯字符串。

## 11. 防抖队列的设计逻辑

### 11.1 队列是按线程去重的

`MemoryUpdateQueue.add()` 在入队时会先移除同一 `thread_id` 已存在的待处理任务，再加入最新一条。

这意味着对于同一线程，队列始终只保留“最新版本”的上下文，而不是简单累积所有更新请求。

这个策略特别适合聊天场景，因为连续几轮追问往往是对同一主题的延续。与其把每轮都分别写进长期记忆，不如等用户暂时停下来，再用最后一轮上下文做一次更完整的更新。

### 11.2 防抖不是装饰性优化，而是核心稳定机制

每次入队后，系统都会重置一个定时器。只有在指定 `debounce_seconds` 内没有新的同线程更新到达时，队列才会真正开始处理。

这个机制的意义有三层：

- 降低频繁 LLM 调用成本
- 给同一话题留出合并窗口
- 避免长期记忆在高频交互中被反复重写

所以这个模块的长期记忆更新节奏，不是“每轮一次”，而是“用户阶段性停顿后一次”。

### 11.3 批处理时还有额外的小延迟

当同一轮需要处理多个排队上下文时，队列会在任务之间加入短暂延迟。这个技巧虽然简单，但可以降低连续调用记忆模型时触发限流的概率。

这类细节很能体现出作者是在按生产环境去思考，而不是只追求代码逻辑跑通。

## 12. `MemoryUpdater` 的核心工作流

`MemoryUpdater` 是整个模块的真正执行引擎。它的工作可以拆成七步。

第一步，读取当前记忆文件内容。

第二步，把过滤后的对话消息格式化成用于更新的对话文本。

第三步，将当前记忆和新对话一起填入记忆更新提示词。

第四步，调用一个关闭 thinking 的模型生成 JSON 格式的增量更新结果。

第五步，解析 LLM 返回的 JSON。

第六步，把增量更新应用到当前记忆对象。

第七步，清理不该保留的上传痕迹，随后原子写回磁盘。

这说明系统采用的不是规则引擎式更新，而是“LLM 产出结构化增量，再由本地逻辑受控应用”的混合架构。

## 13. 记忆更新为什么用 LLM，而不是规则提取

从实现上可以看出，作者显然不想把长期记忆退化成一套关键词匹配器。使用 LLM 更新的原因主要有：

- 很多有价值信息是跨多句、跨多轮的，需要归纳和抽象
- `topOfMind`、`recentMonths` 这类分区本身就是摘要型文本，不适合纯规则构建
- 是否删除旧事实、如何整合新旧上下文，也更适合由模型做语义判断

但系统又没有完全相信 LLM，而是让 LLM 只输出结构化增量，然后由本地逻辑做约束应用。这是一个典型的“LLM 做语义理解，本地逻辑做边界控制”的组合。

## 14. 更新提示词的设计意图

`MEMORY_UPDATE_PROMPT` 不是一个简单的“帮我总结一下”提示词，而是一份非常明确的结构化更新协议。

它对模型提出了多层要求：

- 当前记忆和新对话都要纳入考虑
- `user` 各分区和 `history` 各分区有不同的长度与语义要求
- `facts` 需要给类别和置信度
- 事实删除要显式给出待删除 ID
- 上传文件事件绝对不能进入记忆

这个提示词最重要的价值在于，它把原本模糊的“长期记忆更新”任务，转成了一个约束充分的结构化输出任务。

## 15. 增量应用逻辑是如何受控的

### 15.1 摘要分区的更新不是全量重写所有区域

`_apply_updates()` 会逐个查看：

- `workContext`
- `personalContext`
- `topOfMind`
- `recentMonths`
- `earlierContext`
- `longTermBackground`

只有当某个分区同时满足：

- `shouldUpdate` 为真
- 且提供了新的 `summary`

系统才会更新该分区，并刷新对应 `updatedAt`。

这说明模块不会因为一次局部变化就盲目重写整份记忆。

### 15.2 事实是增量追加且带清理机制

对于 facts，系统支持两种动作：

- 删除指定 ID 的事实
- 追加新的事实

追加时还会检查置信度阈值，只有达到配置要求的事实才会真正进入长期记忆。

这一步非常重要，因为它把“模型可能产生很多猜测”收束成了“只有足够可信的事实才会落盘”。

### 15.3 上限控制不是按时间，而是按置信度

当事实总数超过 `max_facts`，系统会按置信度排序，只保留前 N 条。

这说明事实列表的裁剪原则不是最近优先，而是可信度优先。这个取舍很合理，因为长期记忆的目标是保留最稳固、最可靠的事实，而不是机械追求时序新鲜度。

## 16. 上传污染清理为什么做了两层

这是这个模块里最值得注意的 tricks 之一。

### 16.1 第一层：消息过滤阶段拦截

在 `MemoryMiddleware` 里，系统先把 `<uploaded_files>` 区块从 human 消息中剥离，避免这些临时路径进入送给 LLM 的对话文本。

### 16.2 第二层：落盘前再清理一次

在 `MemoryUpdater` 应用完 LLM 输出之后，系统还会用 `_strip_upload_mentions_from_memory()` 对最终记忆再扫一遍，删除：

- summary 中描述上传事件的句子
- facts 中描述上传行为的条目

这一步说明作者并不完全信任上游过滤和 LLM 遵循提示词的能力，而是又做了一层结果清洗。

这种双保险机制很成熟，因为它承认：

- 上游过滤可能漏掉某些表达
- LLM 也可能仍然把上传事件归纳进记忆

于是最终写盘前再做一次强制清洗，降低长期污染风险。

### 16.3 正则规则是刻意收窄的

上传清理规则不是简单匹配所有“file”字样，而是刻意只匹配上传事件相关句式，例如：

- uploaded file
- file upload
- `/mnt/user-data/uploads/`
- `<uploaded_files>`

同时像“用户常处理 CSV 文件”“用户偏好 PDF 导出”这类合法长期偏好会被保留。

这说明实现者很清楚“文件相关事实”和“上传事件”不是一回事，正则写法是带区分意识的，而不是粗暴删除。

## 17. 注入主 Agent 时如何控制长度

### 17.1 不是整份记忆都注入

`format_memory_for_injection()` 会把当前记忆格式化成适合系统提示词注入的文本，但它并不会把所有字段一股脑放进去。

当前注入重点是：

- `user` 分区里的工作背景、个人背景和当前关注点
- `history` 分区里的近期和较早历史摘要

也就是说，注入策略本身已经做了一轮信息筛选，不是完整镜像存储结构。

### 17.2 注入长度有 token 上限

格式化后，系统会估算 token 数。若超出 `max_injection_tokens`，就按比例截断文本并留出余量。

这里有两个值得注意的细节：

- 若安装了 `tiktoken`，会用更准确的 token 统计
- 若不可用，则退回到基于字符数的粗略估算

这说明作者既希望在能力足够时做精确控制，也不想让模块对可选依赖形成硬耦合。

### 17.3 注入本身也可开关

即使记忆系统启用，是否把记忆注入提示词仍由 `injection_enabled` 单独控制。这意味着项目明确区分了两个阶段：

- 记忆是否持续积累
- 记忆是否参与当前模型决策

这种拆分很有价值，因为有些场景可能希望“后台持续积累长期画像，但暂时不喂给模型”。

## 18. 记忆模型为什么默认关闭 thinking

`MemoryUpdater` 在创建模型时显式使用 `thinking_enabled=False`。这传达出一个很清晰的工程判断：

- 记忆更新是一个结构化摘要任务
- 它更强调稳定、成本和吞吐
- 不需要占用更昂贵的思考型模式

这说明项目把记忆更新看作“后台维护任务”，而不是“高推理深度任务”。

## 19. Gateway 暴露了什么能力

当前 Gateway 对记忆模块暴露的是读接口，而不是任意写接口。主要包括：

- 获取当前记忆数据
- 强制重载记忆数据
- 获取当前记忆配置
- 一次性获取配置与当前数据

这说明记忆系统默认认为自己的写入入口应当是内部记忆更新管线，而不是让外部随意 patch JSON。这样的边界更安全，也更符合“长期画像由系统维护”的定位。

## 20. Agent 级记忆隔离的意义

这是另一个非常重要但容易被忽略的点。

自定义 Agent 可以拥有各自独立的记忆文件。这带来的含义不仅是“文件分开放”，更是：

- 不同 Agent 可以积累不同的长期画像
- 一个专业 Agent 的长期偏好不会污染另一个 Agent
- 删除 Agent 时，其配置、SOUL 和记忆可以一起清理

这说明 lumen 的记忆模块并不把“用户长期画像”理解成单一全局对象，而是允许在多 Agent 生态下做角色级隔离。

从代码链路上看，这个隔离是端到端传递的，而不是只靠命名约定：

- `lead_agent` 创建 `MemoryMiddleware` 时可显式传入 `agent_name`
- 中间件入队时把 `agent_name` 和 `thread_id`、过滤后的消息一起提交
- 队列处理时原样把 `agent_name` 传给 `MemoryUpdater.update_memory()`
- `MemoryUpdater` 再通过 `_get_memory_file_path(agent_name)` 选择全局或 Agent 专属 `memory.json`
- `get_memory_data()` / `reload_memory_data()` 的缓存键同样是 `agent_name`
- `_get_memory_context(agent_name)` 注入系统提示词时，也读取同一作用域下的记忆

因此，全局记忆和自定义 Agent 记忆的隔离不是“文件碰巧不同”，而是更新、读取、缓存和注入都共享同一个 `agent_name` 作用域。

## 21. 这个模块里的几个关键 tricks

如果把持久化记忆模块最有价值的工程技巧提炼出来，主要有下面这些。

### 21.1 用中间件异步投递，而不是主路径同步更新

这样不阻塞用户请求，同时减少高频写入。

### 21.2 用队列防抖和按线程去重

这样记忆更新更像阶段性整合，而不是每轮碎片化覆写。

### 21.3 用“摘要分区 + 离散事实”双轨存储

既保留叙述性脉络，又保留高价值原子事实。

### 21.4 用 LLM 产出增量，用本地逻辑做边界控制

语义理解交给模型，存储边界和阈值控制交给程序。

### 21.5 对上传噪声做双层过滤

先过滤消息，再清洗落盘结果，极大降低长期污染风险。

### 21.6 用 mtime 做轻量缓存失效

在无需复杂同步机制的前提下兼顾性能和一致性。

### 21.7 支持 Agent 级记忆隔离

这让长期记忆真正适配多 Agent 场景，而不只是单一用户画像。

## 22. 当前实现的能力边界

从现有代码看，这个模块也有一些很明确的边界。

- 它基于本地 JSON 文件，不是分布式共享存储
- 记忆更新仍然依赖 LLM 输出 JSON，存在模型质量边界
- facts 裁剪主要按置信度而非复杂时序策略
- Gateway 主要提供读与重载，不提供细粒度编辑接口
- 注入文本目前聚焦摘要分区，并没有把全部 facts 原样塞给模型

这些都不是缺陷，而是当前架构下相当清晰的取舍。它说明这个模块优先追求的是稳定、可解释和成本可控，而不是把长期记忆做成一个复杂知识库系统。

## 23. 这个模块的本质是什么

如果只看表面，lumen 的持久化记忆模块像是“把用户信息写进 `memory.json`”。但从实现看，它其实是一条完整的长期画像数据管线：

- 先从会话结果中筛出适合长期保存的信息
- 通过队列和防抖控制更新节奏
- 用专门的模型把新对话整合成结构化增量
- 受控应用到长期记忆对象中
- 清理临时噪声后原子写盘
- 再把可控长度的摘要重新注入下一轮系统提示词

所以，这个模块不是简单的“存档系统”，而是一套长期用户建模机制。它让 lumen 在多轮、多线程和多 Agent 场景下，不再只依赖短期消息历史，而拥有了一层真正可持续、可演化、可注入的长期记忆。
