# Lumen 持久化记忆模块技术说明

## 1. 模块定位

Lumen 的持久化记忆不是聊天消息历史，也不是一个所有用户共享的全局文件。它是从已完成对话中提炼出的长期用户画像，按 Backend 认证身份派生的 opaque scope 隔离，并可在 scope 内继续按自定义 Agent 隔离。

三类状态的职责不同：

| 状态 | 生命周期 | 所有权 | 用途 |
| --- | --- | --- | --- |
| Thread/checkpoint | 单次会话及其恢复周期 | LangGraph | 消息历史、工具调用和运行状态 |
| Knowledge files | 文档 revision 生命周期 | Backend | 当前会话获准读取的知识材料 |
| Long-term memory | 跨线程、跨 Runtime 重启 | 当前认证用户 scope | 稳定背景、偏好、目标和高价值事实 |

长期记忆不会从任意客户端 scope 或旧全局文件读取。缺少可信 scope 时，读取返回空画像，更新和提示词注入都被禁用。

## 2. 信任边界

### 2.1 scope 由 Backend 产生

业务 Backend 是最终用户身份和会话所有权的授权边界。认证用户启动 Runtime run 时，Backend 使用带域分隔的 HMAC-SHA256 派生 scope：

```text
memory_scope = HMAC-SHA256(
  SECRET_KEY,
  "lumen/runtime-memory-scope/v1\\0" || canonical_user_uuid_bytes
)
```

结果是 64 个小写十六进制字符。它稳定地区分用户，但不直接暴露用户 UUID。

相关实现：

- `backend/modules/chat/runtime_memory_scope.py`
- `backend/modules/chat/runtime_run_controller.py`

Backend 会删除调用方传入的 `memory_scope`：

- 已认证用户：覆盖为服务端派生值
- guest：彻底移除 scope，因此不读取、不写入、不注入长期记忆

Runtime 仍会严格校验 scope 格式，但格式校验不是授权。只有 Backend 派生并经内部网络传入的 scope 才可信。

### 2.2 Runtime 内部传播

scope 通过 LangGraph Runtime context 传播，不放在模型可自由修改的业务输入里。它参与以下链路：

```text
Backend authenticated identity
    -> authorized run context
    -> ScopedMemoryPromptMiddleware
    -> MemoryMiddleware
    -> MemoryUpdateQueue
    -> MemoryUpdater
    -> scoped JSON file
```

`InsightFlowClient` 的嵌入式调用模式只接受构造时传入的可信 scope；单次调用覆盖值不能替换它。

### 2.3 Gateway 接口

Gateway 的 Memory API 要求显式传入合法 scope：

- `GET /api/memory?memory_scope=...&agent_name=...`
- `POST /api/memory/reload?memory_scope=...&agent_name=...`
- `GET /api/memory/config`
- `GET /api/memory/status?memory_scope=...&agent_name=...`

生产拓扑中 Gateway 整个 `/api` 面由独立内部 token 保护，不能直接暴露给浏览器。Memory 路由不会在缺少 scope 时回退到全局数据。

## 3. 存储分区

### 3.1 默认路径

未配置 `memory.storage_path` 时，数据位于：

```text
{LUMEN_HOME}/memories/
  {memory_scope}/
    memory.json
    agents/
      {agent_name}/
        memory.json
```

分区键是 `(memory_scope, agent_name)`：

- `memory_scope` 隔离不同认证用户
- `agent_name` 可选，在同一用户 scope 内隔离不同 Agent
- `agent_name` 会转成小写，且只允许字母、数字和连字符

同名 thread、同名 Agent 或同一 Runtime worker 都不能突破 scope 边界。

### 3.2 `storage_path` 兼容语义

`memory.storage_path` 现在表示 scoped 存储根：

- 空值：使用 `{LUMEN_HOME}/memories/`
- 相对目录：必须位于 `LUMEN_HOME` 内
- 绝对目录：直接作为 scoped 根
- 历史 JSON 文件名，例如 `memory.json`：仅作为位置提示，实际写到相邻的 `memory.json.scoped/` 目录

相对路径逃逸 `LUMEN_HOME` 会被拒绝。

### 3.3 旧文件隔离

历史实现使用的以下文件被视为 legacy quarantine：

```text
{LUMEN_HOME}/memory.json
{LUMEN_HOME}/agents/{agent_name}/memory.json
```

Runtime 永不自动读取、注入或迁移这些文件。这是有意的 fail-closed 行为，避免升级后把旧全局画像泄漏给第一个访问者。

需要迁移旧数据时，必须在明确知道原数据所有者的前提下，由运维工具映射到正确的 scope；不能做自动兜底。

## 4. 数据模型

每个 scope/agent 分区使用结构化 JSON：

```json
{
  "version": "1.0",
  "lastUpdated": "2026-07-15T12:00:00Z",
  "user": {
    "workContext": {"summary": "", "updatedAt": ""},
    "personalContext": {"summary": "", "updatedAt": ""},
    "topOfMind": {"summary": "", "updatedAt": ""}
  },
  "history": {
    "recentMonths": {"summary": "", "updatedAt": ""},
    "earlierContext": {"summary": "", "updatedAt": ""},
    "longTermBackground": {"summary": "", "updatedAt": ""}
  },
  "facts": [
    {
      "id": "fact_ab12cd34",
      "content": "用户偏好中文技术说明",
      "category": "preference",
      "confidence": 0.9,
      "createdAt": "2026-07-15T12:00:00Z",
      "source": "thread-id"
    }
  ]
}
```

摘要分区保存可持续整合的叙述性背景；`facts` 保存带来源和置信度的离散事实。新事实低于 `fact_confidence_threshold` 时不会落盘；超过 `max_facts` 后按置信度保留前 N 条。

## 5. 更新数据流

### 5.1 对话过滤

`MemoryMiddleware.after_agent()` 只在一轮 Agent 执行完成后采样。进入记忆管线前会过滤：

- `ToolMessage`
- 含 `tool_calls` 的中间 AI 消息
- human 消息中的 `<uploaded_files>` 临时路径区块
- 仅包含上传区块的 human 消息及其配对 assistant 回复

过滤后至少需要一条 human 消息和一条最终 AI 消息。这样长期画像不会吸收工具轨迹、临时文件路径或未完成轮次。

### 5.2 防抖队列

`MemoryUpdateQueue` 使用 `(memory_scope, agent_name, thread_id)` 去重。防抖窗口内同一分区、同一线程只保留最新上下文；不同用户即使 thread ID 相同，也不会互相覆盖队列项。

队列当前是 Runtime 进程内的 `threading.Timer` 加内存列表：

- 它不阻塞用户请求
- 它降低高频对话导致的重复模型调用
- 它不是持久队列；进程硬退出可能丢失尚未开始的更新
- 多个 Runtime 进程拥有各自队列，最终写入一致性由文件锁保证

因此长期记忆属于 best-effort 派生数据，不能承载必须一次不丢的业务事实。

### 5.3 LLM 增量更新

`MemoryUpdater` 读取当前画像，把“当前画像 + 过滤后的对话”交给关闭 thinking 的模型，并要求模型返回结构化 JSON 增量。程序只应用显式 `shouldUpdate` 的摘要分区、事实新增和事实删除，不允许模型直接控制文件路径或发布动作。

落盘前会再次清理上传事件相关摘要和 facts，形成输入过滤与输出清理两层防护。

## 6. 并发与崩溃一致性

### 6.1 锁粒度

每个最终 `memory.json` 有独立锁文件。实现同时使用：

- 进程内 `threading.RLock`
- Linux `fcntl.flock`

更新路径在同一个排他锁内执行“读取 -> LLM 合并 -> 写入”，避免两个 Runtime worker 从相同旧快照分别覆盖彼此。不同 scope 使用不同锁，可并行更新。

当前部署依赖 Linux/Docker；`fcntl` 方案不适用于原生 Windows Runtime。

### 6.2 原子发布

发布顺序为：

1. 在目标目录创建唯一临时文件
2. 权限设为 `0600`
3. 写 JSON、flush、`fsync(file)`
4. `os.replace()` 原子替换目标文件
5. `fsync(directory)` 持久化目录项
6. 更新进程内缓存

取消、异常或多进程并发不会暴露半写 JSON；遗留临时文件会在失败路径清理。

### 6.3 读取缓存

缓存键包含完整文件路径、scope 和 agent。返回值使用深拷贝，调用方不能原地污染其他请求看到的数据。缓存通过 `(mtime_ns, size, inode)` 文件签名失效，外部原子替换后能够重新加载。

## 7. 提示词注入

`ScopedMemoryPromptMiddleware` 在每次 model call 时从当前 Runtime context 解析 scope，再读取对应画像。不能在构建全局 graph 时预先捕获某个用户的记忆，否则复用 graph 会造成跨用户泄漏。

注入满足以下条件才发生：

- `memory.enabled=true`
- `memory.injection_enabled=true`
- 当前 run 有合法可信 scope
- 当前分区存在可注入内容

注入长度由 `max_injection_tokens` 控制。缺少 scope 的 guest 和直接调用者得到空记忆上下文。

## 8. 配置

```yaml
memory:
  enabled: true
  storage_path: ""
  debounce_seconds: 30
  model_name: null
  max_facts: 100
  fact_confidence_threshold: 0.7
  injection_enabled: true
  max_injection_tokens: 2000
```

关键约束：

| 配置 | 约束 | 含义 |
| --- | --- | --- |
| `debounce_seconds` | 1 到 300 | 队列静默窗口 |
| `max_facts` | 10 到 500 | 每个 scope/agent 的事实数上限 |
| `fact_confidence_threshold` | 0 到 1 | 新事实最低置信度 |
| `max_injection_tokens` | 100 到 8000 | 单次模型调用的记忆注入上限 |

## 10. 运维注意事项与剩余边界

### 10.1 `SECRET_KEY` 轮换

scope 由 Backend `SECRET_KEY` 派生。直接轮换密钥会为同一用户生成不同 scope，使旧画像不可达。生产轮换需要先选择并测试以下策略之一：

- 离线把旧 scope 目录迁移到新 scope
- 在有限过渡期支持旧钥读取、新钥写入

不要通过恢复读取旧全局 `memory.json` 来解决轮换问题。

### 10.2 备份和权限

`LUMEN_HOME` 是持久数据卷；备份应包含 `memories/`，恢复时保留文件所有权和权限。Gateway 与 LangGraph 共享该卷，但它们不应把这些文件暴露为静态资源。

### 10.3 当前非目标

当前实现不提供：

- 跨节点共享文件锁语义
- 持久、可重放的记忆更新任务
- 用户自助逐字段编辑 API
- 自动判断旧全局文件所有者

如果部署扩展到多主机 Runtime，应把画像和更新队列迁移到支持租户键、事务/CAS 和持久任务的共享存储；不能假设网络文件系统上的 `flock` 与本地磁盘完全等价。
