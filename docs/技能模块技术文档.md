# lumen 技能模块技术说明

## 1. 文档目标

本文详细介绍 lumen 中的 skills 模块。重点不是说明“技能怎么写”，而是解释这个项目如何把磁盘上的技能目录、扩展配置、沙盒挂载、提示词注入和安装分发组织成一个真正可运行的技能系统。

阅读本文后，读者应能够回答以下问题：

- 技能在这个项目里到底是什么，它和普通提示词片段有什么区别
- 系统是如何发现技能、解析元数据并决定启用状态的
- 技能为什么能被 Agent 在运行时真正读取和执行，而不只是存在于仓库里
- `public` 与 `custom` 两类技能在实现上有什么差异
- 技能启停为什么不修改 `SKILL.md` 本身，而是写入扩展配置
- `.skill` 安装链路是如何工作的，以及它在系统里如何作为产物流转

### 1.1 先给出六个直接答案

- 技能到底是什么：它不是单纯的一段提示词，而是一种以目录和 `SKILL.md` 为物理载体、可被模型按需读取的运行时知识包。
- 系统如何发现技能并决定启用状态：先扫描 `skills/` 下的 `public` 与 `custom` 目录，解析 `SKILL.md` 元数据，再叠加扩展配置里的启用状态。
- 技能为什么能在运行时真正被读取：因为系统不仅把技能索引注入提示词，还把技能目录映射到稳定运行时路径，模型后续可以再通过 `read_file` 等工具按需读取正文。
- `public` 与 `custom` 的差异是什么：前者更像项目预置或官方技能集合，后者更像用户安装或本地扩展区域，但两者在运行时都走同一套加载协议。
- 为什么启停不改 `SKILL.md`：因为技能内容本身和部署态开关是两回事，启用状态写入扩展配置可以避免污染技能正文，也更适合管理预置技能。
- `.skill` 安装链路是什么：`.skill` 本质是 ZIP 归档，它可以作为线程产物或上传文件进入系统，再经校验、预解析和复制流程安装到 `skills/custom`。

## 2. 模块定位

lumen 的 skills 模块，本质上是一个“文件系统驱动的运行时知识包系统”。它不是一组硬编码在 Python 里的策略，也不是一个仅供前端展示的模板市场，而是介于以下几层之间的桥接模块：

- 磁盘上的技能目录结构
- Agent 系统提示词注入逻辑
- 沙盒中的文件可见性
- Gateway 提供的技能管理接口
- 扩展配置中的启用状态管理

换句话说，在这个项目里，技能不是一个抽象概念，而是一类有明确物理载体和运行路径的对象。一个技能只有同时满足以下条件，才能真正参与 Agent 行为：

- 技能目录被扫描到
- `SKILL.md` 元数据解析成功
- 当前启用状态允许它暴露出来
- 技能路径被映射进沙盒或本地执行环境
- 系统提示词把技能清单告诉模型
- 模型再通过 `read_file` 等工具去读取技能正文和附属资源

这套链路说明，skills 模块不是“直接把所有技能内容塞进上下文”，而是做了一次分层加载。

## 3. 整体设计原则

从实现上看，skills 模块遵循了几条很明确的原则。

第一，技能是文件系统对象，不是数据库对象。系统通过扫描目录发现技能，而不是维护一张中心化注册表。

第二，技能元数据与技能正文分离。运行时先只读取 `SKILL.md` 的 frontmatter 提取最小元信息，再决定是否在提示词里暴露这项技能。

第三，技能默认轻量暴露，按需深入加载。模型在系统提示词里先只看到名称、描述和文件位置，只有在判断某项技能相关时才会进一步调用 `read_file` 读取正文。

第四，启用状态是外部配置，不改技能本体。也就是说，开关技能不会编辑技能目录，而是写入扩展配置文件。这让技能内容和部署态状态解耦。

第五，技能不是只能“预装在仓库中”，也支持作为 `.skill` 归档包在会话线程中流转并安装到 `custom` 区域。

## 4. 代码分层与职责分工

skills 模块的关键代码可以分成五层。

- `runtimes/backend/src/skills/types.py`
  定义 `Skill` 数据结构，是技能在内存中的统一表示。

- `runtimes/backend/src/skills/parser.py`
  负责解析单个 `SKILL.md`，提取最小元数据。

- `runtimes/backend/src/skills/loader.py`
  负责扫描技能目录、组装 `Skill` 对象、叠加启用状态并返回结果。

- `runtimes/backend/src/config/skills_config.py`
  负责技能目录路径和容器挂载路径配置。

- `runtimes/backend/src/agents/lead_agent/prompt.py`
  负责把启用技能列表注入系统提示词，告诉模型如何使用技能。

除此之外，还有两条外围链路也很重要：

- `runtimes/backend/src/gateway/routers/skills.py`
  提供技能列表、状态更新和 `.skill` 安装接口。

- 沙盒提供者中的技能挂载逻辑
  保证模型在运行时真的能通过容器路径访问技能文件。

## 5. 技能在内存里是什么样子

### 5.1 `Skill` 不是全文，而是索引对象

`Skill` 数据类里保存的不是完整技能正文，而是一组足以支持运行时索引和定位的元信息：

- `name`
- `description`
- `license`
- `skill_dir`
- `skill_file`
- `relative_path`
- `category`
- `enabled`

这个结构说明技能加载器做的事不是“把技能内容全部解析成对象模型”，而是先构建一个可索引的目录项。正文依然留在文件系统中，等模型真正需要时再读取。

这是一种很典型的 progressive loading 设计。它能避免系统提示词在一开始就被所有技能正文塞满。

### 5.2 为什么要保存 `relative_path`

`relative_path` 是一个很关键但容易忽略的字段。它表示从分类根目录到技能目录的相对路径，而不是简单的技能名称。

这带来两个好处：

- 技能目录可以支持层级组织，而不强制所有技能都平铺在 `public` 或 `custom` 根目录下
- 容器路径和文件路径可以通过统一规则推导出来，而不依赖硬编码目录名

换句话说，这个字段让技能系统天然支持“目录层级即命名空间”的组织方式。

### 5.3 容器路径计算不是附属功能，而是运行时关键路径

`Skill` 上有两个很实用的方法：

- 获取技能目录在容器内的完整路径
- 获取 `SKILL.md` 在容器内的完整路径

这两个方法的意义在于，提示词里暴露给模型的不是宿主机路径，而是一个稳定的容器语义路径。后续模型用 `read_file` 读取时，也正是通过这个路径进入技能系统。

这说明 `Skill` 类型本身就已经带有“运行时地址生成器”的角色，而不只是一个元数据容器。

## 6. 技能是如何被发现的

### 6.1 默认根目录的推导方式

默认情况下，技能根目录不是从当前工作目录随意猜的，而是通过 `runtimes/backend/src/skills/loader.py` 中的 `get_skills_root_path()` 按项目结构推导出来的。

其逻辑很简单但很稳定：

- 先定位 `runtimes/backend/src/skills/loader.py` 所在位置
- 向上回退到 `backend` 目录
- 再取它的同级 `skills` 目录

也就是说，项目默认认为技能根目录位于仓库根下的 `skills/`，并且与 `backend/` 同级。

这种写法的好处是，不依赖运行时的当前工作目录，只依赖代码文件自身的位置，因此在不同启动方式下都更稳定。

### 6.2 扫描策略是按分类目录递归遍历

`load_skills()` 会固定扫描两个分类目录：

- `public`
- `custom`

每个分类目录下都使用递归遍历去寻找 `SKILL.md`。这说明系统并不要求技能必须直接挂在一级目录下，只要某个子目录里存在 `SKILL.md`，它就会被视为一个技能目录。

这里还有两个实现细节值得注意。

第一，遍历时会对目录名排序，并跳过隐藏目录。排序的目的不是美观，而是为了让加载结果稳定，减少不同文件系统返回顺序带来的不确定性。

第二，判断一个目录是不是技能目录的条件非常明确：必须存在名为 `SKILL.md` 的主文件。没有这份文件，目录里的其他资源不会被单独视为技能。

### 6.3 只加载 `public` 和 `custom`，体现了发布模型

skills 模块的分类设计很简单，但含义很强：

- `public` 更像项目预置或官方提供的技能集合
- `custom` 更像用户安装或本地扩展得到的技能集合

系统并没有做更复杂的多租户分层，而是用这两个目录完成了“内置能力”和“用户扩展能力”的分离。这样后续的安装逻辑、默认启用逻辑和权限预期都更清晰。

## 7. 元数据解析的实现逻辑

### 7.1 解析入口只关心 frontmatter

`parse_skill_file()` 读取 `SKILL.md` 后，首先通过正则提取顶部 YAML frontmatter。若 frontmatter 不存在，技能直接被忽略。

这说明在当前实现里，frontmatter 不是锦上添花，而是技能对象得以被系统识别的硬条件。

### 7.2 当前运行时解析器是“最小可用解析器”

一个非常重要的实现细节是：运行时加载器并没有使用完整 YAML 解析器去处理 `SKILL.md`，而是做了一个简单的逐行 `key: value` 解析。

这带来的特征很明显：

- 它对简单 frontmatter 很快、很轻量
- 它只真正依赖极少数字段
- 它并不试图完整理解复杂嵌套 YAML

从代码看，运行时真正需要的核心字段只有：

- `name`
- `description`
- 可选的 `license`

只要这几个字段存在，系统就可以构造出 `Skill` 对象。

这其实是一个很实用的工程取舍。技能正文会在后续由模型读取，运行时预解析只需要拿到最小索引信息，不必把 frontmatter 解析成复杂配置树。

### 7.3 失败策略是静默跳过而不是阻断全局加载

如果某个技能的 `SKILL.md` 不存在、frontmatter 不合法、缺少必要字段，或者解析过程中出现异常，`parse_skill_file()` 不会抛出错误终止整个加载过程，而是返回 `None`。

这意味着 skills 模块默认采用的是“局部失败，整体继续”的策略。一个坏技能不会拖垮整套技能系统，这对开放式扩展目录非常重要。

这个宽容策略只适用于单个文件无法解析的情况。成功解析出的技能名称必须在
`public` 与 `custom` 全部可见目录中全局唯一；重复名称会让详情、启停和提示词位置
产生遍历顺序依赖，因此 Loader 会明确拒绝整次加载，而不是静默选择其中一份。

## 8. 启用状态是如何叠加上去的

### 8.1 启用态不存于技能文件，而存于扩展配置

技能对象在解析出来时，`enabled` 初始为真，但这只是一个默认值。真正的启用状态会在 `load_skills()` 里通过扩展配置重新覆盖。

这一步的意义很大，因为它说明：

- `SKILL.md` 描述技能是什么
- 由 Git 忽略的运行态 `extensions_config.json` 决定技能当前是否可用；仓库中的 `extensions_config.example.json` 只提供格式示例

也就是说，技能内容与部署态开关是完全分离的。

### 8.2 为什么这里也从磁盘重新读取配置

`load_skills()` 并没有只依赖进程内缓存的 extensions 配置，而是显式调用 `ExtensionsConfig.from_file()` 从磁盘读取。

这样设计和 MCP 模块类似，核心目的是解决 Gateway 与 LangGraph Server 分进程时的配置一致性问题。Gateway 更新技能启停状态后，Agent 所在进程不需要重启，只要下一次加载技能时重读磁盘即可看到新状态。

这是一种非常务实的跨进程同步策略。

### 8.3 默认启用规则有一个清晰的倾向

`ExtensionsConfig.is_skill_enabled()` 的逻辑很有意思：

- 如果配置里明确写了技能状态，就按配置来
- 如果没有写状态，则 `public` 和 `custom` 类技能默认启用

这意味着系统默认是“只要技能存在，就倾向让它可用”，而不是保守地默认禁用所有技能。这个取向更符合技能系统的定位，因为技能本身就是为了扩展 Agent 能力。

## 9. `enabled_only` 的意义

`load_skills()` 支持 `enabled_only` 参数。这个参数不是单纯为了列表过滤，而是贯穿了两类运行模式：

- 管理界面和 API 查询时，需要看到全部技能，包括已禁用项
- 系统提示词注入时，只应该暴露当前启用技能

因此，`enabled_only` 实际上把技能模块分成了两个视角：

- 管理视角：关心全部安装状态
- 运行时视角：只关心当前可用能力

这个设计避免了“为了展示禁用技能而误把它们暴露给模型”的问题。

## 10. 技能为什么能真正被 Agent 使用

这是 skills 模块最重要的问题。

很多系统会把技能做成一段额外提示词，然后就结束了。但 lumen 并不是这样做的。它把技能真正接入运行时，依赖两条链路同时成立：

- 提示词告诉模型有哪些技能、技能文件在哪
- 沙盒或本地环境保证这些文件路径实际可读

只有这样，模型才能在需要时调用 `read_file` 去读取技能正文和附属资源。

## 11. 提示词注入的实现逻辑

### 11.1 注入内容不是技能全文，而是技能目录索引

`get_skills_prompt_section()` 会加载全部启用技能，然后在系统提示词里构造一个 `<skill_system>` 片段。这个片段包含每项技能的：

- 名称
- 描述
- 主文件位置

换句话说，系统提示词里注入的是技能目录索引，而不是技能正文。这正是 skills 模块的核心技巧之一。

模型先通过这些摘要信息判断“这项技能是否相关”，若相关，再按提示词要求去读取对应 `SKILL.md`。

### 11.2 Prompt 里显式规定了使用协议

技能片段里并不只是列出技能清单，还显式告诉模型一套使用流程：

- 当用户请求和技能用例匹配时，先读技能主文件
- 读懂技能工作流和说明
- 技能文件中引用的外部资源只在需要时再继续加载
- 之后严格遵循技能说明

这说明 skills 模块真正实现的是一种“模型侧调用约定”。技能并不是自动执行的，而是通过提示词把模型约束到一种固定的 progressive loading 模式上。

### 11.3 `available_skills` 是一个很实用的裁剪开关

`get_skills_prompt_section()` 支持 `available_skills` 过滤集。这意味着某些特殊 Agent 可以只暴露技能子集，而不是继承整个技能生态。

最典型的用法出现在 bootstrap 场景。引导阶段 Agent 只需要使用 `bootstrap` 技能，因此系统可以在构造提示词时只放出这一项。

这个能力很重要，因为它说明 skills 模块并不是全局强绑定的，它也支持按 Agent 场景裁剪暴露面。

### 11.4 主提示词里把技能提升成一条工作原则

除了技能清单本身，主系统提示词的 critical reminders 里还专门加入了 `Skill First` 约束，要求模型在处理复杂任务前优先加载相关技能。

这相当于给技能系统做了一个全局优先级声明。也就是说，技能不是“碰巧存在的可选文档”，而是被明确纳入主 Agent 行为规范的一等机制。

## 12. 沙盒挂载为什么是技能模块成立的前提

### 12.1 技能文件必须在运行环境中可见

如果系统提示词里只告诉模型“技能文件在 `/mnt/skills/...`”，但运行环境里根本没有这个路径，那么整个技能系统就只是纸面设计。

因此，skills 模块真正可用的关键前提，是沙盒层必须把宿主机技能目录映射到运行时路径。

### 12.2 本地沙箱模式的做法

在本地沙箱提供者里，系统会读取 `SkillsConfig`：

- 找到宿主机技能目录
- 找到配置中的容器路径，默认是 `/mnt/skills`
- 建立容器路径到本地实际路径的映射

后续 `LocalSandbox` 在处理命令和文件路径时，会根据这套映射把容器语义路径解析成宿主机路径，再在输出里反向替换回来。

这一步的意义非常大，因为它让本地开发环境也能保持与容器环境一致的技能路径语义。

### 12.3 容器沙箱模式的做法

在 aio 容器沙箱提供者里，技能目录会作为只读挂载加入容器，目标路径同样是配置中的容器路径。

这里的关键 trick 是：

- 技能目录使用只读挂载，降低风险
- 在 Docker inside Docker 场景下，优先允许通过宿主机环境变量指定技能目录路径，保证真正的 Docker daemon 能解析该路径

这说明 skills 模块从一开始就考虑了“Agent 在容器里读技能文件”的真实执行问题，而不是只在提示词层停留。

## 13. `SkillsConfig` 的作用

`SkillsConfig` 看起来只有两个字段，但它是技能系统路径语义的中心：

- `path`
- `container_path`

其中：

- `path` 决定宿主机上技能根目录在哪
- `container_path` 决定模型和沙盒里看到的技能根路径是什么

这两个维度分开后，技能系统就拥有了很好的部署弹性：

- 本地开发可以用默认仓库路径
- 生产环境可以把技能目录放在别的位置
- 容器内对模型暴露的路径仍然可以保持稳定

这正是路径抽象的价值所在。

## 14. Gateway 是如何管理技能状态的

### 14.1 列表与详情接口

Gateway 暴露了技能列表和单项详情接口，这部分本身并不复杂。它们的关键作用是把 `load_skills(enabled_only=False)` 的结果转成 API 可消费的结构，便于前端或管理端展示全部技能，包括禁用项。

### 14.2 启停接口为什么不改 `SKILL.md`

技能状态更新接口只会修改 `extensions_config.json` 中的技能启用状态，不会编辑技能目录里的 `SKILL.md`。

这是一种很正确的边界划分：

- `SKILL.md` 是技能内容
- `extensions_config.json` 是当前部署态

如果把启用状态写进 `SKILL.md`，就会把“技能本身是什么”和“本次部署是否启用”混在一起，尤其对 `public` 技能来说更不合理。

### 14.3 写回配置时要保留 MCP 配置

更新技能状态时，Gateway 不是只写 skills 部分，而是会保留当前 `mcpServers` 配置一起写回。

这背后的原因和 MCP 模块一样：`extensions_config.json` 是技能与 MCP 的共享配置文件。如果更新技能状态时不保留 MCP 配置，就会把别的扩展配置冲掉。

这说明技能模块虽然逻辑独立，但在存储层和 MCP 模块存在明显的共享边界。

## 15. `.skill` 安装链路是怎么工作的

### 15.1 `.skill` 本质上是 ZIP 归档

系统把技能分发格式定义成 `.skill` 文件，但从实现上看，它本质是 ZIP 压缩包。这个设计非常实用：

- 打包和传输简单
- 可以原样保留技能目录结构
- 附属资源如 `scripts`、`references`、`assets` 都能一起打包

### 15.2 安装来源是线程产物，而不是本地任意路径

Gateway 的安装接口接收的是：

- 线程 ID
- 一个线程虚拟路径

也就是说，安装流程默认认为 `.skill` 文件是当前会话线程中的一个产物或上传文件，然后再把它安装到全局 `skills/custom` 目录。

这是一个很有代表性的设计：技能包可以由 Agent 生成、由用户上传、再通过线程产物进入安装流程。skills 模块与会话系统是打通的。

### 15.3 安装算法的主要步骤

从实现看，安装流程大致分成以下几步：

第一步，把线程虚拟路径解析成真实文件路径。

第二步，校验文件存在、是普通文件、扩展名为 `.skill`，且确实是合法 ZIP。

第三步，把压缩包先解压到临时目录，而不是直接复制到目标目录。

第四步，判断技能内容是“外层单目录包裹”还是“文件直接位于压缩包根目录”，两种结构都兼容。

第五步，读取并校验 `SKILL.md` frontmatter，提取技能名。

第六步，检查 `public` 与 `custom` 全部可见技能中是否已有同名所有者。

第七步，通过同文件系统目录重命名，把完整暂存目录原子发布到 `skills/custom/<skill-name>`。

这个流程的核心思想是“先验证，后落盘”，避免把非法归档直接写进技能库。

### 15.4 frontmatter 校验器的职责

安装流程使用的 frontmatter 校验器比运行时加载器更严格。它会检查：

- 是否存在 `SKILL.md`
- 是否存在合法 YAML frontmatter
- frontmatter 是否是字典
- 是否包含不允许的字段
- `name` 和 `description` 是否存在且合法
- 技能名称是否符合命名规范

这说明 skills 模块实际上有两级解析策略：

- 运行时加载器采用最小解析，只关心能否把技能索引出来
- 安装器采用严格校验，目的是保证新进入系统的技能质量和命名规范

这是一种很合理的分工。面向存量读取时应宽容，面向新内容写入时应严格。

## 16. `.skill` 文件如何作为产物被访问

skills 模块不仅支持安装技能，还支持把 `.skill` 归档中的内部文件作为线程产物读取。

Gateway 的 artifacts 路由里专门支持一种路径形式：请求 `.skill` 压缩包内的内部文件，例如读取其中的 `SKILL.md`。

这意味着一个技能包在会话里不只是一个黑盒压缩文件，还可以被拆开查看其中的文本资源。这个能力带来两个好处：

- 用户或 Agent 可以在安装前先查看技能正文
- 技能包可以像其他产物一样被预览、审查和分发

这进一步说明 `.skill` 不只是安装输入格式，也是系统里的可观察产物格式。

## 17. 嵌入式客户端与 Gateway 的双入口

skills 模块不仅有 Gateway API，也有嵌入式 `InsightFlowClient` 的直接调用入口。

客户端提供了：

- 列出技能
- 获取技能详情
- 更新技能状态
- 安装技能

这说明技能系统并不依赖 Gateway 才能使用。即使在嵌入式或单进程场景下，也可以直接通过客户端 API 管理技能。

同时，客户端在安装 `.skill` 时还额外加入了一些本地安全检查，例如限制解压总大小、检查压缩包内路径是否安全以及去除符号链接。这说明项目作者已经把“技能包来自外部”视为需要谨慎处理的输入。

## 18. 一个很重要的实现特征：技能正文不是由后端解释执行

skills 模块和很多插件系统不同的一点是，它默认并不把 `SKILL.md` 解析成某种后端 DSL，也不在 Python 侧执行技能正文逻辑。

技能正文真正的执行者是模型自身。后端做的事主要是：

- 发现技能
- 提供元数据
- 暴露文件路径
- 保证文件可读
- 通过提示词教模型如何读取和遵循技能

这说明 skills 模块更准确的定位是“面向模型的运行时知识包系统”，而不是“服务器端插件执行引擎”。

## 19. 技能模块中的几个关键 tricks

如果把这个模块里最值得借鉴的工程技巧提炼出来，主要有以下几点。

### 19.1 用元数据索引代替全文预加载

系统提示词只暴露技能摘要和路径，正文按需读，极大降低了上下文占用。

### 19.2 用文件系统做技能注册表

技能是否存在，由目录和 `SKILL.md` 决定，而不是靠额外数据库同步。

### 19.3 用扩展配置保存启停状态

这样既能热更新，又不会污染技能本体内容。

### 19.4 用容器路径统一模型视角

无论本地还是容器模式，模型看到的技能路径都是稳定的 `/mnt/skills/...` 语义。

### 19.5 安装时严格，运行时宽容

这是 skills 模块最成熟的一点。安装链路用严格校验保证新增内容质量，运行时加载则尽量局部容错，不让坏技能拖垮整个系统。

### 19.6 让技能成为线程产物的一种

通过 `.skill` 格式和 artifacts 路由，技能可以生成、预览、传输、安装，形成完整闭环。

## 20. 当前实现的能力边界

从现有实现看，skills 模块也有一些明确边界。

- 运行时 frontmatter 解析比较轻量，更偏向最小索引，不追求完整 YAML 语义
- 当前分类模型固定为 `public` 和 `custom`
- 技能的执行逻辑主要依赖模型遵循提示词约定，而不是后端强制编排
- 启停状态是全局性的，不是按线程或按用户细粒度隔离

这些都不是缺陷，而是当前架构下非常清晰的取舍。它表明 skills 模块优先追求的是：足够灵活、成本可控、易于扩展，而不是把技能系统做成一个复杂的插件框架。

## 21. 这个模块的本质是什么

如果只看表面，lumen 的 skills 模块像是一个 `skills/` 目录加若干 `SKILL.md` 文件。但从实现角度看，它实际上是一套完整的运行时扩展机制。

它做了以下几件关键事情：

- 把磁盘目录里的技能发现出来并转换成统一对象
- 通过最小元数据解析建立技能索引
- 通过扩展配置控制技能启停状态并支持跨进程热生效
- 通过系统提示词把技能目录暴露给模型
- 通过沙盒挂载让技能文件在运行时真实可读
- 通过 `.skill` 归档和安装接口支持分发与增量扩展

所以，skills 模块在这个项目里既不是单纯的“文档目录”，也不是传统意义上的“后端插件”。它更接近一个以文件系统为载体、以提示词协议为执行入口、以沙盒路径为可达保证的模型侧扩展运行时。
